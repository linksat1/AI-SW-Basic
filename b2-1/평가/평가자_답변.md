# B2-1 가계부 콘솔 프로그램 평가자 답변

평가 항목별 구현 방식, 코드 위치, 실행 근거를 정리했습니다. 코드 경로는 `b2-1/` 기준입니다.

## 항목 1. 기능과 데이터 영속성

### 명령 기능

프로그램은 거래 추가·목록·검색·요약·예산 설정·카테고리 관리·수정·삭제·CSV 가져오기·내보내기를 제공합니다. 명령별 인자 처리와 실행 함수는 [`budget_app/cli.py`](../budget_app/cli.py)에 있습니다.

### 데이터 저장

거래, 카테고리, 예산을 각각 JSONL 파일로 나누어 저장합니다.

| 파일 | 저장 내용 |
|---|---|
| `data/transactions.jsonl` | 거래 ID, 날짜, 타입, 카테고리, 금액, 메모, 태그 |
| `data/categories.jsonl` | 등록된 카테고리 이름 |
| `data/budgets.jsonl` | 월과 예산 금액 |

각 저장소가 파일 경로와 입출력을 맡습니다. 저장소 생성은 [`cli.py`](../budget_app/cli.py)의 `_build_service()`, JSONL 읽기·쓰기는 [`repository.py`](../budget_app/repository.py)에 있습니다.

### 카테고리 보호와 예산 계산

거래에서 사용 중인 카테고리는 삭제할 수 없습니다. 예산을 저장한 뒤 월별 요약을 실행하면 사용률과 초과 경고를 출력합니다.

실행 결과 근거:

- 사용 중인 `food` 삭제 시도: [`09_category_remove_blocked.txt`](../제출/results/09_category_remove_blocked.txt) — 오류 메시지와 종료 코드 1
- 예산 초과 요약: [`07_summary_after_budget.txt`](../제출/results/07_summary_after_budget.txt) — 사용률 185.0%, 초과 경고 출력

### CSV 스키마

CSV 열은 `date,type,category,amount,memo,tags`입니다. `import`는 UTF-8 CSV를 행 단위로 읽고, `export`는 헤더를 포함한 UTF-8 CSV를 기록합니다. 관련 코드는 [`service.py`](../budget_app/service.py)의 `import_csv()`와 `export_csv()`입니다.

### 오류와 종료 코드

예상한 오류는 원인과 해결 힌트를 표시합니다. 정상 실행은 종료 코드 0, 오류는 0이 아닌 코드를 반환합니다. 실제 결과는 [`10_update_not_found.txt`](../제출/results/10_update_not_found.txt)와 [`11_export_missing_condition.txt`](../제출/results/11_export_missing_condition.txt)에서 확인할 수 있습니다.

## 항목 2. 모듈과 클래스의 책임 경계

모듈은 바뀌는 이유가 서로 다른 기능별로 나누었습니다.

| 모듈 | 책임 |
|---|---|
| `__main__.py` | CLI 프로그램의 시작점 |
| `cli.py` | 명령 옵션 처리, 사용자 입력, 화면 출력 |
| `service.py` | 입력 검증, 가계부 규칙, 월별 계산 |
| `repository.py` | JSONL 파일 읽기와 쓰기 |
| `models.py` | 거래 데이터 구조인 `Transaction` 정의 |
| `decorators.py` | 오류 처리, 실행 로그와 시간 측정 |

주요 클래스도 각자 맡은 역할이 다릅니다.

- `Transaction`: 거래 한 건의 필드와 데이터 변환
- `TransactionRepository`: 거래 파일의 추가·조회·수정·삭제
- `CategoryStore` / `BudgetStore`: 카테고리와 월별 예산 저장
- `BudgetService`: 저장소와 검증 규칙을 연결해 거래·예산 기능을 처리

이렇게 나누면 화면을 바꿀 때는 CLI, 업무 규칙을 바꿀 때는 Service, 파일 형식을 바꿀 때는 Repository를 중심으로 수정할 수 있습니다.

## 항목 2. `update`/`delete`의 안전한 처리

JSONL은 행 길이가 달라질 수 있어 파일 중간의 거래만 직접 덮어쓰기 어렵습니다. 이 프로그램은 기존 내용을 읽고 변경 결과를 임시 파일에 기록한 뒤 `os.replace()`로 원본과 교체합니다. 핵심 함수는 [`repository.py`](../budget_app/repository.py)의 `_atomic_write_jsonl()`입니다.

```python
with tmp_path.open("w", encoding="utf-8") as f:
    for row in rows:
        f.write(json.dumps(row, ensure_ascii=False) + "\n")
os.replace(tmp_path, path)
```

새 파일 기록이 완료된 후 교체하므로, 기록 도중 실패했을 때 쓰다 만 내용으로 원본을 덮을 위험을 줄입니다. 모든 저장장치 장애에서 무조건 안전하다는 뜻은 아닙니다.

## 항목 3. 제너레이터와 스트리밍

`iter_all()`은 JSONL 파일을 한 줄씩 읽어 거래 객체를 `yield`합니다.

```python
def iter_all(self) -> Iterator[Transaction]:
    for row in _read_jsonl(self.path):
        yield Transaction.from_dict(row)
```

`yield`를 사용하면 파일의 모든 거래를 한 번에 리스트로 만들지 않고, 필요한 거래를 하나씩 처리할 수 있습니다. `list --limit N`은 `deque(maxlen=N)`을 사용해 최근 N건만 유지합니다.

현재 구현의 한계도 함께 설명해야 합니다. `search`는 최신순 결과를 내기 위해 일치하는 거래를 메모리에 모으고, CLI도 결과를 `list()`로 받습니다. 따라서 검색 결과가 많으면 메모리 사용량이 늘어납니다.

관련 코드는 [`repository.py`](../budget_app/repository.py)의 `iter_all()`, `latest()`, `search()`와 [`cli.py`](../budget_app/cli.py)의 `cmd_search()`입니다. 목록 실행 결과는 [`03_list.txt`](../제출/results/03_list.txt)에 있습니다.

## 항목 3. 데코레이터로 공통 기능 분리

명령 함수에는 `@handle_errors`와 `@log_execution`을 적용합니다.

```python
@handle_errors
@log_execution
def cmd_add(args):
    ...
```

- `log_execution`: 명령 함수명, 성공/실패 상태, 실행 시간을 `budget_app.log`에 기록합니다.
- `handle_errors`: 오류를 사용자용 메시지와 힌트로 바꾸고 종료 코드를 반환합니다.

이 공통 처리를 명령마다 반복 작성하지 않아도 됩니다. 구현은 [`decorators.py`](../budget_app/decorators.py), 실제 실행 기록은 [`budget_app_예시.log`](../제출/budget_app_예시.log)에서 확인할 수 있습니다.

## 항목 3. 타입 힌트의 이점

예를 들어 `validate_amount(amount_str: str) -> int`는 문자열을 받아 정수를 반환한다는 것을 함수 정의만 보고 알 수 있습니다.

```python
def validate_amount(amount_str: str) -> int:
    ...

def search_transactions(
    self,
    date_from: str | None = None,
) -> Iterator[Transaction]:
    ...
```

`str | None`은 검색 조건이 생략될 수 있음을 나타냅니다. 타입 힌트는 코드 이해와 IDE/정적 분석 도구에 도움을 주지만, 그 자체로 실행 중 입력값을 검사하지는 않습니다. 실제 검증은 [`service.py`](../budget_app/service.py)에서 수행합니다.

## 항목 4. JSONL을 저장 포맷으로 선택한 이유

JSONL은 한 줄에 JSON 객체 하나를 저장합니다. 표준 라이브러리로 읽고 쓰기 쉽고, 거래 추가는 파일 끝에 한 줄을 덧붙이면 됩니다. 반면 검색·요약은 파일을 순회해야 하고, 수정·삭제는 파일을 다시 작성해야 합니다.

CSV는 스프레드시트에서 다루기 좋고 행·열 데이터를 교환하기에 편리합니다. 다만 태그처럼 목록 형태의 데이터를 내부 저장 형식으로 표현할 때는 별도 변환 규칙이 필요합니다.

그래서 내부 데이터는 JSONL로 저장하고, 외부 교환에는 CSV를 사용합니다.

## 항목 4. 거래가 10만 건으로 늘어날 때의 병목과 개선

현재 구조에서 예상되는 병목은 다음과 같습니다.

1. **ID 생성:** `next_id()`가 새 거래를 추가할 때 기존 파일 전체를 확인합니다. CSV를 여러 행 가져오면 이 탐색이 반복될 수 있습니다.
2. **검색·요약·내보내기:** 인덱스 없이 파일 전체를 순회합니다. 검색과 내보내기는 결과를 메모리에 모으는 부분도 있습니다.
3. **수정·삭제:** 파일 전체를 읽고 새 파일로 다시 씁니다. 데이터가 많을수록 입출력 비용이 커집니다.

개선 방향으로는 ID 카운터/메타데이터 사용, CSV 일괄 처리, 날짜·카테고리 인덱스 또는 페이지 조회 도입을 고려할 수 있습니다. 질의와 동시성 요구가 더 복잡해지면 SQLite 같은 데이터베이스로 옮길 수 있습니다.

## 항목 4. 잘못된 CSV 행 처리와 사용자 신뢰

현재 `import`는 행마다 검증하고 `AppError` 또는 필수 열 누락(`KeyError`)이 있는 행을 건너뜁니다. 나머지 행은 계속 등록해 `imported`와 `skipped` 수를 출력합니다. 관련 코드는 [`service.py`](../budget_app/service.py)의 `import_csv()`와 [`cli.py`](../budget_app/cli.py)의 `cmd_import()`입니다.

현재 방식은 **행 단위 부분 성공**입니다. 실패한 행의 번호와 구체적인 사유는 출력하지 않습니다. 사용자 신뢰를 높이려면 행 번호·필드·오류 이유를 별도 리포트로 제공할 수 있습니다. 전체 롤백이 필요하다면 먼저 모든 행을 검증한 뒤 성공한 내용을 한 번에 저장하도록 설계할 수 있습니다.

가져오기 결과 예시는 [`12_import.txt`](../제출/results/12_import.txt)에 있습니다: `imported=2, skipped=1`.

## 발표용 요약 답변

> 거래·카테고리·예산을 JSONL 파일 세 개에 나누어 저장하고, CLI·서비스·저장소·모델로 책임을 분리했습니다. 파일은 제너레이터로 한 줄씩 읽고, 목록은 최근 N건만 유지합니다. 수정과 삭제는 임시 파일에 먼저 기록한 뒤 교체합니다. 공통 오류 처리와 실행 로그는 데코레이터로 적용했고, 타입 힌트로 함수와 데이터의 입출력 계약을 드러냈습니다. 현재 검색 결과는 메모리에 모이며, CSV 가져오기는 행 단위 부분 성공입니다. 거래가 크게 늘면 반복 전체 탐색과 재작성을 개선하겠습니다.

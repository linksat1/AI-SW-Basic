# B2-1 가계부 콘솔 프로그램 설명 및 평가 질문 대비 자료

이 자료는 `budget_app/`에 구현한 파일 기반 가계부 콘솔 프로그램이 과제 목표를 어떻게
만족하는지, 평가자 앞에서 아주 쉬운 말로 설명할 수 있도록 정리한 문서입니다.
외워서 말하기보다, 아래 설명을 본인 말투로 바꿔서 연습하는 용도로 사용하세요.
모든 예시는 실제 실행 결과([제출/results/](제출/results/), [제출/실행결과.md](제출/실행결과.md))로 검증했습니다.

## 1. 과제 결과물 한 줄 설명

이번 과제는 **표준 라이브러리만으로 만든 Python CLI 가계부 프로그램**입니다.

```
budget_app/
├── __main__.py     ← 실행 진입점
├── cli.py          ← 입력/출력만 담당
├── service.py       ← 검증 + 비즈니스 규칙
├── repository.py    ← 파일 저장/조회 (JSONL)
├── models.py         ← 데이터 구조(Transaction)
├── decorators.py     ← 예외처리/로그/시간측정 분리
└── errors.py         ← 사용자 오류 타입(AppError)
```

`add/list/search/summary/budget/category/update/delete/import/export` 10개 명령이 모두
동작하며, 데이터는 `transactions.jsonl / categories.jsonl / budgets.jsonl` 3개 파일로 저장됩니다.

## 2. 파일 기반 저장(JSONL)으로 CRUD/검색/요약/입출력을 구현했는지 설명

**아주 쉬운 설명**: 데이터베이스 서버 없이, 그냥 텍스트 파일에 한 줄에 하나씩
JSON으로 거래를 적어두는 방식입니다. `data/transactions.jsonl`을 열어보면 이렇게 생겼습니다.

```json
{"id": "TX-000001", "date": "2024-01-15", "type": "expense", "category": "food", "amount": 18000, "memo": "점심(수정)", "tags": ["meal"]}
```

| 동작 | 구현 방법 |
|---|---|
| Create(추가) | `add` → 파일 맨 끝에 한 줄 추가(append) |
| Read(조회) | `list`/`search` → 파일을 한 줄씩 읽어서 조건에 맞는 것만 보여줌 |
| Update(수정) | `update` → 전체를 다시 읽으면서 해당 줄만 바꾼 뒤 통째로 다시 씀 |
| Delete(삭제) | `delete` → 전체를 다시 읽으면서 해당 줄만 빼고 다시 씀 |
| 검색 | `search` → 기간/카테고리/타입/키워드/태그 조건을 모두 만족하는 줄만 필터링 |
| 요약 | `summary` → 특정 월(`YYYY-MM`)로 시작하는 날짜만 모아서 합계/카테고리별 집계 |
| 입출력 | `import`/`export` → 내부 저장은 JSONL이지만, 외부 교환용으로는 CSV 스키마를 고정해서 변환 |

**말로 설명하는 예시**: "제출/results/10_update.txt를 보시면, `TX-000001`의 금액과 메모만
바뀌고 나머지 거래는 그대로인 걸 확인할 수 있습니다. 파일을 부분적으로 고치는 게 아니라
전체를 다시 읽어서 새로 쓰는 방식이라, 중간에 프로그램이 멈춰도 파일이 반토막 나지 않도록
임시 파일에 먼저 쓰고(`os.replace`) 통째로 교체합니다."

## 3. 콘솔 프로그램을 클래스/모듈로 구조화한 설명 (계층별 책임)

| 계층 | 파일 | 책임 | 하지 않는 일 |
|---|---|---|---|
| CLI | `cli.py` | 사용자 입력 받기, 화면 출력 | 파일을 직접 읽거나 쓰지 않음, 검증 규칙을 직접 판단하지 않음 |
| Service | `service.py` | 날짜/금액/카테고리 검증, 예산 계산, CSV 변환 규칙 | 파일이 JSONL인지 CSV인지는 모름 |
| Repository | `repository.py` | JSONL 파일을 어떻게 읽고 쓰는지 | 날짜 형식이 맞는지는 검사하지 않음 |
| Model | `models.py` | `Transaction`이 어떤 필드로 구성되는지 | 저장 방식이나 검증 로직은 모름 |

**말로 설명하는 예시**: "`cli.py`의 `cmd_add` 함수는 `input()`으로 값을 받아서
`service.add_transaction(...)`을 호출할 뿐, 날짜가 올바른지는 직접 검사하지 않습니다.
검증은 `service.py`의 `validate_date` 함수가 담당합니다. 만약 나중에 저장 방식을
JSONL에서 CSV로 바꾸고 싶다면 `repository.py`만 고치면 되고, `cli.py`나 `service.py`는
건드릴 필요가 없습니다. 이렇게 책임을 나누면 한 부분을 고칠 때 다른 부분이 깨질 위험이 줄어듭니다."

**클래스 최소 2개 요구사항**: `Transaction`(모델), `TransactionRepository`/`CategoryStore`/`BudgetStore`(저장소),
`BudgetService`(서비스)까지 총 5개 클래스를 사용했습니다.

## 4. yield 기반 제너레이터로 스트리밍 처리하는 이유와 동작 방식 설명

`repository.py`의 핵심 코드:

```python
def iter_all(self) -> Iterator[Transaction]:
    """파일을 한 줄씩 읽어 Transaction으로 변환해 yield (스트리밍)."""
    for row in _read_jsonl(self.path):
        yield Transaction.from_dict(row)
```

**아주 쉬운 설명**: `return`은 결과를 한 번에 다 만들어서 통째로 돌려주지만,
`yield`는 "하나 만들 때마다 바로 하나씩 건네주는" 방식입니다.
거래가 100만 건이 있어도, `iter_all()`은 한 번에 100만 개짜리 리스트를 메모리에
만들지 않고, 호출하는 쪽에서 하나씩 꺼내 쓸 때마다 딱 그만큼만 처리합니다.

`list --limit N`은 여기서 한 걸음 더 나아갑니다.

```python
def latest(self, limit: int) -> Iterator[Transaction]:
    window: deque[Transaction] = deque(maxlen=limit)
    for tx in self.iter_all():
        window.append(tx)
    yield from reversed(window)
```

**말로 설명하는 예시**: "`deque(maxlen=limit)`는 크기가 정해진 상자입니다.
새 항목이 들어오면 가장 오래된 항목이 자동으로 밀려나가기 때문에, 파일에 거래가
몇 건이 있든 이 상자는 항상 `limit`개만큼의 크기만 유지합니다. 그래서 '최근 N건'을
구하기 위해 전체 데이터를 리스트로 만들어 정렬할 필요가 없습니다."

**실제 확인**: `제출/results/03_list.txt`에서 `--limit 3`을 주면 정확히 3건만,
가장 최근에 추가한 순서(`TX-000004` → `TX-000003` → `TX-000002`)로 출력되는 것을 볼 수 있습니다.

## 5. 데코레이터로 공통 관심사(로그/예외/시간측정)를 분리한 구조와 이유 설명

```python
@handle_errors
@log_execution
def cmd_add(args: argparse.Namespace) -> int:
    ...
```

**아주 쉬운 설명**: 데코레이터는 함수를 다른 함수로 감싸서 "원래 함수가 실행되기 전/후에
자동으로 끼워 넣을 동작"을 정의하는 방법입니다. `cmd_add` 본문에는 "무엇을 할지"만 있고,
"실행 시간을 재고 로그를 남기는 일"과 "오류가 나면 예쁘게 출력하는 일"은
`decorators.py`에 따로 정의해서 여러 명령 함수에 재사용합니다.

- `log_execution`: 함수 실행 전후 시간을 재서 `budget_app.log`에 `[시각] 함수명 status=OK/ERROR elapsed=Xms`로 기록
- `handle_errors`: 함수 안에서 발생한 `AppError`(예상된 오류)나 예상 못한 예외를 잡아서
  스택트레이스 대신 `[오류]`/`[힌트]` 메시지로 바꾸고, 성공 시 종료 코드 0, 실패 시 1을 반환

**왜 나눴는가?**: "만약 이 로직을 10개 명령 함수마다 똑같이 복사해서 넣었다면, 나중에
로그 형식을 바꾸고 싶을 때 10곳을 다 고쳐야 합니다. 데코레이터로 분리하면 `decorators.py`
한 곳만 고치면 모든 명령에 자동으로 반영됩니다."

**실제 확인**: `제출/budget_app_예시.log`를 보면 `cmd_category_remove status=ERROR`,
`cmd_export status=ERROR`처럼 실패한 명령도 로그에 정확히 남아 있고,
`제출/results/10_update_not_found.txt`를 보면 존재하지 않는 id로 수정 시도 시
스택트레이스 없이 `[오류] 존재하지 않는 거래 id입니다` + 종료 코드 1만 나오는 것을 확인할 수 있습니다.

## 6. 타입 힌트로 입출력 계약을 명확히 했을 때의 이점 설명 (실제 코드 예)

```python
def validate_amount(amount_str: str) -> int:
    ...

@dataclass
class Transaction:
    id: str
    amount: int
    tags: list[str] = field(default_factory=list)

def search_transactions(
    self,
    date_from: str | None = None,
    ...
) -> Iterator[Transaction]:
    ...
```

**아주 쉬운 설명**: 타입 힌트는 함수에 붙이는 "이 함수는 이런 값을 받아서 이런 값을
돌려준다"는 설명서입니다. `validate_amount(amount_str: str) -> int`만 봐도
"문자열을 넣으면 정수가 나온다"는 걸 코드를 실행해보지 않고도 알 수 있습니다.

**실제로 얻은 이점**: `date_from: str | None = None`처럼 "없어도 되는 값"을 명시했기 때문에,
`search` 명령에서 `--from` 옵션을 안 줘도 되는 걸 코드만 보고 알 수 있었습니다.
만약 타입 힌트가 없었다면 이 함수가 `None`을 허용하는지, 항상 문자열이 필요한지
함수 내부 코드를 전부 읽어봐야 알 수 있었을 것입니다.

## 8. 평가 질문 대비 답변 자료

아래 답변은 외워서 말하기보다, 본인 말투로 자연스럽게 설명하는 연습용입니다.

### 항목 1. 저장 구조 확인 질문

**Q1. 왜 파일을 3개로 나눴는가? 하나로 합치면 안 되는가?**

거래, 카테고리, 예산은 성격이 다른 데이터입니다. 하나의 파일에 다 넣으면 "이 줄이
거래인지 카테고리인지 예산인지"를 매번 구분하는 코드가 필요해집니다. 파일을 나누면
`TransactionRepository`, `CategoryStore`, `BudgetStore`가 각자 자기 파일만 신경 쓰면 되므로
코드가 단순해집니다.

**Q2. update/delete를 구현할 때 왜 "한 줄만 바꾸기"가 아니라 "전체를 다시 쓰기"를 택했는가?**

JSONL은 텍스트 파일이라 중간 줄의 길이가 바뀌면(예: 금액이 15000 → 180000으로 자릿수가
늘어나면) 그 뒤에 있는 모든 내용을 밀어내야 합니다. 파일 시스템은 이런 "중간 삽입"을
효율적으로 지원하지 않기 때문에, 안전하게 하려면 전체를 새로 쓰는 편이 낫습니다.
대신 안전성을 위해 임시 파일에 먼저 쓰고 `os.replace`로 원자적으로 교체합니다.

**Q3. `os.replace`로 원자적 교체를 하는 이유는?**

파일에 쓰는 도중 프로그램이 강제 종료되면, 쓰다 만 파일이 남을 수 있습니다.
임시 파일에 새 내용을 다 쓴 뒤 `os.replace`로 한 번에 이름을 바꿔치기하면,
쓰는 도중 문제가 생겨도 원본 파일은 이전 상태 그대로 남고 절대 반쯤 깨진 상태가 되지 않습니다.

### 항목 2. 검증/예외 처리 질문

**Q1. 잘못된 입력이 들어오면 프로그램이 어떻게 반응하는가?**

`add`처럼 대화형 입력을 받는 명령은 값이 유효할 때까지 같은 질문을 다시 합니다
(`제출/results/13_add_invalid_date_retry.txt` 참고). `update`처럼 옵션으로 값을 받는
명령은 잘못된 값이면 `AppError`를 던지고, `handle_errors` 데코레이터가 이를 잡아서
`[오류]`/`[힌트]` 메시지를 보여주고 종료 코드 1로 끝냅니다.

**Q2. 스택트레이스를 왜 안 보여주는가?**

스택트레이스는 개발자에게는 유용하지만 일반 사용자에게는 "무슨 문제인지, 어떻게
고쳐야 하는지" 알려주지 않습니다. `AppError`에 `message`(원인)와 `hint`(해결 힌트)를
따로 담아서, 사용자가 바로 이해하고 조치할 수 있는 메시지만 보여주도록 했습니다.

**Q3. 예상하지 못한 오류(버그)가 나면 어떻게 되는가?**

`handle_errors`는 `AppError`뿐 아니라 일반 `Exception`도 잡습니다. 실제로 JSONL 파일을
일부러 손상시켜서 테스트했을 때도(`Expecting value: line 1 column 1` 같은 파싱 오류),
스택트레이스 없이 `[오류] 처리 중 문제가 발생했습니다: ...` 메시지와 함께 종료 코드 1로
안전하게 종료되는 것을 확인했습니다.

---

### 항목 3. 명령 설계 질문

**Q1. `update`를 옵션 기반과 대화형 중 어떤 방식으로 고정했고, 이유는?**

옵션 기반(`update --id <id> [--date ...] ...`)으로 고정했습니다. 수정은 보통 "특정 필드
하나만 빠르게 바꾸는" 경우가 많아서, 매번 모든 필드를 대화형으로 다시 입력받는 것보다
바꾸고 싶은 값만 옵션으로 지정하는 편이 실무적으로 더 편리하다고 판단했습니다.

**Q2. `category add`/`remove`는 왜 대화형으로 만들었는가?**

과제 예시 화면(`category add` 실행 시 `카테고리명: ` 프롬프트)이 대화형으로 제시되어
있었고, 카테고리는 자주 바뀌는 값이 아니라 가끔 관리하는 값이라 대화형으로도 충분하다고
판단했습니다.

**Q3. `export`에 왜 `--month` 또는 `--from/--to` 중 하나가 필수인가?**

조건 없이 실행하면 전체 데이터를 무조건 다 내보내게 되는데, 의도치 않게 전체 데이터가
파일로 빠져나가는 걸 방지하기 위해 최소 1개의 조건을 강제했습니다. 실제로 조건 없이
실행하면 `[오류] export는 --month 또는 --from/--to 조건이 최소 1개 필요합니다`가 출력되고
종료 코드 1로 끝나는 것을 확인했습니다(`제출/results/11_export_missing_condition.txt`).

**Q4. 카테고리 삭제 시 사용 중인 카테고리는 어떻게 처리했는가?**

삭제를 막는 방식을 선택했습니다. `remove_category`에서 `used_categories()`로 현재
거래에서 쓰이는 카테고리 집합을 구한 뒤, 삭제하려는 이름이 그 안에 있으면 `AppError`를
던져서 삭제를 거부합니다(`제출/results/09_category_remove_blocked.txt`).

---

### 항목 4. 설계 의도 질문

**Q1. `--data-dir` 옵션은 왜 만들었는가?**

기본값은 `./data`지만, 여러 사용자가 같은 프로그램을 다른 데이터로 테스트하거나,
테스트용 데이터와 실제 데이터를 분리하고 싶을 때를 대비해 저장 위치를 바꿀 수 있게 했습니다.

**Q2. id를 `TX-000001`처럼 만든 이유는?**

기존 거래 중 가장 큰 번호를 찾아 1을 더하는 방식(`next_id`)으로 구현했습니다.
6자리로 0을 채운 이유는 목록을 봤을 때 자릿수가 흔들리지 않아 정렬/가독성이 좋기 때문입니다.

**Q3. `list`/`search`의 "최신순"은 정확히 어떤 기준인가?**

파일에 저장된 순서(추가한 순서)의 역순입니다. 데이터가 항상 날짜순으로 입력된다는
보장이 없는 상태에서, 전체를 정렬하려면 파일 전체를 메모리에 올려야 해서 스트리밍의
장점이 사라집니다. 그래서 "입력 순서의 역순"을 최신순으로 정의했고, 이는 README에도
명시해뒀습니다.

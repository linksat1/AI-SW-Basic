검증 방법

주장(README)을 그대로 신뢰하지 않고 저장소를 직접 클론해 코드를 읽고, README가 제시한 tests/final_test_commands.txt를 실제로 실행해 출력을 대조했다. 이어서 README에 없는 엣지케이스(해시 충돌 유발, 20개 키 삽입 후 리사이징, 따옴표 파싱, 잘못된 입력)를 별도로 작성해 직접 프로빙했다.

02

강점과 확인할 점

강점

  • 자료구조 구현 정확도 — 체이닝 해시맵(로드팩터 0.75, 2배 확장·재해싱), 최소 힙, 이중 연결 리스트 모두 정상 동작 확인. data_structures/*.py
  • O(1) LRU 설계 — Entry가 자신의 lru_node 참조를 들고 있어 탐색 없이 즉시 이동/삭제
  • TTL lazy deletion — 힙에 stale 항목이 남아도 entry.expire_at과 비교해 안전하게 무시
  • 상태 일관성 — 삭제 로직을 _delete_key() 한 곳에 모아 HashMap/LRU/메모리/evicted_keys 불일치를 방지
  • 에러 처리 — unknown command, 인자 개수, 정수 파싱, OOM을 Redis 스타일 그대로 재현
  • 한계 자기 인지 — KEYS 순회 비용, 리사이징 stop-the-world, stale TTL 누적을 스스로 문서화함

구두로 확인할 점

  • move_to_front 설계 — 노드를 제자리에서 재연결하지 않고 삭제 후 재생성. 결과는 맞지만 매 GET/SET마다 객체가 새로 할당됨 doubly_linked_list.py:291
  • 문서 분량과 작성 시점 괴리 — 핵심 로직은 07-14 09:29~10:17(약 50분, 커밋 5개)에 완성. 1,600줄 README와 상세 주석은 3일 뒤 07-17 아침에 일괄 추가됨
  • KEYS 패턴 매칭 미구현 — 과제 범위 내로 보이나 본인 입으로 근거 확인 필요
  • 보너스 미구현 — 동적 배열, BST, Pub/Sub 등은 필수 범위 밖으로 스킵

## 1. 과제 개요

**만들어야 하는 것**: `dict`/`set`/`collections` 없이 해시맵·이중 연결
리스트·힙을 직접 구현해 만든 CLI 기반 Mini Redis (Python 표준 라이브러리만 사용)

**완성 기준** (`mini_redis/` 폴더에 이미 구현되어 있음):
- [x] String 명령어 6개: SET / GET / DEL / EXISTS / DBSIZE / KEYS
- [x] 메모리 관리 2개: CONFIG SET maxmemory / INFO memory
- [x] TTL 관리 2개: EXPIRE / TTL
- [x] `mini-redis>` 프롬프트의 REPL CLI (exit/quit 종료)
- [x] 이중 연결 리스트 직접 구현 (`linked_list.py`) — 모든 연산 O(1)
- [x] 체이닝 해시맵 직접 구현 (`hashmap.py`) — 직접 설계한 해시 함수, 로드 팩터 0.75 초과 시 2배 확장
- [x] 최소 힙 직접 구현 (`heap.py`) — `_heapify_up`/`_heapify_down` 포함
- [x] LRU 자동 제거(메모리 초과 시) + TTL 자동 만료(힙 기반) 흐름
- [x] Redis 스타일 출력(OK / (nil) / (integer) N / (error) ...) + 에러 처리 표준

**폴더 구조**:
```
b3-1/
├── 가이드.md                  ← 지금 보고 있는 이 문서
├── 과제                        ← 원본 과제 요구사항 (참고용, 수정 X)
├── 평가질문_설명자료.md         ← 평가 질문 대비 설명 자료
├── mini_redis/                 ← 실제 구현체 (제출물)
│   ├── __main__.py
│   ├── cli.py

│   ├── linked_list.py
```

## 2. 개발 환경 준비

이 과제는 **Python 3.8 이상**이 필요합니다.

```bash
python3 --version
```

외부 라이브러리 설치(`pip install`)는 전혀 필요 없습니다. 표준 라이브러리 중
`time`(TTL 계산)과 `shlex`(따옴표 값 파싱)만 사용했고, `dict`/`set`/`collections`는
과제 제약에 따라 전혀 사용하지 않았습니다.

## 3. 실행해보기

**항상 `b3-1` 폴더에서 실행해야 합니다.** (`mini_redis`가 그 안의 하위 폴더이기 때문입니다.)

```bash
cd b3-1
python3 -m mini_redis
```

`mini-redis> ` 프롬프트가 뜨면 아래를 순서대로 입력해봅니다.

### 3-1. String 기본 명령어

```
mini-redis> SET user:1 Alice
OK
mini-redis> GET user:1
"Alice"
mini-redis> EXISTS user:1
(integer) 1
mini-redis> DBSIZE
(integer) 1
mini-redis> SET user:2 Bob
OK
mini-redis> KEYS
1. "user:1"
2. "user:2"
mini-redis> DEL user:1
(integer) 1
mini-redis> GET user:1
(nil)
```

값에 공백이 있으면 큰따옴표로 감쌉니다: `SET user:3 "Charlie Park"`

### 3-2. 메모리 관리 + LRU 자동 제거

```
mini-redis> CONFIG SET maxmemory 30
OK
mini-redis> SET user:1 "Alice"
OK
mini-redis> SET user:2 "Bob"
OK
mini-redis> SET user:3 "Charlie"
OK
```

세 번째 SET까지 하면 총 사용량(33byte)이 maxmemory(30byte)를 넘어서 가장 오래
쓰이지 않은 `user:1`이 자동으로 지워집니다. 확인해봅니다.

```
mini-redis> GET user:1
(nil)
mini-redis> INFO memory
used_memory:22
maxmemory:30
evicted_keys:1
```

### 3-3. TTL 관리 (실제로 몇 초 기다려보기)

```
mini-redis> EXPIRE user:2 3
(integer) 1
mini-redis> TTL user:2
(integer) 2
```

**여기서 3초 이상 기다린 뒤** 다시 조회해봅니다.

```
mini-redis> GET user:2
(nil)
mini-redis> TTL user:2
(integer) -2
```

키가 자동으로 사라지고, `TTL`도 "키 없음"을 뜻하는 `-2`를 반환하는지 확인합니다.

### 3-4. 에러 처리 확인

```
mini-redis> CONFIG SET maxmemory abc
(error) ERR value is not an integer or out of range
mini-redis> GET
(error) ERR wrong number of arguments for 'GET' command
mini-redis> HELLO
(error) ERR unknown command 'HELLO'
```

### 3-5. 종료

```
mini-redis> exit
```

(`quit`도 동일하게 동작합니다.)

## 4. 코드 구조 한눈에 보기

| 파일 | 역할 | 한 줄 설명 |
|---|---|---|
| `__main__.py` | 진입점 | `python -m mini_redis`로 실행하면 가장 먼저 호출됨 |
| `cli.py` | 입출력 담당 | 사용자 입력 파싱 + Redis 스타일 출력 포맷팅 (저장 로직은 모름) |
| `store.py` | 규칙 담당 | SET/GET/TTL/LRU/메모리 제거 등 "무엇을 저장하고 언제 지울지" |
| `hashmap.py` | 자료구조 | 체이닝 방식 해시맵 (직접 설계한 해시 함수 포함) |
| `linked_list.py` | 자료구조 | 이중 연결 리스트 (체이닝 + LRU 순서 추적에 재사용) |
| `heap.py` | 자료구조 | 배열 기반 최소 힙 (TTL 만료 관리) |

**왜 이렇게 나눴나요?**: `cli.py`만 봐도 "이 프로그램이 어떤 명령을 받는지"와
"화면에 어떻게 보여주는지" 알 수 있고, `store.py`만 봐도 "이 프로그램의 저장
규칙이 뭔지" 알 수 있습니다. 세 자료구조 파일은 각각 독립적으로 테스트하고
재사용할 수 있도록 store.py의 비즈니스 로직과 완전히 분리했습니다.

**의존 관계**: `cli.py` → `store.py` → `hashmap.py` / `linked_list.py` / `heap.py`,
그리고 `hashmap.py` → `linked_list.py`(체이닝에 재사용). 자료구조 세 파일은
서로를 제외하면 store.py나 cli.py를 전혀 모릅니다(재사용 가능한 범용 모듈).

## 5. 핵심 개념 쉽게 이해하기

### 해시맵의 해시 함수와 충돌 해결(체이닝)

`hashmap.py`의 해시 함수:

```python
@staticmethod
def _hash_string(key: str) -> int:
    h = 0
    for ch in key:
        h = (h * 31 + ord(ch)) & 0xFFFFFFFF
    return h
```

**비유**: 우편번호처럼, 문자열(키)을 숫자 하나로 뭉개는 규칙입니다. 글자 하나씩
누적해서 31을 곱해가며 더하기 때문에, 같은 글자들이라도 순서가 다르면 완전히
다른 숫자가 나옵니다("ab"와 "ba"의 해시값이 다름). 이 숫자를 버킷 개수로
나눈 나머지가 "이 키는 몇 번 서랍에 넣을지"를 정합니다.

문제는 서랍(버킷) 개수보다 키가 많으면 필연적으로 두 키가 같은 서랍에
들어가는 "충돌"이 생긴다는 점입니다. 이때 그 서랍 안에 이중 연결 리스트를
두고 여러 (key, value)를 매달아 두는 것이 "체이닝"입니다. 조회할 때는 먼저
해시로 서랍을 찾은 뒤(O(1)), 그 서랍 안의 짧은 리스트만 순회해서(평균 O(1),
최악 O(n)) key가 일치하는 항목을 찾습니다.

### 이중 연결 리스트 + 해시맵으로 O(1) LRU를 만드는 방법

`store.py`는 두 자료구조를 함께 씁니다.

```python
self._lru_list = DoublyLinkedList()   # 사용 순서 (head=최근, tail=오래됨)
self._lru_nodes = HashMap()           # key -> 그 key가 위치한 Node
```

**비유**: `_lru_list`만 있으면 "이 키가 리스트의 어디에 있는지" 알아내려면
처음부터 끝까지 훑어야 합니다(O(n)). 하지만 `_lru_nodes`라는 "주소록"을 함께
들고 있으면, key 하나로 바로 그 Node 객체를 O(1)에 찾아낼 수 있고, Node를
손에 쥔 순간 `move_to_front`/`remove_node`도 이웃 포인터만 갈아 끼우면 되므로
O(1)입니다. 즉, "위치를 찾는 것"은 해시맵이, "찾은 다음 옮기는 것"은 연결
리스트가 담당하는 역할 분담 덕분에 전체가 O(1)이 됩니다.

`SET`이나 `GET`이 성공할 때마다 해당 키를 `head`(가장 최근)로 옮기고, 메모리가
부족해지면 `tail`(가장 오래 방치된 키)부터 지웁니다.

### 힙이 TTL 관리에 적합한 이유

```python
self._ttl_heap = MinHeap()   # (expire_at, key) 최소 힙
```

**비유**: 알람시계를 여러 개 맞춰놓고 "다음으로 울릴 알람이 뭔지" 알고
싶다고 생각해보세요. 알람을 시각순으로 정렬된 리스트에 넣으면 조회는
빠르지만(맨 앞만 보면 됨) 새 알람을 끼워 넣을 때마다 전체를 밀어야 해서
O(n)입니다. 반대로 그냥 아무 순서로나 쌓아두면 삽입은 빠르지만 "가장 빠른
알람"을 찾으려면 전부 훑어야 합니다(O(n)). 최소 힙은 "완전히 정렬하지는
않되, 항상 맨 위(root)에는 가장 작은 값이 오도록"만 유지해서, 삽입도
O(log n), "가장 빠른 것 확인"도 O(1)(peek), "가장 빠른 것 꺼내기"도
O(log n)로 둘 다 빠르게 만듭니다. TTL은 정확히 "다음에 뭐가 제일 먼저
만료되는지"만 반복해서 알면 되는 문제라서 힙과 궁합이 좋습니다.

이 프로젝트는 힙에서 꺼낸 항목이 "아직 유효한 TTL"인지 확인하는
**lazy deletion**(지연 삭제) 전략을 씁니다. `SET`으로 키를 덮어써서 TTL이
사라지거나 `EXPIRE`로 새 시각이 다시 설정되면, 힙 안에 남아있던 예전 항목은
"유령"이 되는데, 이런 유령은 굳이 힙에서 찾아 지우지 않고 나중에 꺼낼 때
현재 데이터와 비교해서 다르면 그냥 버립니다(`store.py`의
`_purge_expired_from_heap` 참고). 과제 명세에서도 이 방식을 명시적으로
허용합니다.

### 메모리 제한 환경에서 LRU로 제거하는 전체 흐름

`SET`이 호출됐을 때 `store.py`의 흐름:

1. 만료된 항목 정리(`_purge_expired_from_heap`) + 이 키가 이미 만료돼 있었다면 삭제
2. 새 (key, value)의 byte 크기가 maxmemory 자체보다 크면 → **아무것도 바꾸지 않고** OOM 에러
3. 기존 키가 있었다면 그만큼 `used_memory`를 먼저 빼고
4. 새 값을 저장하고 `used_memory`에 새 크기를 더함
5. 이 키를 LRU `head`로 이동(방금 사용했으므로)
6. `used_memory > maxmemory`인 동안 LRU `tail`(가장 오래된 키)을 하나씩
   제거하며 `used_memory`를 줄이고 `evicted_keys`를 1씩 증가

방금 저장한 키는 5번 단계에서 이미 `head`로 옮겨졌기 때문에, 6번의 제거
대상(tail)이 될 수 없습니다 — 그래서 "방금 넣은 키가 자기 자신 때문에
바로 다시 지워지는" 모순이 생기지 않습니다.

## 7. 자주 발생하는 문제 해결

### `ModuleNotFoundError: No module named 'mini_redis'`
- `b3-1` 폴더 **안에서** 실행하고 있는지 확인하세요. `cd b3-1` 후 다시 실행합니다.

### `SET user:1 Alice Kim`처럼 값에 공백이 있는데 따옴표를 안 쓰면?
- `(error) ERR wrong number of arguments for 'SET' command`가 납니다. 인자가
  3개(`user:1`, `Alice`, `Kim`)로 잘못 나뉘기 때문입니다. 공백이 있는 값은
  반드시 큰따옴표로 감싸세요: `SET user:1 "Alice Kim"`.

### TTL을 설정했는데 3초를 기다리지 않고 바로 조회하면?
- 아직 만료 시각이 안 지났으므로 `GET`은 정상 값을, `TTL`은 남은 초를
  그대로 보여줍니다. 실제로 시간이 지나야 자동 삭제를 확인할 수 있습니다.

### `INFO memory`의 `used_memory`가 예상과 다름
- `used_memory`는 오직 `len(utf8(key)) + len(utf8(value))`의 합입니다.
  자료구조 자체의 오버헤드(노드, 포인터 등)는 포함하지 않습니다. 한글처럼
  UTF-8에서 여러 byte를 쓰는 문자는 글자 수보다 byte 수가 더 크게 계산됩니다
  (예: 한글 1글자 = UTF-8 기준 3byte).

### 프로그램을 다시 실행했더니 이전에 넣은 데이터가 사라짐
- 정상입니다. 과제 제약사항에 "데이터 영속성(파일 저장)은 구현하지 않는다"고
  명시되어 있어, 메모리에만 저장하고 프로그램 종료 시 사라지도록 설계했습니다
  (Redis도 원래 In-Memory 저장소입니다).

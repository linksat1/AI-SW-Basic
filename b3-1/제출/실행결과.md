# B3-1 Mini Redis — 실행 결과 제출자료

`가이드.md`의 실행 시나리오를 실제로 실행한 결과입니다.
실행 환경: Python 3.9.6, 실행 위치: `b3-1/` (명령: `python3 -m mini_redis`)

모든 원본 캡처는 [`results/`](results/) 폴더에 시나리오별 텍스트 파일로 들어 있습니다.
아래는 그 결과를 과제의 "2. 최종 결과물" 항목 순서에 맞춰 정리한 요약입니다.

## 1. String 타입 기본 명령어 (SET/GET/DEL/EXISTS/DBSIZE/KEYS)

([results/01_string_기본명령어.txt](results/01_string_기본명령어.txt))

```
mini-redis> SET user:1 Alice
OK
mini-redis> GET user:1
"Alice"
mini-redis> EXISTS user:1
(integer) 1
mini-redis> EXISTS user:99
(integer) 0
mini-redis> DBSIZE
(integer) 1
mini-redis> SET user:2 Bob
OK
mini-redis> KEYS
1. "user:1"
2. "user:2"
mini-redis> DEL user:1
(integer) 1
mini-redis> DEL user:1
(integer) 0
mini-redis> GET user:1
(nil)
mini-redis> DBSIZE
(integer) 1
```

6개 명령(SET/GET/DEL/EXISTS/DBSIZE/KEYS) 모두 요구사항대로 동작합니다.
이미 삭제된 키를 다시 `DEL`하면 `(integer) 0`, 없는 키를 `GET`하면 `(nil)`을 반환합니다.

## 2. 메모리 관리 + LRU 자동 제거 (과제 예시 재현)

([results/02_메모리관리_LRU제거.txt](results/02_메모리관리_LRU제거.txt))

과제의 "8. 결과 예시"를 그대로 실행했습니다.

```
mini-redis> CONFIG SET maxmemory 30
OK
mini-redis> SET user:1 "Alice"
OK
mini-redis> SET user:2 "Bob"
OK
mini-redis> SET user:3 "Charlie"
OK
mini-redis> GET user:1
(nil)
mini-redis> INFO memory
used_memory:22
maxmemory:30
evicted_keys:1
mini-redis> KEYS
1. "user:2"
2. "user:3"
```

`user:1`(11byte) + `user:2`(9byte) + `user:3`(13byte) = 33byte로 maxmemory(30)를
초과하는 순간, 가장 오래 사용되지 않은 `user:1`이 자동으로 제거됩니다.
제거 후 `used_memory:22`(=9+13), `evicted_keys:1` — **과제 예시의 수치와 정확히 일치**합니다.

## 3. TTL 관리 (힙 기반, 실제 3초 경과 후 만료 확인)

([results/03_TTL_실제만료.txt](results/03_TTL_실제만료.txt))

```
mini-redis> EXPIRE user:2 3
(integer) 1
mini-redis> TTL user:2
(integer) 2

[※ 이 지점에서 실제로 3.2초 대기 후 다음 명령을 실행함]

mini-redis> GET user:2
(nil)
mini-redis> TTL user:2
(integer) -2
```

실제로 `time.sleep(3.2)`로 3.2초를 기다린 뒤 실행한 결과입니다. 3초 뒤 `GET`이
`(nil)`을 반환하며 키가 자동으로 삭제되었고, `TTL`도 "키 없음"을 뜻하는 `-2`를
반환합니다 — 과제 예시와 동일한 흐름입니다.

## 5. OOM (단일 엔트리가 maxmemory 자체를 초과)

([results/05_OOM_단일엔트리초과.txt](results/05_OOM_단일엔트리초과.txt))

```
mini-redis> CONFIG SET maxmemory 5
OK
mini-redis> SET toolong "abcdefgh"
(error) OOM command not allowed when used_memory > 'maxmemory'
mini-redis> DBSIZE
(integer) 0
mini-redis> INFO memory
used_memory:0
maxmemory:5
evicted_keys:0
```

`toolong`(7byte) + `abcdefgh`(8byte) = 15byte > maxmemory(5byte)이므로, 아무리
LRU로 다른 키를 지워도 공간을 만들 수 없는 경우입니다. 저장을 아예 시도하지
않고 OOM 에러만 반환하며, `used_memory`/`evicted_keys`가 전혀 변하지 않은
것으로 "아무 부작용 없이 실패"했음을 확인할 수 있습니다.

## 6. TTL/LRU 엣지 케이스

([results/06_TTL_엣지케이스.txt](results/06_TTL_엣지케이스.txt))

```
mini-redis> TTL nosuchkey
(integer) -2
mini-redis> EXPIRE nosuchkey 10
(integer) 0
mini-redis> SET k v1
OK
mini-redis> TTL k
(integer) -1
mini-redis> EXPIRE k 100
(integer) 1
mini-redis> TTL k
(integer) 99
mini-redis> SET k v2
OK
mini-redis> TTL k
(integer) -1
mini-redis> EXPIRE k -5
(integer) 1
mini-redis> EXISTS k
(integer) 0
```

- 없는 키의 `TTL` → `-2`, `EXPIRE` → `0`
- TTL이 없는 키의 `TTL` → `-1`
- `EXPIRE k 100` 이후 `SET k v2`로 덮어쓰면 TTL이 다시 `-1`(초기화)로 바뀝니다
  — **"SET이 기존 키를 덮어쓸 때 TTL은 초기화한다"** 규칙이 정확히 동작합니다.
- `EXPIRE k -5`(0 이하)는 "즉시 만료"로 처리되어 바로 삭제되고, 이어지는
  `EXISTS k`가 `0`을 반환합니다.

## 8. 해시맵 로드 팩터 초과 → 버킷 2배 확장

([results/08_해시맵_확장_대량삽입.txt](results/08_해시맵_확장_대량삽입.txt))

초기 버킷 용량 8, 로드 팩터 0.75이므로 이론상 7번째 키(7/8=0.875)부터 확장이
시작되어야 합니다. `key0`~`key19` 20개를 연속으로 넣으면 8→16→32로 최소 2번
이상 확장이 일어나는데, 확장(재해싱) 과정에 버그가 있었다면 일부 키가
유실되거나 덮어써졌을 것입니다.

```
mini-redis> DBSIZE
(integer) 20
mini-redis> GET key0
"val0"
mini-redis> GET key19
"val19"
mini-redis> KEYS
(20개 모두 출력됨 - 순서는 해시값 기준이라 삽입 순서와 다름)
```

`DBSIZE`가 정확히 20, 맨 처음 넣은 `key0`과 맨 마지막 `key19` 모두 정상
조회되어 확장 후에도 데이터 무결성이 유지됨을 확인했습니다.

## 10. 파싱/설정값 예외 처리 엣지케이스 (보충)

([results/10_예외처리_엣지케이스.txt](results/10_예외처리_엣지케이스.txt))

```
mini-redis> SET name "Alice Kim"
OK
mini-redis> SET name "unterminated
(error) ERR unbalanced quotes in input
mini-redis> CONFIG SET maxmemory -5
(error) ERR value is not an integer or out of range
mini-redis> EXPIRE name 3.5
(error) ERR value is not an integer or out of range
mini-redis> SET t v
OK
mini-redis> EXPIRE t 100
(integer) 1
mini-redis> SET t v2
OK
mini-redis> TTL t
(integer) -1
```

- 큰따옴표 짝이 맞지 않는 입력(`SET name "unterminated`)은 `shlex.split()`이
  `ValueError`를 던지고, 이를 `dispatch()`에서 잡아 `ERR unbalanced quotes in
  input`으로 표준화해서 반환합니다(코드: `mini_redis/cli.py`의 `dispatch()`).
- `CONFIG SET maxmemory -5`처럼 음수를 주면 `_parse_int()`는 파싱에 성공하지만
  `bytes_limit < 0` 조건에 걸려 정수 파싱 실패와 동일한 에러로 처리됩니다
  (`mini_redis/cli.py:_cmd_config`).
- `EXPIRE name 3.5`처럼 소수 TTL은 과제 스펙(정수 초 단위)에 따라
  `_parse_int()`가 `int("3.5")`에서 `ValueError`를 내며 그대로
  `ERR value is not an integer or out of range`로 거부됩니다.
- 기존 항목(6번)에서 확인한 "SET이 TTL을 초기화한다" 규칙(`EXPIRE t 100` →
  `SET t v2` → `TTL t`가 `-1`)도 이 실행에서 다시 한번 재현되었습니다.

## 11. 금지 API 미사용 검증 (보충)

과제 제약("dict/set/collections/heapq 사용 금지")을 실제로 지켰는지 소스
전체를 정적으로 검사했습니다.

```bash
$ grep -nE "\bdict\(|\bset\(|import collections|import heapq|from collections|from heapq" mini_redis/*.py
cli.py:92:        store.set(key, value)              # ← MiniRedisStore.set() 메서드 호출, 내장 set()이 아님
cli.py:170:    # 주석: "dict(테이블)로 만들지 않고 if/elif로 분기"
store.py:219:        # 주석: "이론상 set()의 ..." (설명용 문구, 실제 호출 아님)
```

세 건 모두 실제 `dict()`/`set()` 인스턴스화나 `collections`/`heapq` import가
아니라, 자체 메서드 이름(`.set(...)`)이나 주석 속 언급이었습니다. 즉 매핑은
`HashMap`, 우선순위 큐는 `MinHeap`, 순서 있는 목록은 `DoublyLinkedList`
직접 구현으로만 처리되며, 금지 API 사용은 0건으로 확인됩니다.

## 데이터 구조 자체 단위 검증 (보충)

REPL 실행과는 별개로, `mini_redis/linked_list.py`·`hashmap.py`·`heap.py` 세
모듈을 직접 import해 아래를 확인했습니다.

- **DoublyLinkedList**: `insert_front/insert_back/remove_front/remove_back/
  remove_node/move_to_front` 실행 후 리스트 내용이 매번 기대한 순서와 일치
- **HashMap**: 30개 키를 작은 초기 용량(4)에서 시작해 넣어 여러 차례 리사이즈를
  유도한 뒤 전부 정상 조회, `remove` 후 `contains`가 `False`로 바뀌는지,
  `get(key, default)`와 `get(key)`(KeyError) 두 형태 모두 정상 동작하는지 확인
- **MinHeap**: 무작위 50개 `(우선순위, 키)`를 넣고 전부 `pop()`했을 때
  결과가 정확히 오름차순 정렬과 일치(`popped == sorted(values)`)

세 자료구조 모두 예외 없이 통과했습니다.

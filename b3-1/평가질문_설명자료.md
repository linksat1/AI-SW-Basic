## 1. 과제 결과물 한 줄 설명

이번 과제는 **`dict`/`set`/`collections`를 전혀 쓰지 않고, 해시맵·이중 연결
리스트·최소 힙을 밑바닥부터 직접 구현해 만든 CLI 기반 Mini Redis**입니다.

```
mini_redis/
├── __main__.py      ← 실행 진입점
├── cli.py            ← REPL, 명령어 파싱, Redis 스타일 출력
├── store.py          ← String/메모리(LRU)/TTL 저장 규칙 (핵심 엔진)
├── hashmap.py         ← 체이닝 해시맵 (직접 설계한 해시 함수)
├── linked_list.py     ← 이중 연결 리스트 (체이닝 + LRU 순서 추적에 재사용)
└── heap.py            ← 배열 기반 최소 힙 (TTL 만료 관리)
```

`SET/GET/DEL/EXISTS/DBSIZE/KEYS`(String 6개) + `CONFIG SET maxmemory/INFO
memory`(메모리 2개) + `EXPIRE/TTL`(TTL 2개), 총 10개 명령이 모두 Redis 스타일
출력(`OK`, `(nil)`, `(integer) N`, `(error) ...`)으로 동작합니다.

## 2. 해시맵의 해시 함수와 충돌 해결 방식(체이닝) 설명

**아주 쉬운 설명**: 해시맵은 "문자열 키를 숫자로 바꾼 뒤, 그 숫자를 서랍
번호처럼 써서 값을 빠르게 찾는" 자료구조입니다. `hashmap.py`의 해시 함수는
이렇게 생겼습니다.

```python
@staticmethod
def _hash_string(key: str) -> int:
    h = 0
    for ch in key:
        h = (h * 31 + ord(ch)) & 0xFFFFFFFF
    return h

def _bucket_index(self, key: str) -> int:
    return self._hash_string(key) % self._capacity
```

각 글자를 `ord()`로 숫자(유니코드 코드포인트)로 바꾼 뒤, 이전까지 누적한
값에 31을 곱하고 더합니다. 31을 곱하는 이유는 Java의 `String.hashCode()`도
쓰는 관례적인 방식으로, 홀수이면서 계산이 가볍고 문자 위치에 따라 값이
크게 벌어지도록 만들어 충돌을 줄여주기 때문입니다("ab"와 "ba"는 이 방식으로
서로 다른 해시값이 나옵니다). 마지막에 버킷 개수로 나눈 나머지가 실제
저장할 "서랍 번호(인덱스)"입니다.

**충돌 해결(체이닝)**: 서랍 개수는 유한한데 키는 무한히 늘어날 수 있으니,
서로 다른 두 키가 같은 서랍 번호로 계산되는 "충돌"이 반드시 생깁니다. 이때
그 서랍 안에 리스트를 두고 여러 개를 매달아 두는 방식이 체이닝입니다.

```python
def _find_node(self, key: str):
    idx = self._bucket_index(key)
    chain = self._buckets[idx]          # 그 서랍에 있는 이중 연결 리스트
    if chain is None:
        return idx, None
    node = chain.head
    while node is not None:             # 서랍 안을 순회하며 key 비교
        if node.data.key == key:
            return idx, node
        node = node.next
    return idx, None
```

체이닝에 새 리스트 클래스를 또 만들지 않고 `linked_list.py`의
`DoublyLinkedList`를 그대로 재사용했습니다. 과제 명세도 "권장: 이중 연결
리스트 재사용"이라고 안내하고 있어서, 자료구조 하나를 두 군데(체이닝 + LRU)에
재사용하는 설계를 택했습니다.

**로드 팩터와 확장**: 서랍 하나에 몰리는 키가 많아지면(체인이 길어지면)
평균 O(1)이던 조회가 O(n)에 가까워집니다. 그래서 `(저장된 키 수) / (서랍 수)`가
0.75를 넘으면 서랍 수를 2배로 늘리고 모든 키를 다시 해싱합니다(`_resize`).
버킷 개수가 바뀌면 `해시값 % 버킷수` 결과도 전부 바뀌기 때문에 단순히 배열만
늘리는 게 아니라 반드시 재해싱이 필요합니다.

**실제 확인**: `제출/results/08_해시맵_확장_대량삽입.txt`에서 초기 용량 8인
상태로 20개의 키를 연속으로 넣으면(8→16→32로 최소 두 번 확장) `DBSIZE`가
정확히 20이고 첫 번째(`key0`)/마지막(`key19`) 키 모두 정상 조회되어, 확장
과정에서 데이터가 유실되지 않음을 확인했습니다.

## 3. 이중 연결 리스트 + 해시맵으로 O(1) LRU 추적이 가능한 이유 설명

`store.py`는 LRU 추적을 위해 두 자료구조를 함께 씁니다.

```python
self._lru_list = DoublyLinkedList()   # 사용 순서: head=최근 사용, tail=오래됨
self._lru_nodes = HashMap()           # key -> 그 key가 위치한 Node 객체
```

**아주 쉬운 설명**: "언제 마지막으로 썼는지" 순서를 유지하는 리스트가 하나
있고, "이 키가 리스트의 어느 자리에 있는지"를 즉시 알려주는 주소록(해시맵)이
하나 더 있는 구조입니다.

```python
def _touch_lru(self, key: str) -> None:
    if self._lru_nodes.contains(key):
        node = self._lru_nodes.get(key)      # 해시맵으로 O(1) 위치 조회
        self._lru_list.move_to_front(node)    # 이미 아는 노드라 O(1) 이동
    else:
        node = self._lru_list.insert_front(key)
        self._lru_nodes.put(key, node)
```

만약 해시맵(`_lru_nodes`) 없이 리스트만 있었다면, "user:5를 방금 썼다"는
사실을 반영하려고 해도 리스트 안에서 `user:5` 노드를 처음부터 찾아야 해서
O(n)이 걸립니다. 해시맵이 key → Node 참조를 바로 돌려주기 때문에, 찾는 과정
없이 곧바로 `move_to_front(node)`를 호출할 수 있고, `DoublyLinkedList`는
이웃 노드의 포인터만 갈아 끼우면 되므로(`linked_list.py`의 `move_to_front`
참고) 결과적으로 "찾기 + 옮기기" 전체가 O(1)이 됩니다.

**말로 설명하는 예시**: "해시맵은 '어디 있는지'를 O(1)에 알려주는 역할만
하고, 실제 순서를 옮기는 건 연결 리스트가 O(1)에 처리합니다. 배열로 순서를
관리했다면 중간 요소를 앞으로 옮길 때 뒤 요소들을 한 칸씩 밀어야 해서
O(n)이었을 텐데, 연결 리스트는 포인터만 조작하면 되니까 순서에 상관없이
항상 O(1)입니다."

## 4. 힙이 TTL 만료 시간 관리에 적합한 이유 설명

```python
self._ttl_heap = MinHeap()   # (expire_at, key) 최소 힙
```

**아주 쉬운 설명**: TTL 관리가 반복해서 풀어야 하는 문제는 "지금까지 설정된
여러 만료 시각 중에서, 가장 먼저 만료되는 게 언제·누구인가?"입니다. 이 질문에
빠르게 답하려고 최소 힙을 씁니다.

- 정렬된 리스트를 썼다면: "가장 빠른 것"은 맨 앞이라 O(1)로 알 수 있지만,
  새 `EXPIRE`가 들어올 때마다 어디에 끼워 넣을지 찾고 뒤를 미느라 O(n).
- 힙을 쓰면: 완전 이진 트리 모양("부모가 항상 자식보다 작다")만 유지하면
  되므로, 삽입(`push`)도 트리 높이만큼인 O(log n), "가장 빠른 것 확인"은
  루트만 보면 되니 O(1)(`peek`), "가장 빠른 것 꺼내기"도 O(log n)입니다.

```python
def _purge_expired_from_heap(self) -> None:
    now = time.time()
    while self._ttl_heap.size() > 0:
        expire_at, key = self._ttl_heap.peek()
        if expire_at > now:
            break                      # 가장 빠른 것도 안 지났으면 끝
        self._ttl_heap.pop()
        entry = self._map.get(key, None)
        if entry is not None and entry.expire_at == expire_at:
            self._remove_key(key)      # 진짜 만료된 것만 실제 삭제
        # 아니면 '유령' 항목 -> 조용히 버림 (lazy deletion)
```

파이썬 튜플은 첫 번째 원소부터 비교하기 때문에, `(expire_at, key)`를 그대로
힙에 넣기만 해도 별도의 비교 함수 없이 `expire_at`이 작은 순서로 정렬됩니다.

**lazy deletion을 쓰는 이유**: 배열 기반 힙은 "중간에 있는 특정 원소 하나만
콕 집어 지우기"가 번거롭습니다(그 원소의 배열 위치를 추가로 추적해야 함).
그래서 `SET`으로 TTL이 사라지거나 `EXPIRE`로 새 시각이 다시 설정되면, 힙 안의
예전 항목은 그냥 놔두고(유령 항목), 나중에 그 항목이 힙 꼭대기까지 올라와
꺼내질 때 "지금 데이터의 `expire_at`과 정확히 일치하는가"만 확인해서
다르면 버립니다. 과제 명세에서도 "lazy deletion 전략 등은 구현 선택"이라고
이 방식을 명시적으로 허용합니다.

**실제 확인**: `제출/results/03_TTL_실제만료.txt`에서 `EXPIRE user:2 3` 이후
실제로 3.2초를 기다린 뒤 `GET user:2`가 `(nil)`, `TTL user:2`가 `(integer) -2`를
반환해 자동 만료가 정확히 동작함을 확인했습니다. `제출/results/06_TTL_엣지케이스.txt`에서는
`SET k v1` → `EXPIRE k 100` → `SET k v2`로 덮어썼을 때 `TTL k`가 다시 `-1`(TTL
없음)로 바뀌는 것도 확인했는데, 이게 바로 힙에 남은 예전 `(expire_at, k)`가
유령이 되어 나중에 조용히 버려지는 경우입니다.

## 5. 메모리 제한 환경에서 LRU로 제거하는 전체 흐름(used_memory 갱신 포함) 설명

`store.py`의 `set()`이 실행되는 순서를 그대로 따라가 보면 이렇습니다.

```python
def set(self, key: str, value: str) -> None:
    self._purge_expired_from_heap()          # ① 만료분 먼저 정리
    self._expire_if_needed(key)               # ② 이 키가 이미 만료돼 있었다면 삭제

    new_entry_size = _byte_len(key) + _byte_len(value)
    if self._maxmemory > 0 and new_entry_size > self._maxmemory:
        raise OOMError()                       # ③ 단일 엔트리 자체가 넘치면 즉시 실패

    existing = self._map.get(key, None)
    if existing is not None:
        self._used_memory -= _byte_len(key) + _byte_len(existing.value)  # ④ 덮어쓸 값 빼기

    self._map.put(key, _ValueEntry(value=value, expire_at=None))  # ⑤ 저장 (TTL 초기화)
    self._used_memory += new_entry_size        # ⑥ used_memory 갱신
    self._touch_lru(key)                       # ⑦ 방금 썼으니 LRU head로

    self._evict_lru_until_under_limit(just_set_key=key)  # ⑧ 초과분만큼 LRU 꼬리부터 제거
```

**아주 쉬운 설명**: "일단 자리 있는지부터 확인하고(③), 없으면 넣지도 않고
바로 포기합니다. 자리가 있으면 넣고(⑤⑥), 방금 쓴 걸 맨 앞으로 표시해두고(⑦),
그래도 전체 용량을 넘겼으면 가장 오래 방치된 것부터 하나씩 지웁니다(⑧)."

`used_memory`는 오직 `Σ(len(utf8(key)) + len(utf8(value)))`로만 계산합니다
(자료구조 오버헤드 제외). 그래서 새 값을 넣을 때는 더하고, 지울 때는 정확히
그 키+값의 byte 수만큼 뺍니다(`_remove_key` 참고). 이 더하기/빼기가 어긋나면
`used_memory`가 실제 저장량과 달라지므로, 저장·삭제·덮어쓰기·제거(eviction)
네 경로 모두 반드시 같은 `_byte_len` 계산과 `_remove_key`를 거치도록 통일했습니다.

**방금 넣은 키가 자기 자신 때문에 지워지지 않는 이유**: ⑦번에서 이미 LRU
`head`(가장 최근)로 옮겨졌기 때문에, ⑧번의 제거 대상인 `tail`(가장 오래됨)이
되려면 다른 모든 키가 먼저 지워져야 합니다. 그리고 ③번에서 이미 "이 키
하나만으로도 넘치는지"를 검증했기 때문에, 다른 키를 전부 지우고 나면 반드시
`used_memory ≤ maxmemory`가 되어 루프가 끝납니다(무한 루프 불가능).

**실제 확인**: `제출/results/02_메모리관리_LRU제거.txt`에서 `maxmemory=30`
설정 후 `user:1`(11B) → `user:2`(9B, 누적 20B) → `user:3`(13B, 누적 33B>30)
순으로 넣으면 가장 오래된 `user:1`이 자동 제거되고, 이후 `INFO memory`가
`used_memory:22`(=9+13), `evicted_keys:1`을 정확히 보여줍니다 — **과제 예시의
수치와 완전히 일치**합니다.

## 6. 발표 또는 평가 때 사용할 짧은 요약

> "dict/set/collections 없이 해시맵·이중 연결 리스트·최소 힙 세 자료구조를
> 직접 구현했습니다. 해시맵은 다항식 롤링 해시로 버킷을 정하고 충돌은 연결
> 리스트로 체이닝하며, 로드 팩터 0.75를 넘으면 2배로 확장·재해싱합니다.
> LRU는 '해시맵으로 위치를 O(1)에 찾고, 연결 리스트로 그 위치를 O(1)에
> 옮기는' 조합으로 구현했고, TTL은 '가장 빨리 만료되는 것'을 O(log n)에
> 찾을 수 있는 최소 힙과 지연 삭제(lazy deletion) 전략으로 구현했습니다.
> 메모리 제한을 넘기면 SET 직후 LRU 꼬리(가장 오래 방치된 키)부터 자동으로
> 제거하며 used_memory와 evicted_keys를 정확히 갱신합니다."

## 7. 평가 질문 대비 답변 자료 (`실제평가항목` 5개 문항 기준)

이 절은 `실제평가항목` 파일에 적힌 평가문항 순서(항목 1~5)를 그대로 따라
정리했습니다. 발표/평가 자리에서는 이 순서대로 넘어가면 됩니다.

### 항목 1. 기능 동작 확인 (직접 시연 + 근거 파일)

이 항목은 "설명"이 아니라 "실제로 동작하는지 보여주는" 항목이므로, 각
질문마다 그대로 재현 가능한 명령어와 `제출/results/`의 근거 로그를 짝지어
둡니다.

**① String 기본 동작 — SET/GET/DEL/EXISTS/DBSIZE/KEYS**

```
SET user:1 Alice   → OK
```

### 항목 2. 기본 자료구조 구현 설명

**Q1. 이중 연결 리스트의 노드가 `prev`/`next`/`data`로 구성되고, 핵심
메서드들이 어떻게 O(1)로 동작하는가?**

```python
class Node:
    __slots__ = ("prev", "next", "data")
    def __init__(self, data):
        self.prev = None
        self.next = None
        self.data = data
```

`data`는 실제 값(체이닝에서는 `(key, value)`, LRU에서는 `key`)을 들고
있고, `prev`/`next`는 좌우 이웃 노드에 대한 참조입니다. 핵심은 "노드를
이미 손에 쥐고 있으면" 어떤 연산이든 이웃 포인터 2~4개만 갈아 끼우면
끝난다는 점입니다.

- `insert_front`/`insert_back`: 새 노드를 만들어 `head`/`tail` 포인터
  주변만 연결 — 순회 없음, O(1).
- `remove_node(node)`: `node.prev.next = node.next`,
  `node.next.prev = node.prev`처럼 **이웃의 포인터만** 갱신 — 리스트를
  처음부터 훑어 위치를 찾지 않으므로 O(1) (배열이라면 삭제 뒤 뒤 요소를
  한 칸씩 당겨야 해서 O(n)).
- `move_to_front(node)`: 현재 위치에서 떼어낸 뒤(포인터 갱신) `head`
  앞에 다시 끼워 넣음 — 새 노드를 만들지 않고 **같은 Node 객체를
  재사용**하기 때문에, 해시맵이 들고 있던 그 노드에 대한 참조가 계속
  유효합니다. (`linked_list.py`의 `move_to_front` 참고.)

"위치를 찾는" 역할(O(n)이 될 수 있는 부분)은 이 클래스가 아니라 해시맵이
맡고, `DoublyLinkedList`는 "노드를 손에 쥔 다음부터"의 연산만 책임지도록
역할을 나눈 것이 O(1)의 핵심입니다.

**Q2. 직접 설계한 해시 함수가 어떤 입력을 받아 어떤 과정을 거쳐 인덱스를
만드는가?**

```python
def _hash_string(key: str) -> int:
    h = 0
    for ch in key:
        h = (h * 31 + ord(ch)) & 0xFFFFFFFF
    return h

def _bucket_index(self, key: str) -> int:
    return self._hash_string(key) % self._capacity
```

문자열 키를 한 글자씩 `ord()`로 유니코드 코드포인트(정수)로 바꾼 뒤,
누적값에 31을 곱하고 더하는 다항식 롤링 해시입니다. 31을 곱하는 이유는
Java `String.hashCode()`와 같은 관례로, 홀수·소수라 배수 관계로 인한
충돌이 덜 생기고 `31*i == (i<<5) - i`처럼 시프트/뺄셈만으로 계산할 수
있어 가볍기 때문입니다. `& 0xFFFFFFFF`로 32비트 범위로 오버플로를
정리한 뒤, 마지막에 `% capacity`로 버킷 배열 범위 안의 인덱스로 접습니다.

**Q3. 충돌 해결을 체이닝으로 어떻게 구현했으며, 버킷 내부 구조는 어떻게
선택했는가?**

버킷 개수는 유한한데 키는 무한히 늘어날 수 있어 서로 다른 두 키가 같은
인덱스로 계산되는 "충돌"이 반드시 생깁니다. 각 버킷에 리스트를 두고
같은 인덱스로 몰린 키들을 매달아 두는 방식이 체이닝입니다.

```python
def _find_node(self, key: str):
    idx = self._bucket_index(key)
    chain = self._buckets[idx]
    if chain is None:
        return idx, None
    node = chain.head
    while node is not None:
        if node.data.key == key:
            return idx, node
        node = node.next
    return idx, None
```

버킷 내부 구조로는 파이썬 리스트가 아니라 `linked_list.py`의
`DoublyLinkedList`를 그대로 재사용했습니다. 과제 명세도 "권장: 이중
연결 리스트 재사용"을 안내하고 있고, 삽입(`insert_front`)과 삭제
(`remove_node`)가 O(1)이라 체이닝 자료구조로 적합하며, 자료구조 하나를
체이닝과 LRU 두 군데에 재사용하는 설계이기도 합니다.

**Q4. 로드 팩터가 0.75를 초과하면 "버킷 2배 확장"을 어떤 절차로
수행하는가?**

```python
if self._size / self._capacity > 0.75:
    self._resize(self._capacity * 2)

def _resize(self, new_capacity: int) -> None:
    old_buckets = self._buckets
    self._capacity = new_capacity
    self._buckets = [None] * new_capacity
    self._size = 0
    for chain in old_buckets:
        ...  # 각 체인의 모든 (key, value)를 새 버킷에 다시 put
```

절차는 ① `(저장된 키 수) / (버킷 수)`를 매 `put` 뒤 계산해 0.75 초과
여부 확인 → ② 새 용량(2배)의 빈 버킷 배열을 새로 할당 → ③ 기존 모든
버킷을 순회하며 체인에 담긴 `(key, value)`를 하나씩 꺼내 **새 용량 기준으로
다시 해시 인덱스를 계산해(rehash)** 새 버킷에 삽입 → ④ 기존 버킷 배열은
버립니다. 버킷 개수가 바뀌면 `해시값 % 버킷수` 결과도 모두 바뀌기 때문에
배열만 늘리는 것으로는 부족하고 반드시 전체 재해싱(O(n))이 필요합니다.
근거: `제출/results/08_해시맵_확장_대량삽입.txt`(초기 용량 8에서 20개
연속 삽입 → 8→16→32로 최소 두 번 확장되어도 `DBSIZE`가 정확히 20, 첫/마지막
키 모두 정상 조회됨을 확인).

### 항목 3. LRU, TTL, 메모리 관리 흐름 설명

**Q1. LRU 구현에서 "해시맵 + 이중 연결 리스트"가 각각 어떤 역할을 하며,
왜 둘 다 필요한가?**

```python
self._lru_list = DoublyLinkedList()   # 사용 순서: head=최근 사용, tail=오래됨
self._lru_nodes = HashMap()           # key -> 그 key가 위치한 Node 객체
```

연결 리스트는 "누가 가장 최근에 쓰였고 누가 가장 오래 방치됐는지" 순서를
유지하는 역할, 해시맵은 "이 키가 리스트의 어느 노드에 있는지"를 즉시
알려주는 역할입니다. 리스트만 있다면 특정 키의 노드를 찾으려면 처음부터
순회해야 해 O(n)이고, 해시맵만 있다면애초에 "가장 오래된 키"라는 순서
개념을 표현할 수 없습니다. 즉 "빠른 위치 조회"와 "순서 유지"라는 서로
다른 두 가지 필요를 각각 다른 자료구조가 나눠 맡고, 둘을 같은 Node
객체로 연결해서 함께 써야 O(1)이 완성됩니다.

**Q2. "조회는 해시맵으로, 사용 기록 갱신은 리스트 이동으로 처리한다"는
관점에서 O(1) LRU 달성 원리를 설명하면?**

```python
def _touch_lru(self, key: str) -> None:
    if self._lru_nodes.contains(key):
        node = self._lru_nodes.get(key)      # ① 해시맵으로 O(1) 위치 조회
        self._lru_list.move_to_front(node)    # ② 이미 아는 노드라 O(1) 이동
    else:
        node = self._lru_list.insert_front(key)
        self._lru_nodes.put(key, node)
```

①번이 "조회" 단계로, 리스트를 순회하지 않고 해시맵이 key→Node 참조를
바로 돌려줍니다. ②번이 "갱신" 단계로, 이미 Node 참조를 손에 쥐고
있으므로 `move_to_front`는 이웃 포인터만 갈아 끼우면 됩니다(순회 없음).
배열로 순서를 관리했다면 중간 요소를 앞으로 옮길 때 뒤 요소들을 한 칸씩
밀어야 해 O(n)이었을 부분이, "해시맵으로 찾고 + 연결 리스트로 옮기고"의
조합 덕분에 전체가 O(1)이 됩니다.

**Q3. TTL 관리에 힙을 사용한 이유는? 힙이 가장 빠른 만료 시간을 빠르게
찾는 성질을 갖는다는 점을 포함해서 설명하면?**

```python
self._ttl_heap = MinHeap()   # (expire_at, key) 최소 힙
```

TTL 관리가 반복해서 답해야 하는 질문은 "지금까지 설정된 만료 시각 중
가장 먼저 만료되는 게 언제·누구인가?"입니다. 최소 힙은 "부모가 항상
자식보다 작다"는 성질만 유지하는 완전 이진 트리라서, 루트가 항상 전체
중 최솟값(=가장 빠른 만료 시각)입니다. 그래서 `peek()`(루트 확인)이
O(1), 삽입(`push`)과 최솟값 제거(`pop`)는 트리 높이만큼인 O(log n)입니다.
정렬된 리스트를 썼다면 "가장 빠른 것 확인"은 O(1)이어도 새 `EXPIRE`가
들어올 때마다 삽입 위치를 찾아 뒤를 미는 데 O(n)이 걸렸을 것입니다.
파이썬 튜플은 첫 원소부터 비교하므로 `(expire_at, key)`를 그대로 힙에
넣기만 해도 별도 비교 함수 없이 만료 시각 순으로 정렬됩니다.

**Q4. 메모리 초과 시 eviction 흐름을 `used_memory` 산정·갱신, LRU 제거,
`evicted_keys` 증가까지 포함해 단계별로 설명하면?**

`store.py`의 `set()` 실행 순서를 그대로 따라가면:

```python
def set(self, key, value):
    self._purge_expired_from_heap()          # ① 만료분 먼저 정리
    self._expire_if_needed(key)               # ② 이 키가 이미 만료돼 있었다면 삭제

    new_entry_size = _byte_len(key) + _byte_len(value)
    if self._maxmemory > 0 and new_entry_size > self._maxmemory:
        raise OOMError()                       # ③ 단일 엔트리 자체가 넘치면 즉시 실패

    existing = self._map.get(key, None)
    if existing is not None:
        self._used_memory -= _byte_len(key) + _byte_len(existing.value)  # ④ 덮어쓸 값 빼기

    self._map.put(key, _ValueEntry(value=value, expire_at=None))  # ⑤ 저장
    self._used_memory += new_entry_size        # ⑥ used_memory 갱신
    self._touch_lru(key)                       # ⑦ 방금 썼으니 LRU head로

    self._evict_lru_until_under_limit(just_set_key=key)  # ⑧ 초과분만큼 LRU 꼬리부터 제거
```

⑧번 내부는 `while used_memory > maxmemory: tail 키를 골라 _remove_key로
삭제 → used_memory에서 그 키+값 byte 수만큼 빼고 → evicted_keys += 1`을
반복합니다. `used_memory`는 오직 `Σ(len(utf8(key)) + len(utf8(value)))`로만
계산하며(자료구조 오버헤드 제외), 저장(⑥)·삭제·덮어쓰기(④)·제거(⑧)
네 경로 모두 같은 `_byte_len` 계산을 거치도록 통일해 값이 어긋나지
않게 했습니다. ⑦에서 방금 쓴 키가 이미 LRU head로 옮겨졌기 때문에, ⑧의
제거 대상(tail)이 되려면 다른 모든 키가 먼저 지워져야 하고, ③에서 이미
"이 키 하나만으로도 넘치는지"를 검증했으므로 루프는 반드시 종료됩니다
(무한 루프 불가능). 근거: `제출/results/02_메모리관리_LRU제거.txt`에서
`used_memory:22`, `evicted_keys:1`이 과제 예시와 정확히 일치.

**Q5. GET 명령어의 전체 흐름을 TTL 확인 → 만료 판단 → 만료 키 삭제 →
값 반환 → LRU 갱신 조건 순서로 설명하면?**

```python
def get(self, key: str):
    self._purge_expired_from_heap()      # ① 힙에 쌓인 만료분을 먼저 정리
    if self._expire_if_needed(key):       # ② 이 key 자체가 만료돼 있었는지 확인
        return None                        #    만료였다면 삭제 후 즉시 (nil)
    entry = self._map.get(key, None)
    if entry is None:
        return None                        # ③ 애초에 없던 key도 (nil)
    self._touch_lru(key)                   # ④ 값을 실제로 돌려줄 때만 LRU 갱신
    return entry.value                     # ⑤ 값 반환
```

①은 힙 전체 관점의 청소(다른 키들의 만료도 함께 정리), ②는 "이 key가
지금 만료 상태인가"를 개별 확인하는 단계로, TTL이 지났다면 그 자리에서
삭제하고 `None`을 반환합니다. ③에서 원래 없던 키도 동일하게 `None`을
반환합니다. LRU 갱신(④)은 "실제로 값을 성공적으로 돌려준 경우"에만
수행합니다 — 이미 사라진(만료된) 키를 조회한 것은 "방금 사용했다"고 볼
수 없기 때문에, ②·③에서 `None`을 반환하는 경로는 LRU를 건드리지
않습니다.

### 항목 4. 확장 사고 및 구조 개선 설명

**Q1. LRU 대신 LFU(Least Frequently Used) 정책을 구현한다면 자료구조를
어떻게 변경해야 하는가?**

현재 LRU는 "해시맵(key→Node) + 사용 순서 하나짜리 이중 연결 리스트"
조합입니다. LFU는 "가장 오래 안 썼는가"가 아니라 "가장 적게 썼는가"를
기준으로 제거해야 하므로, 순서 하나만으로는 표현이 안 되고 **키별 사용
빈도(count)**를 추적해야 합니다. O(1)을 유지하려면 보통 이렇게 확장합니다.

- `key → (Node, frequency)`를 알려주는 해시맵은 그대로 유지.
- 리스트를 하나가 아니라 **빈도별로 여러 개**(`frequency → 그 빈도를 가진
  key들의 이중 연결 리스트`) 두고, 이 매핑도 해시맵으로 관리합니다.
- 접근 시 해당 key를 현재 빈도의 리스트에서 O(1)로 떼어(`remove_node`)
  `frequency+1` 리스트 앞에 O(1)로 다시 끼워 넣고(`insert_front`),
  frequency 값을 갱신합니다.
- 가장 낮은 frequency 값(`min_freq`)을 변수로 별도 추적해두면, 제거할
  때 `min_freq`에 해당하는 리스트의 tail만 보면 됩니다. 만약 어떤 키를
  옮기면서 원래 있던 `min_freq` 리스트가 비게 되면 `min_freq += 1`.

즉 "해시맵으로 위치를 O(1)에 찾고 리스트로 O(1)에 옮긴다"는 LRU의 핵심
아이디어는 그대로 재사용하되, 순서 축이 하나(시간)에서 여러 개(빈도별
버킷)로 늘어나는 구조 확장이 필요합니다.

**Q2. 데이터가 10만 건으로 늘어나면 현재 구조에서 병목이 될 수 있는
부분은 어디이며, 어떻게 개선할 수 있는가?**

- **TTL 힙의 유령(lazy-deleted) 항목 누적**: 같은 키에 `EXPIRE`를 자주
  재설정하거나 `SET`으로 TTL을 지우는 패턴이 많으면, 힙에는 예전 항목이
  "유령"으로 계속 쌓입니다(항목 4의 lazy deletion 설명 참고). 실제 키
  수는 10만 개인데 힙 크기는 그보다 훨씬 커질 수 있어 `push`/`pop` 비용
  (O(log n))의 n이 부풀려집니다. 개선하려면 key→힙 인덱스 매핑을 추가로
  유지해 TTL이 재설정될 때 힙에서 해당 항목을 직접 O(log n)에 갱신/삭제
  하는 "인덱스형 힙"으로 바꿀 수 있습니다.
- **`KEYS` 명령의 전체 순회**: `DoublyLinkedList`를 순회해 모든 key를
  나열하므로 10만 건이면 그 자체로 O(n) 응답입니다. 이는 "모든 키를
  보여준다"는 기능의 본질상 피할 수 없지만, 실무에서는 `SCAN`처럼 커서
  기반으로 나눠서 반환하는 방식으로 한 번의 응답 지연을 줄입니다.
- **해시맵 리사이즈 비용**: 로드 팩터 0.75를 넘을 때마다 O(n) 재해싱이
  발생합니다. 10만 건까지 여러 번의 2배 확장(초기 용량 대비 약 15회
  전후)이 필요한데, 매 확장이 O(n)이라도 다음 확장까지 삽입 횟수도
  같이 늘어나므로 전체적으로는 상환(amortized) O(1)을 유지합니다 —
  다만 확장이 일어나는 그 순간만큼은 지연이 튈 수 있어(latency spike),
  초기 용량을 예상 데이터 규모에 맞게 크게 잡아 리사이즈 횟수 자체를
  줄이는 것이 실전에서는 더 유리합니다.
- **순수 파이썬 객체 오버헤드**: `Node`/`HashMap`/`MinHeap`이 모두 파이썬
  레벨 객체라 C로 구현된 내장 `dict`보다 상수 배 느립니다. 10만 건
  규모에서는 알고리즘 복잡도(O(1)/O(log n))보다 이 언어 자체 오버헤드가
  체감 성능에 더 크게 기여할 수 있습니다.

**Q3. `used_memory`에 자료구조 오버헤드까지 포함하는 모델로 바꾸면
무엇이 달라지고, 공정한 비교/채점을 위해 어떤 보정이 필요한가?**

지금은 `used_memory = Σ(len(utf8(key)) + len(utf8(value)))`만 계산해
"사용자가 넣은 데이터양"만 반영합니다. 여기에 `Node`, 해시맵 버킷 슬롯,
힙 배열 원소 같은 내부 오버헤드까지 더하면 같은 데이터를 넣어도
`used_memory`가 커지고, 같은 `maxmemory` 값에서 이전보다 훨씬 이른
시점에 LRU 제거·OOM이 발생하게 됩니다. 또한 오버헤드 크기는 파이썬
객체 헤더, 포인터 크기(32bit/64bit), 인터프리터 구현(CPython vs 다른
구현체)에 따라 달라지므로, 같은 코드라도 실행 환경에 따라 `used_memory`
수치 자체가 달라지는 문제가 생깁니다. 공정한 비교/채점을 위해서는
① "오버헤드를 어떤 상수로 볼 것인지"(예: 노드당 고정 N바이트로
단순화)를 사전에 명확히 정의해 문서화하고, ② 그 상수 계산식을
채점 기준에도 동일하게 반영하며, ③ 필요하면 `maxmemory` 값 자체도
오버헤드 포함 여부에 맞게 재조정해야 이전 버전과 결과를 비교할 수
있습니다. (현재 구현은 순수 데이터양만 보는 쪽을 택해, 환경에 관계없이
결정적이고 채점하기 쉬운 값을 유지하는 것을 우선했습니다.)

### 항목 5. 보너스

과제 "5. 보너스 과제(선택)"의 5가지(동적 배열 직접 구현 / 스택·큐·덱
문서화 / 이진 트리 순회 / BST / Pub-Sub)는 모두 선택 사항이라 **이번
제출에는 포함하지 않았습니다.** 필수 요구사항(String 10개 명령어, 3대
자료구조 직접 구현, 메모리 관리, TTL 관리, CLI, 에러 처리 표준)을 먼저
확실하게 완성하는 데 집중했습니다.

다만 힙(`heap.py`)의 내부 배열(`self._data = []`)과 해시맵의 버킷
테이블(`self._buckets = [None] * capacity`)은 이미 파이썬 `list`를
"고정 길이 배열"로만 제한적으로 쓰고 있어서, 보너스 1번(동적 배열 직접
구현)을 이어서 진행한다면 이 두 곳의 `list` 사용을 자체 구현한 동적
배열 클래스(예: 용량 초과 시 2배 확장하는 배열)로 교체하는 형태로
자연스럽게 확장할 수 있습니다.

## 부록. 그 밖에 나올 수 있는 질문

`실제평가항목`에 직접 명시되진 않았지만, 구현 과정에서 판단 근거가 필요했던
질문들입니다.

**A1. dict/set/collections를 정말 하나도 안 썼는가? 어떻게 확인했는가?**

`grep`으로 `mini_redis/*.py` 전체에서 `dict(`, `{...}` 리터럴, `set(`,
`frozenset(`, `collections` import를 검색해 실제 사용례가 없음을
확인했습니다(주석/문자열 언급과 `store.set(...)`처럼 이름이 우연히
겹치는 메서드 호출만 걸러졌습니다). 대신 파이썬 `list`는 "고정 길이
배열/인덱스 접근" 용도로만 제한적으로 사용했습니다 — 해시맵 버킷
테이블과 힙 내부 배열이 그 예로, 둘 다 과제 제약이 명시적으로 허용한
용도입니다.

**A2. shlex 모듈은 왜 써도 된다고 판단했는가?**

`shlex`는 문자열을 "따옴표를 인식해서 토큰으로 쪼개는" 파싱 유틸리티일
뿐, 키-값을 저장하거나 순서를 관리하는 자료구조가 아닙니다. 과제가
금지한 것은 "해시맵/캐시를 내장 컬렉션으로 대체하는 것"이므로, 배우고자
하는 자료구조(해시맵/연결 리스트/힙)와 무관한 문자열 토크나이징에 표준
라이브러리를 쓰는 것은 제약 취지에 어긋나지 않는다고 판단했습니다.

**A3. 네트워크/영속성/동시성을 구현하지 않은 이유는?**

과제의 "기능 범위" 제약사항에 "네트워크 통신은 구현하지 않는다(오직
CLI)", "데이터 영속성은 구현하지 않는다", "멀티스레딩/락 같은 동시성
처리는 요구하지 않는다"고 명시되어 있어 그대로 따랐습니다. 이 과제의
목표는 Redis를 흉내 낸 완제품이 아니라, 해시맵/연결 리스트/힙이라는
핵심 자료구조의 동작 원리를 직접 손으로 확인하는 것이기 때문입니다.

**A4. 각 자료구조가 올바르게 동작하는지 어떻게 검증했는가?**

REPL 통합 테스트 외에, `linked_list.py`/`hashmap.py`/`heap.py`를 직접
import해서 자료구조 단위로도 검증했습니다. 이중 연결 리스트는 6개
메서드를 순서대로 호출하며 매번 리스트 내용이 기대와 일치하는지,
해시맵은 작은 초기 용량(4)으로 시작해 30개를 넣어 여러 번 강제로
리사이즈시킨 뒤 전부 정상 조회되는지, 힙은 무작위 50개를 넣고 전부
꺼냈을 때 결과가 `sorted()`와 정확히 일치하는지 확인했습니다
(`제출/실행결과.md`의 "데이터 구조 자체 단위 검증" 참고).

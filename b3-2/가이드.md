## 1. 과제 개요

**만들어야 하는 것**: `sorted()`/`list.sort()` 없이 정렬 알고리즘을 직접
구현하고, 그래프 전용 라이브러리 없이 커밋 그래프 탐색(위상 정렬/최단
경로/조상)을 직접 구현해 만든 CLI 기반 Mini Git (Python 표준 라이브러리만 사용)

**완성 기준** (`mini_git/` 폴더 + `main.py`에 이미 구현되어 있음):
- [x] 저장소/브랜치 관리: INIT / BRANCH / SWITCH / COMMIT
- [x] LOG (위상 정렬 — 부모가 항상 자식보다 먼저)
- [x] LOG --sort-by=date|author (직접 구현한 병합 정렬)
- [x] PATH (무방향 최단 경로, 사전순 타이브레이크)
- [x] ANCESTORS (도달 가능한 모든 조상)
- [x] SEARCH <keyword> / SEARCH --author=<name> (역색인 기반)
- [x] `mini-git>` 프롬프트의 REPL CLI (exit/quit 종료, 명령어 대소문자 무관)
- [x] 커밋 그래프(DAG) + hash 기반 해시맵 저장소, 세션 내 유일한 hash
- [x] 역색인 2종(keyword→hash 목록, author→hash 목록)
- [x] 표준 에러(Invalid args / Unknown branch / Unknown commit)

**폴더 구조**:
```
b3-2/
├── 가이드.md                  ← 지금 보고 있는 이 문서
├── 과제                        ← 원본 과제 요구사항 (참고용, 수정 X)
├── 평가질문_설명자료.md         ← 평가 질문 대비 설명 자료
├── main.py                     ← 엔트리 포인트 (필수 제출물 1)
├── README.md                   ← 실행 방법, 명령어 목록 (필수 제출물 2)
├── mini_git/                   ← 실제 구현체
│   ├── cli.py                    REPL, 명령어 파싱, 출력 포맷팅
│   ├── repository.py             저장소 상태(브랜치/HEAD/사용자) 관리
│   ├── commit.py                 Commit 노드 + 세션 내 유일한 hash 생성
│   ├── traversal.py              위상 정렬 / 최단 경로 / 조상 탐색
│   ├── sorting.py                 직접 구현한 병합 정렬

    ├── 실행결과.md               ← 실행 결과 요약
```

## 2. 개발 환경 준비

이 과제는 **Python 3.10 이상**을 권장하지만, f-string이나 타입 힌트 문법에
크게 의존하지 않게 작성해 Python 3.8 이상에서도 동작합니다.

## 3. 실행해보기

**항상 `b3-2` 폴더에서 실행해야 합니다.**

```bash
cd b3-2
python main.py
```

`mini-git> ` 프롬프트가 뜨면 아래를 순서대로 입력해봅니다.

### 3-1. 저장소 초기화와 첫 커밋

```
mini-git> init "Alice"
Initialized repository.
Current branch: main
Current user: Alice
mini-git> commit "Initial commit"
[main a1b2c3] Initial commit
```

(실제 hash는 매번 다르게 생성됩니다. 이후 예시에서는 편의상 과제 예시의
`a1b2c3` 같은 표기를 그대로 사용하지만, 직접 실행하면 실제 값으로 나타납니다.)

### 3-2. 브랜치 생성/전환 후 커밋 분기

```
mini-git> branch feature
Created branch: feature
mini-git> switch feature
Switched to branch: feature
mini-git> commit "Add login feature"
[feature d4e5f6] Add login feature
mini-git> switch main
Switched to branch: main
mini-git> commit "Add payment feature"
[main g7h8i9] Add payment feature
```

### 3-3. LOG (위상 정렬)

```
mini-git> log
commit a1b2c3 (Alice, ...) [main]
Initial commit
commit d4e5f6 (Alice, ...) [feature]
Add login feature
commit g7h8i9 (Alice, ...) [main]
Add payment feature
```

부모(Initial commit)가 항상 자식들보다 먼저 나오는지 확인합니다.

### 3-4. PATH / ANCESTORS (화면에 실제로 출력된 hash를 그대로 복사해 사용)

```
mini-git> path <Initial의 hash> <Add payment feature의 hash>
Path: a1b2c3 -> g7h8i9
mini-git> ancestors <Add payment feature의 hash>
Ancestors of g7h8i9:
- a1b2c3
```

### 3-5. SEARCH

```
mini-git> search login
Found 1 commit:

- d4e5f6: Add login feature

mini-git> search --author=Alice
Found 3 commits:
...
```

### 3-6. LOG --sort-by

```
mini-git> log --sort-by=date
mini-git> log --sort-by=author
```

### 3-7. 종료

```
mini-git> exit
```

(`quit`도 동일하게 동작합니다.)

## 4. 코드 구조 한눈에 보기

| 파일 | 역할 | 한 줄 설명 |
|---|---|---|
| `main.py` | 진입점 | `python main.py`로 실행하면 가장 먼저 호출됨 |
| `mini_git/cli.py` | 입출력 담당 | 사용자 입력 파싱 + 출력 포맷팅 (저장 로직은 모름) |
| `mini_git/repository.py` | 상태 담당 | 브랜치/HEAD/사용자 관리, 각 명령의 진입점 |
| `mini_git/commit.py` | 자료구조 | Commit 노드 정의 + 유일한 hash 생성 |
| `mini_git/traversal.py` | 알고리즘 | 위상 정렬(LOG) / 최단 경로(PATH) / 조상(ANCESTORS) |
| `mini_git/sorting.py` | 알고리즘 | 직접 구현한 병합 정렬 (LOG --sort-by) |
| `mini_git/index.py` | 자료구조 | 역색인 (SEARCH) |
| `mini_git/errors.py` | 오류 타입 | 표준 에러 메시지를 표현하는 예외 클래스들 |

**의존 관계**: `main.py` → `cli.py` → `repository.py` → (`commit.py`,
`traversal.py`, `sorting.py`, `index.py`). 탐색/정렬/인덱싱 세 알고리즘
모듈은 서로 독립적이며 Repository의 상태를 몰라도 단독으로 테스트할 수
있다 — "알고리즘 로직은 독립된 함수 또는 클래스로 분리한다"는 제약을
그대로 따른 구조다.

## 5. 핵심 개념 쉽게 이해하기

### 커밋 그래프가 DAG인 이유

각 커밋은 자신의 "부모" 커밋(들)을 가리킬 뿐, 절대 미래의 커밋(아직 존재하지
않는 자식)을 가리킬 수 없습니다. 시간은 한 방향으로만 흐르기 때문에 커밋
A가 B의 부모이면 B가 A의 부모가 되는 것은 논리적으로 불가능합니다 —
즉 간선이 "사이클을 이룰 수 없다." 방향(부모 참조)이 있으면서 사이클이
없는 그래프, 그것이 정확히 DAG(Directed Acyclic Graph)입니다. 병합 커밋처럼
부모가 2개가 되어도(여러 브랜치가 합쳐져도) 이 성질은 깨지지 않습니다.

### "부모가 먼저 출력되는 로그" = 위상 정렬

`traversal.topological_order`는 Kahn의 알고리즘(진입차수 기반 BFS)을 쓴다.

```python
in_degree = {h: len(c.parents) for h, c in commits.items()}
queue = [h for h in commits if in_degree[h] == 0]   # 부모 없는 커밋부터
while queue has items:
    현재 커밋을 결과에 추가
    현재 커밋을 부모로 둔 자식들의 in_degree를 1씩 감소
    in_degree가 0이 된 자식을 큐에 추가
```

**비유**: "선수과목을 다 들어야 다음 과목을 들을 수 있는" 커리큘럼을 짜는
것과 같습니다. 선수과목이 없는 과목부터 듣고, 한 과목을 들을 때마다 그
과목을 선수과목으로 하는 다른 과목들의 "남은 선수과목 수"를 하나씩
지워나가다 0이 되면 그 과목도 들을 수 있게 되는 방식입니다. DAG는
사이클이 없으므로 이 과정이 반드시 모든 노드를 방문하고 끝납니다.

### 두 커밋 사이의 최단 경로 / 모든 조상 탐색

- **ANCESTORS**: `commit.parents`를 계속 따라 올라가는 BFS입니다. 조상은
  "자식→부모" 방향의 간선만 따라가면 되므로 일반적인 방향 그래프 BFS와
  같습니다. 병합 커밋 때문에 같은 조상에 여러 경로로 도달할 수 있어
  `visited` 집합으로 중복 방문을 막습니다.
- **PATH**: 과제 명세가 "부모-자식 연결을 무방향 간선으로 간주"하라고
  명시했기 때문에, 커밋마다 부모 쪽으로도 자식 쪽으로도 이동할 수 있는
  별도의 무방향 그래프를 만들어 BFS로 최단 거리를 구합니다. 여러 개의
  최단 경로가 있을 수 있어서(예: 같은 부모에서 갈라진 두 브랜치의 끝
  커밋 사이), "사전순으로 가장 작은 경로"를 고르기 위해 시작점과 끝점
  양쪽에서 BFS 거리를 미리 구해두고, 매 걸음마다 "최단 경로 위에 있는
  다음 후보들" 중 hash가 가장 작은 것을 탐욕적으로 선택합니다(자세한
  코드는 `traversal.shortest_path`의 docstring 참고).

### 정렬 알고리즘 직접 구현 (병합 정렬) — 시간복잡도와 안정성

`sorting.merge_sort`는 리스트를 절반으로 계속 나누다가(분할), 크기 1이 되면
그 자체로 정렬된 것으로 보고, 두 정렬된 절반을 다시 하나로 합치는(병합)
과정을 반복합니다.

- **시간복잡도**: 분할은 항상 정확히 반씩 일어나므로 트리의 깊이가
  `log n`이고, 각 깊이에서 병합에 드는 전체 시간이 `n`이라 총
  `O(n log n)`입니다. 입력이 이미 정렬돼 있든 거꾸로 정렬돼 있든 분할
  방식 자체가 바뀌지 않으므로 **평균과 최악이 모두 O(n log n)**으로
  동일합니다(퀵 정렬은 최악의 경우 O(n²)까지 나빠질 수 있는 것과 대조적).
- **안정 정렬**: 병합 단계에서 두 값이 같을 때 `<=`를 써서 항상 왼쪽(원래
  앞에 있던) 값을 먼저 채택합니다. 그래서 정렬 기준(예: author)이 같은
  원소들끼리는 정렬 전의 상대적 순서가 그대로 유지됩니다. `LOG
  --sort-by=author`에서 같은 작성자의 커밋들이 원래(위상 정렬) 순서를
  유지한 채 묶이는 이유가 이것입니다.

### 역색인이 순회 검색보다 빠른 이유

`index.py`의 `InvertedIndex`는 "단어 → 그 단어가 들어간 커밋들"이라는
표를 커밋이 생성될 때마다(COMMIT 시점) 미리 만들어 둡니다.

- 역색인이 없다면: `SEARCH login`을 처리하려고 커밋 N개를 전부 훑으며
  메시지 안에 "login"이 있는지 검사해야 합니다 → **O(N)**.
- 역색인이 있으면: `keyword_index["login"]`처럼 딕셔너리에서 그 단어의
  커밋 목록을 바로 꺼내기만 하면 됩니다 → 평균 **O(1)** (+ 결과 개수만큼
  복사하는 O(k)).

커밋 수가 많아질수록 이 차이는 커집니다. 대신 "커밋이 생성될 때 미리
색인해두는" 비용(O(메시지 길이))을 매번 지불하는 트레이드오프입니다 —
"자주 검색되고 가끔 쓰이는" 데이터에 유리한 전형적인 설계입니다.

### 6-1. 보너스 과제 진행 여부

과제 "5. 보너스 과제(선택)" 3가지(Diff / Merge 브랜치 병합 / 정렬 알고리즘
성능 비교)는 **모두 선택 사항이라 이번 제출에는 포함하지 않았습니다.** 필수
요구사항(저장소·브랜치 관리, LOG/PATH/ANCESTORS/SEARCH, 정렬·역색인 직접
구현, 에러 처리 표준, CLI)을 우선 확실하게 완성하는 데 집중했습니다.

다만 `Commit` 클래스는 이미 `parents`를 리스트로 다루고 있고 `traversal.py`의
위상 정렬/최단 경로/조상 탐색 함수 모두 부모가 2개 이상(병합 커밋)이어도
그대로 동작하도록 일반적으로 작성해 두었습니다(단위 테스트에서 다이아몬드형
그래프로 이미 검증). 따라서 보너스 2번(Merge)을 이어서 구현한다면
`repository.py`에 "현재 브랜치 HEAD와 대상 브랜치 HEAD를 부모로 하는 새
커밋을 만드는" `merge()` 메서드 하나만 추가하면 되고, 탐색/정렬 알고리즘은
수정할 필요가 없는 구조입니다.

## 7. 자주 발생하는 문제 해결

### `ModuleNotFoundError: No module named 'mini_git'`
- `b3-2` 폴더 **안에서** 실행하고 있는지 확인하세요. `cd b3-2` 후
  `python main.py`로 실행합니다.

### `PATH`/`ANCESTORS`에 `Unknown commit: ...`이 뜸
- 커밋 hash는 실행마다 새로 생성됩니다. 반드시 방금 `LOG`나 `COMMIT` 결과
  화면에 실제로 찍힌 hash를 복사해서 사용하세요.

### `LOG --sort-by=author`를 했는데 순서가 안 바뀜
- 정상입니다. 이 프로그램은 세션당 사용자가 하나(`INIT`에서 설정한 이름)뿐이라,
  모든 커밋의 author가 동일하면 정렬 기준으로 구분이 안 되고 안정 정렬 규칙에
  따라 원래 순서가 그대로 유지됩니다. 여러 작성자를 다루는 상황은
  `가이드.md`의 단위 테스트(§7 대응 자료)로 별도 검증했습니다.

### 프로그램을 다시 실행했더니 이전 커밋이 사라짐
- 정상입니다. 과제 제약사항에 "데이터 영속성은 구현하지 않아도 된다(메모리
  상 동작으로 충분)"고 명시되어 있어, 세션(프로세스) 안에서만 상태를
  유지하도록 설계했습니다.

### `INIT`을 다시 실행하면 어떻게 되나요?
- 저장소 전체(커밋, 브랜치, 역색인)가 초기화되고 새 사용자로 다시
  시작합니다. 이전 커밋들은 모두 사라집니다(의도된 동작입니다).

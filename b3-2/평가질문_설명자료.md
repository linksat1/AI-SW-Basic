## 1. 과제 결과물 한 줄 설명

이번 과제는 **그래프 전용 라이브러리와 `sorted()`/`list.sort()` 없이, 커밋
그래프 탐색(위상 정렬·최단 경로·조상)과 정렬 알고리즘을 직접 구현해 만든

```

```

INIT/BRANCH/SWITCH/COMMIT(저장소·브랜치 관리) + LOG/LOG --sort-by(로그) +

## 2. 커밋 그래프를 구현하고, Git의 커밋 구조가 왜 DAG인지 설명

**아주 쉬운 설명**: 커밋 하나는 `commit.py`의 `Commit` 클래스로 표현됩니다.

```python
class Commit:
    def __init__(self, commit_hash, message, author, timestamp, parents, branch):
        self.hash = commit_hash
        self.message = message
        self.author = author
        self.timestamp = timestamp
        self.parents = list(parents)  # 0개, 1개, 또는 2개(병합) 부모 hash
        self.branch = branch
```

각 커밋은 `parents`로 "자신보다 먼저 존재했던" 커밋(들)만 가리킵니다.
이 참조들을 전부 모으면, 커밋을 노드로 하고 "자식 → 부모" 참조를 간선으로
하는 그래프가 만들어집니다.

**왜 방향성(Directed)인가**: `parents` 참조는 항상 "과거"만 가리킵니다.
커밋 B가 커밋 A를 부모로 가진다는 것은 "B가 A보다 나중에 만들어졌다"는
뜻이고, 이 관계는 절대 뒤집힐 수 없습니다(A가 B의 부모이면서 동시에 B가
A의 부모일 수 없음). 그래서 간선에 방향이 있습니다.

**왜 비순환(Acyclic)인가**: 순환이 있으려면 "A → B → C → A"처럼 자기
자신에게 돌아오는 경로가 있어야 하는데, 이는 "A가 자기 자신보다 나중에
만들어졌다"는 모순을 뜻합니다. `COMMIT` 명령이 항상 "현재 시점의 HEAD를
부모로 하는 새 커밋"만 만들 수 있게 되어 있어서(`repository.commit()`),
구조적으로 이미 존재하는 커밋을 미래의 부모로 되돌릴 방법이 없습니다.

방향이 있으면서 사이클이 없는 그래프 = **DAG(Directed Acyclic Graph)**이고,
병합 커밋으로 부모가 2개가 되어도(브랜치 두 개가 합쳐져도) 이 두 성질은
그대로 유지됩니다.

## 3. "부모가 먼저 출력되는 로그"를 위한 접근(위상 정렬 성격의 출력) 설명

`traversal.topological_order`는 **Kahn의 알고리즘**(진입차수 기반 BFS)을 씁니다.

```python
in_degree = {h: len(c.parents) for h, c in commits.items()}
children = {h: [] for h in commits}
for h, c in commits.items():
    for p in c.parents:
        children[p].append(h)

queue = [h for h in commits if in_degree[h] == 0]  # 부모 없는 커밋부터 시작
result = []
while queue:
    current = queue.pop(0)
    result.append(current)
    for child in children[current]:
        in_degree[child] -= 1
        if in_degree[child] == 0:
            queue.append(child)
```

**아주 쉬운 설명**: "진입차수"는 "이 커밋을 출력하기 전에 먼저 출력돼야
하는 다른 커밋이 몇 개 남았는가"입니다(= 아직 안 나온 부모의 수). 부모가
0개인 커밋(뿌리)부터 출력 후보에 넣고, 하나를 출력할 때마다 그 커밋을
부모로 둔 자식들의 "남은 부모 수"를 하나씩 지웁니다. 0이 되는 순간
그 자식도 이제 출력해도 되는 상태가 되어 후보에 추가됩니다. 이 과정을
반복하면 "부모가 항상 자식보다 먼저 나오는" 순서가 자연스럽게 만들어집니다.

**단순 정렬로는 안 되는 이유**: "최신순"이라면 timestamp로 정렬하면
그만이지만, "부모가 먼저"라는 조건은 timestamp 하나만으로는 보장되지
않습니다(이론적으로 시계가 부정확하거나 동시각에 커밋되면 꼬일 수 있음).
반면 위상 정렬은 애초에 그래프의 부모-자식 "관계"만 보고 순서를
결정하므로, 시각 정보와 무관하게 항상 정확합니다.

**실제 확인**: `제출/results/02_LOG_위상정렬.txt`에서 뿌리 커밋(Initial
commit)이 항상 맨 위에 오고, 그 뒤로 두 브랜치(feature/main)에서 갈라진
자식 커밋들이 나오는 것을 확인했습니다. 단위 테스트에서는 병합 커밋까지
있는 다이아몬드형 그래프로 "부모가 항상 자식보다 앞선 위치"라는 성질을
모든 간선에 대해 검증했습니다(`제출/실행결과.md` §7).

## 4. 두 커밋 사이의 최단 경로 / 특정 커밋의 모든 조상 탐색 방법 설명

### ANCESTORS: 부모 방향 BFS

```python
def ancestors(commits, commit_hash):
    visited = set()
    queue = list(commits[commit_hash].parents)
    result = []
    while queue:
        h = queue.pop(0)
        if h in visited:
            continue
        visited.add(h)
        result.append(h)
        queue.extend(commits[h].parents)
    return result
```

**아주 쉬운 설명**: "부모의 부모의 부모..."를 계속 따라 올라가는 탐색입니다.
부모 목록에서 하나씩 꺼내 방문 처리하고, 그 커밋의 부모도 다시 큐에
넣는 식으로 반복합니다. 병합 커밋 때문에 같은 조상에 여러 경로로 도달할
수 있어(예: 다이아몬드형 구조), `visited` 집합으로 이미 본 커밋은
건너뛰어 중복과 무한 루프를 막습니다.

### PATH: 무방향 BFS + 사전순 타이브레이크

과제 명세는 "커밋-부모 연결을 무방향 간선으로 간주"하라고 명시합니다.
즉 부모 방향만이 아니라 자식 방향으로도 이동할 수 있는 별도 그래프를
만들어야 합니다.

```python
def _undirected_adjacency(commits):
    adjacency = {h: [] for h in commits}
    for h, c in commits.items():
        for p in c.parents:
            adjacency[h].append(p)
            adjacency[p].append(h)   # 양방향 간선
    return adjacency
```

최단 거리 자체는 이 무방향 그래프에서 BFS 한 번(O(V+E))이면 구해집니다.
문제는 "최단 경로가 여러 개일 때 사전순으로 가장 작은 것"을 골라야
한다는 점입니다. 이를 위해 시작점(`start_hash`)과 끝점(`end_hash`) **양쪽에서**
각각 BFS 거리를 구해둔 뒤, 시작점부터 한 걸음씩 전진하면서 "이 지점까지의
최단 거리 + 여기서 목적지까지 남은 최단 거리 = 전체 최단 거리"를 만족하는
이웃들(=반드시 어떤 최단 경로 위에 있는 이웃) 중 hash 문자열이 가장 작은
것을 매번 고릅니다.

```python
while current != end_hash:
    best_next = None
    for neighbor in adjacency[current]:
        on_shortest_path = (
            dist_from_start.get(neighbor) == dist_from_start[current] + 1
            and dist_from_end.get(neighbor) == dist_from_end[current] - 1
        )
        if on_shortest_path and (best_next is None or neighbor < best_next):
            best_next = neighbor
    current = best_next
    path.append(current)
```

**왜 이 방법이 맞는가**: 경로를 문자열로 이어붙였을 때 "사전순으로 가장
작다"는 것은, 첫 글자(첫 커밋)부터 비교해서 더 작은 쪽이 이기고, 같으면
다음 글자(다음 커밋)를 비교하는 방식입니다. 그래서 "지금까지는 같은데,
바로 다음 한 걸음에서 더 작은 쪽을 고른다"를 매 단계 반복하면, 결과적으로
전체 문자열이 사전순으로 가장 작은 경로가 완성됩니다(단, 매 걸음에서
선택지가 "실제로 최단 경로를 유지하는" 이웃으로 한정되어 있어야 하며,
그 조건이 바로 위 `on_shortest_path` 체크입니다).

**실제 확인**: 단위 테스트에서 `root`가 `b1→c1`과 `b2→c2` 두 브랜치를 거쳐
`merge`(병합 커밋)로 합쳐지는 그래프를 만들어, 두 경로 모두 길이가 3으로
동일할 때 사전순으로 더 작은 `root→b1→c1→merge`가 정확히 선택됨을
확인했습니다(`제출/실행결과.md` §7). REPL에서도 `제출/results/04_PATH_최단경로.txt`에서
직접 연결(길이 1)과 공통 부모를 거치는 간접 연결(길이 2)을 모두 확인했습니다.

## 5. 정렬 알고리즘 직접 구현, 평균/최악 시간복잡도 및 안정 정렬 여부 설명

`sorting.merge_sort`는 병합 정렬을 일반화된 형태(비교 키를 함수로 받음)로
구현했습니다.

```python
def merge_sort(items, key):
    if len(items) <= 1:
        return list(items)
    mid = len(items) // 2
    left = merge_sort(items[:mid], key)
    right = merge_sort(items[mid:], key)
    return _merge(left, right, key)

def _merge(left, right, key):
    merged = []
    i = j = 0
    while i < len(left) and j < len(right):
        if key(left[i]) <= key(right[j]):   # <=  → 안정 정렬의 핵심
            merged.append(left[i]); i += 1
        else:
            merged.append(right[j]); j += 1
    merged.extend(left[i:])
    merged.extend(right[j:])
    return merged
```

**시간복잡도**: 리스트를 절반씩 나누는 분할 과정은 입력이 어떻게 배치돼
있든 항상 정확히 반으로 쪼개지므로, 재귀 깊이가 `log₂n`입니다. 각 깊이
층에서 이루어지는 병합 작업의 총량은 그 층에 있는 원소 전체 개수인
`n`입니다. 따라서 전체 시간은 `O(n) × O(log n) = O(n log n)`이며, 이는
**입력의 초기 배치와 무관하게 항상 성립**하므로 평균과 최악이 동일하게
O(n log n)입니다. (참고로 퀵 정렬은 평균은 O(n log n)이지만, 피벗을 잘못
고르면(예: 이미 정렬된 배열에서 항상 첫 원소를 피벗으로 고르는 구현)
최악의 경우 O(n²)까지 나빠질 수 있습니다 — 병합 정렬은 이런 입력 의존성이
없습니다.)

**안정 정렬 여부**: `_merge`에서 두 값을 비교할 때 `<`가 아니라 `<=`를
씁니다. 즉 두 값이 같을 때도 "왼쪽 그룹(원래 앞쪽에 있던 원소들)"을
먼저 채택합니다. 그 결과, 정렬 기준 값이 동일한 원소들끼리는 정렬하기
전의 상대적 순서가 정렬 후에도 그대로 유지됩니다 — 이것이 **안정
정렬(Stable Sort)**의 정의입니다.

**이게 왜 중요한가**: `LOG --sort-by=author`에서 같은 작성자가 커밋을
여러 개 가진 경우, "동률 처리 규칙은 자유"라는 과제 조건 안에서
"원래(위상 정렬) 순서를 유지한다"는 **직관적이고 재현 가능한 규칙**을
별도 코드 없이 안정 정렬의 성질만으로 얻을 수 있습니다.

**실제 확인**: 단위 테스트에서 작성자가 `Charlie/Alice/Bob/Alice`인 가짜
커밋 4개를 만들어 `author` 키로 정렬한 결과, 두 `Alice` 커밋 중 원본에서
먼저 나온 것이 정렬 후에도 먼저 나옴을 확인했습니다. 또한 무작위 정수
1,000개를 정렬해 파이썬 내장 `sorted()`(검증 목적으로만 사용, 실제 구현에는
미사용)의 결과와 완전히 일치함을 확인했습니다(`제출/실행결과.md` §7).

## 6. 역색인의 동작 원리와, 순회 검색보다 빠른 이유(시간복잡도 관점) 설명

`index.py`의 `InvertedIndex`는 커밋이 만들어질 때마다(`COMMIT` 실행 시)
메시지를 미리 분해해 색인해 둡니다.

```python
def add_commit(self, commit):
    for token in commit.message.split():      # 공백 기준 분리
        keyword = token.lower()                 # 소문자 정규화
        self._keyword_index.setdefault... .append(commit.hash)
    self._author_index.setdefault... .append(commit.hash)
```

**아주 쉬운 설명**: 책 뒤에 붙어있는 "찾아보기(색인)"와 같은 원리입니다.
책을 읽을 때마다 처음부터 그 단어를 찾는 대신, 미리 "이 단어는 몇 페이지에
나온다"를 정리해 둔 목록을 보고 바로 그 페이지로 넘어가는 것과 같습니다.
여기서는 "이 단어는 어떤 커밋(들)에 나온다"를 미리 정리해 둡니다.

**시간복잡도 비교**:

| 방식 | SEARCH 처리 방법 | 시간복잡도 |
|---|---|---|
| 순회 검색(역색인 없음) | 커밋 N개를 전부 훑으며 메시지 안에 키워드가 있는지 매번 검사 | O(N) |
| 역색인 검색(이 구현) | `keyword_index[키워드]`를 딕셔너리에서 바로 조회 | 평균 O(1) + 결과 복사 O(k) |

커밋이 10개면 차이가 크게 안 느껴지지만, 커밋이 100만 개라면 순회 검색은
매번 100만 번을 다 훑어야 하는 반면, 역색인은 여전히 거의 즉시 결과를
돌려줍니다. 대신 "커밋을 만들 때마다 미리 색인해두는" 비용(메시지 길이에
비례하는 O(m))을 매번 지불하는 트레이드오프입니다 — 검색이 저장보다
훨씬 자주 일어나는 상황(Git 로그처럼 한 번 만든 커밋을 여러 번 찾아보는
경우)에 유리한 구조입니다.

**author 검색도 같은 원리**: `author_index[작성자명]`으로 바로 조회하므로,
"이 사람이 만든 커밋을 모두 보여줘"도 전체 순회 없이 O(1) 조회로 처리됩니다.

**실제 확인**: `제출/results/06_SEARCH.txt`에서 `search login`이 정확히
1건(`Add login feature`)을, `search --author=Alice`가 3건(전체)을,
없는 키워드는 0건을 반환함을 확인했습니다. 대소문자가 섞인 메시지도
"Login"으로 검색하면 매칭되는지(소문자 정규화 확인) 별도 단위 테스트로도
검증했습니다(`제출/실행결과.md` §7).

## 7. 발표 또는 평가 때 사용할 짧은 요약

> "커밋은 부모 hash 목록만 들고 있는 노드이고, 이 참조들이 모여 DAG를
> 이룹니다. LOG는 Kahn의 위상 정렬로 부모가 항상 자식보다 먼저 나오게
> 했고, PATH는 부모-자식 연결을 무방향 간선으로 보고 양쪽에서 BFS 거리를
> 구해 사전순으로 가장 작은 최단 경로를 탐욕적으로 재구성했습니다.
> ANCESTORS는 부모 방향 BFS로 도달 가능한 모든 조상을 찾습니다. 정렬은
> sorted() 없이 병합 정렬을 직접 구현해 O(n log n)을 항상 보장하고
> 안정 정렬 성질로 동률 처리를 자연스럽게 해결했습니다. 검색은 커밋
> 생성 시점에 미리 만들어두는 역색인으로 전체 순회 없이 O(1)에 처리됩니다."

## 8. 평가 질문 대비 답변 자료

### 항목 1. 그래프 설계 질문

**Q1. 병합 커밋(부모 2개)이 생기면 DAG 성질이 깨지지 않는가?**

깨지지 않습니다. 부모가 1개든 2개든, "자식이 부모보다 나중에 만들어졌다"는
방향성과 "자기 자신으로 돌아오는 경로가 없다"는 비순환성은 그대로
유지됩니다. `traversal.py`의 세 함수(위상 정렬/최단 경로/조상) 모두
`commit.parents`의 길이를 가정하지 않고 일반적으로 순회하도록 작성해서,
병합 커밋이 있어도 코드 수정 없이 그대로 동작합니다(단위 테스트에서
다이아몬드형 그래프로 이미 검증).

**Q2. 커밋 저장소로 왜 dict를 썼는가? list로도 되지 않는가?**

`PATH`/`ANCESTORS`/`COMMIT`(부모 조회) 등 대부분의 연산이 "이 hash를 가진
커밋을 찾아라"라는 형태입니다. list에서 특정 값을 찾으려면 처음부터
끝까지 훑어야 해서 O(n)이지만, dict(해시맵)는 평균 O(1)에 바로 찾을 수
있습니다. 과제 명세도 "커밋 저장소는 커밋 hash로 빠르게 찾을 수 있어야
한다(예: 해시맵 기반)"고 명시하고 있고, 이 과제는 dict 사용을 허용하므로
(b3-1의 Mini Redis와 달리 dict/list/set은 자유롭게 사용 가능) 표준
dict를 그대로 활용했습니다.

**Q3. 커밋 hash 중복은 어떻게 막았는가?**

`commit.py`의 `generate_commit_hash`는 메시지/작성자/시각/부모 목록에
더해 **세션 동안 계속 증가하기만 하는 카운터**를 함께 SHA-1으로 해싱합니다.
완전히 동일한 내용으로 두 번 커밋해도 카운터 값이 다르므로 해시 입력
문자열 자체가 절대 겹치지 않습니다. 그럼에도(이론상 6자리 16진수 공간에서
극히 낮은 확률로) 충돌이 발생하면, 이미 존재하는 hash인지 확인해 다시
시도하는 방어 로직도 넣어두었습니다.

---

### 항목 2. 알고리즘 구현 질문

**Q1. 위상 정렬에서 동시에 진입차수가 0이 되는 커밋이 여러 개면 어떤
순서로 나오는가?**

FIFO 큐(리스트를 인덱스로 순회)를 쓰기 때문에, "먼저 큐에 들어온" 순서가
그대로 유지됩니다. 이 프로젝트의 전형적인 시나리오(하나의 뿌리 커밋에서
여러 브랜치가 갈라지는 경우)에서는 이 순서가 대체로 "먼저 생성된 순서"와
일치합니다. 과제 명세도 "학습 목적상 부모가 자식보다 먼저"라는 조건만
요구할 뿐 동률 처리 규칙은 정하지 않았으므로, 이 방식은 결정적이고
설명 가능한 선택입니다.

**Q2. PATH의 사전순 타이브레이크 로직을 O(n²)이 아니라 왜 더 효율적으로
만들 수 있었는가?**

모든 최단 경로를 일일이 나열해서(경로 개수가 그래프 구조에 따라
지수적으로 늘어날 수 있음) 문자열 비교로 최솟값을 고르는 방식도 가능은
하지만, 이 구현은 그 대신 "매 걸음마다 가능한 다음 후보 중 최솟값만
탐욕적으로 선택"하는 방식을 씁니다. 시작점/끝점 양방향 BFS(O(V+E))를
한 번씩 미리 해두면, 이후 경로 재구성은 경로 길이만큼의 반복 × 각 지점의
이웃 수 정도로 끝나 훨씬 효율적입니다.

**Q3. 병합 정렬 대신 퀵 정렬을 선택했다면 무엇이 달라졌을까?**

퀵 정렬은 평균 O(n log n)으로 병합 정렬과 같지만, (a) 최악의 경우
O(n²)로 나빠질 수 있고 (b) 일반적인 구현은 원소 교환(swap) 방식이라
안정 정렬이 아닙니다(같은 값이라도 위치가 바뀔 수 있음). 이 과제는
"동률 처리"가 중요한 `LOG --sort-by`에 정렬 결과를 쓰므로, 안정성이
보장되고 시간복잡도가 입력에 흔들리지 않는 병합 정렬을 선택했습니다.

### 항목 3. 명령어/CLI 설계 질문

**Q1. LOG의 `[branch]` 표시는 과제 예시와 다르게 --sort-by 결과에도
항상 나오게 했는데, 왜인가?**

과제 예시는 `--sort-by` 결과에서 `[branch]` 태그를 생략했지만, "출력
포맷은 자유이나 hash/author/timestamp/message가 식별 가능해야 한다"고만
명시되어 있어 형식 선택의 여지가 있었습니다. 정보가 더 많은 쪽이
유용하다고 판단해 두 출력 모두 일관되게 `[branch]`를 포함시켰습니다.

**Q2. INIT을 다시 호출하면 기존 데이터는 어떻게 되는가?**

저장소 전체(커밋/브랜치/역색인)를 새로 초기화합니다. 과제 명세가 "INIT은
저장소 초기화"라고 정의하고 있고, 별도의 "재초기화 방지" 요구사항이
없었기 때문에 매번 새로 시작하는 것이 가장 직관적이라고 판단했습니다.

**Q3. BRANCH를 이미 존재하는 이름으로 다시 호출하면?**

과제 명세에 이 경우에 대한 표준 에러가 정의되어 있지 않아서, 현재 HEAD
위치로 브랜치 포인터를 재설정하는 단순한 정책(덮어쓰기)을 택했습니다.
에러로 만들려면 새로운 에러 메시지를 발명해야 하는데, 명세가 제시한
3종(Invalid args / Unknown branch / Unknown commit)에 없는 문구를
임의로 추가하는 것보다, 있는 범위 안에서 가장 부작용이 적은 동작을
택하는 편이 낫다고 판단했습니다.

**Q4. INIT 이전에 다른 명령을 입력하면 어떻게 되는가?**

`Repository not initialized. Run INIT first.`라는 안내 메시지를 반환합니다.
이는 과제 명세의 최소 3종 표준 에러에는 없지만, "잘못된 입력에 대한 최소
에러 메시지를 표준화한다"는 조항이 그 3개가 전부라고 못박지는 않았기
때문에, 사용성을 위해 추가한 확장입니다.

### 항목 4. 제약 사항 관련 질문

**Q1. `sorted()`/`list.sort()`를 정말 하나도 안 썼는가?**

`main.py`와 `mini_git/*.py` 전체에서 `sorted(`, `.sort(` 패턴을 grep으로
전수 검사해 실사용이 없음을 확인했습니다(주석에서 이 API들을 "쓰지
않겠다"고 설명하는 텍스트만 걸렸고, 실제 호출은 0건이었습니다). 정렬이
필요한 유일한 지점(`LOG --sort-by`)은 전부 `sorting.merge_sort`를 거칩니다.
단, **테스트 코드**(제출 대상이 아닌 검증용 스크립트)에서는 merge_sort의
정확성을 "정답과 비교"하기 위한 목적으로만 파이썬 내장 `sorted()`를 한 번
사용했는데, 이는 구현 자체가 아니라 검증 도구로 쓴 것이라 제약 위반이
아니라고 판단했습니다.

**Q2. 그래프 전용 라이브러리를 안 썼다는 건 어떻게 확인했는가?**

`main.py`/`mini_git/*.py`의 모든 `import`/`from` 문을 확인한 결과
`hashlib`, `itertools`, `datetime`, `shlex`(모두 표준 라이브러리이며
그래프와 무관) 외에는 내부 모듈(`mini_git.xxx`)만 임포트하고 있어,
networkx 같은 그래프 전용 라이브러리는 전혀 쓰이지 않았습니다.

**Q3. dict/list/set을 자유롭게 쓸 수 있다는 걸 어떻게 활용했는가?**

커밋 저장소(`Repository.commits`), 브랜치 테이블(`Repository.branches`),
역색인 두 종류(`InvertedIndex._keyword_index`, `_author_index`)는 모두
파이썬 `dict`를 그대로 사용했습니다. 이 과제(b3-2)는 b3-1(Mini Redis)과
달리 "그래프 전용 라이브러리"와 "정렬 표준 API"만 금지하고 dict/list/set은
명시적으로 허용하고 있어, 해시맵을 직접 구현하는 대신 표준 dict로 "hash로
빠르게 찾기" 요구사항을 만족시켰습니다. `visited` 추적에는 `set`을
사용해 조상 탐색의 중복 방문 검사를 O(1)로 처리했습니다.

**Q4. 네트워크/파일 추적/영속성을 구현하지 않은 이유는?**

과제의 "기능 범위" 제약사항에 "파일 내용 추적은 구현하지 않는다(커밋
메타데이터 중심)", "네트워크 통신은 구현하지 않는다", "데이터 영속성은
구현하지 않아도 된다(메모리 상 동작으로 충분)"고 명시되어 있어 그대로
따랐습니다. 이 과제의 목표는 Git을 완전히 재현하는 것이 아니라, 커밋
그래프와 그 위의 탐색·정렬·검색 알고리즘의 동작 원리를 직접 손으로
확인하는 것이기 때문입니다.

### 항목 5. 검증 방법 질문

**Q1. 각 알고리즘이 올바르게 동작하는지 어떻게 검증했는가?**

REPL을 통한 통합 테스트 외에, `sorting.py`/`traversal.py`/`index.py`를
직접 import해서 모듈 단위로도 검증했습니다. 병합 정렬은 서로 다른
작성자·시각을 가진 가짜 커밋과 무작위 정수 1,000개로, 그래프 탐색은
병합 커밋이 있는 다이아몬드형 구조를 직접 만들어 위상 정렬 순서·최단
경로의 사전순 타이브레이크·조상 집합을 모두 정밀 검증했습니다
(`제출/실행결과.md`의 "데이터 구조/알고리즘 자체 단위 검증" 참고).

**Q2. 과제의 "8. 결과 예시"와 실제 실행 결과가 일치하는가?**

명령의 구조(초기화→커밋→브랜치→전환→커밋→LOG→PATH→SEARCH)와 각 명령의
출력 형식(`Initialized repository.` / `[branch hash] message` /
`commit hash (author, timestamp) [branch]` / `Path: h1 -> h2` /
`Found N commit(s):`)이 모두 예시와 동일하게 재현됩니다. 실제 hash 값은
SHA-1 기반으로 매 실행마다 새로 생성되므로 예시의 `a1b2c3`과는 다르지만,
과제 원문도 "실제 문구와 디자인은 달라도 된다"고 명시하고 있어 문제가
되지 않습니다.

# B3-2_추가 평가 질문 대비 설명 자료

## 1. AI API 연동 흐름(요청 구성 → 응답 처리 → 예외 대응)을 말로 설명

이 도구의 핵심은 단순히 AI API를 호출하는 것이 아니라, 어떤 데이터와 문맥을 AI에게 전달하느냐에 달려 있습니다. 먼저 `git status`와 `git diff`로 변경 내용을 수집하고, 사용자가 입력한 수정 의도를 함께 묶어 프롬프트를 구성합니다. 이후 모델에 `system`과 `user` 메시지를 전달하고, 응답을 파싱해 제목과 본문을 분리합니다.

예외 대응도 중요합니다. 호출 전에 API Key와 SDK 설치 여부를 확인해, 키가 없으면 요청을 보내지 않고 설정 방법을 안내합니다. 호출 중에는 SDK 예외를 종류별로 받아 원인을 알려줍니다. 401은 키 오류, 403은 권한, 404는 모델 ID, 429는 요청 한도, 5xx는 서버 오류, 시간 초과와 연결 실패는 네트워크 문제로 구분합니다. 응답이 와도 `stop_reason`이 `refusal`이면 거절로, `max_tokens`이면 잘림 경고로 처리합니다. 실제로 잘못된 키로 호출했을 때 `인증 실패(401): ... (invalid x-api-key)`가 출력되는 것을 확인했습니다(제출/results/04).

## 2. temperature, max_tokens, effort가 결과 품질에 미치는 영향 설명

`temperature`는 다음 단어를 고를 때의 무작위성입니다. 값이 높으면 표현이 다양해지지만 형식이 흔들리기 쉽고, 낮으면 일관되지만 단조로워집니다. 다만 현재 Anthropic API 버전(2026-10-21)과 기본 모델 `claude-opus-5-5`는 temperature를 받지 않습니다. 그래서 이 도구는 기본으로 temperature를 보내지 않고, 사용자가 지정하면 요청에 넣되 400 오류가 나면 그 이유를 안내합니다.

대신 `effort`로 품질과 비용을 조절합니다. effort는 모델이 답하기 전에 얼마나 깊이 생각할지 정하는 값입니다. `low`는 빠르고 저렴해서 diff 요약 같은 작업에 충분하고, 복잡한 변경이면 `medium`이나 `high`로 올립니다.

`max_tokens`는 응답 길이의 상한입니다. 최신 모델은 답하기 전에 생각하는 토큰도 이 한도에 포함됩니다. 그래서 예전처럼 512 정도로 두면 본문이 중간에 잘릴 수 있어 기본값을 16000으로 두었습니다. 실제 비용은 사용한 토큰만큼만 나갑니다. 설명문의 길이는 max_tokens가 아니라 프롬프트의 규칙(섹션별 불릿 1~3개, 제목 50자 권장)으로 제어합니다.

## 3. Git 변경 사항을 프로그램 입력으로 연결하는 방식 설명

이 도구는 Git 명령 결과를 프로그래밍적으로 수집합니다. `git status --porcelain`은 변경된 파일 목록을 알려주고, `git diff`는 실제 코드 차이를 보여줍니다. 이 정보를 AI가 이해할 수 있는 plain text로 합쳐서 프롬프트로 넘깁니다.

이 방식의 장점은, 사용자가 코드 변경 의도를 문장으로 적어 주면 AI가 변경 맥락을 더 잘 파악한다는 점입니다. 단순히 코드만 보고 추측하는 것보다, “로그인 로직 수정, 세션 검증 강화, 예외 처리 보완” 같은 문맥이 함께 들어가면 설명의 정확도가 높아집니다.

## 4. 프롬프트 설계 원리와 코드 설명 품질 제어

AI가 좋은 설명을 만들도록 하려면, 단순히 “코드 설명해줘”가 아니라 구조를 요구해야 합니다. 예를 들어 `Summary`, `What Changed`, `Why It Was Needed`, `How to Verify` 같은 섹션을 요구하면 응답 형식이 일관됩니다.

이는 코드 설명을 단순 기술 문서가 아니라 실무용 리뷰 문서로 바꾸는 핵심입니다. AI가 섹션을 따라가도록 요구함으로써, 문서의 구조와 핵심 포인트를 안정적으로 유지할 수 있습니다.

## 5. 보안과 검증의 중요성 설명

API 키는 코드에 하드코딩하면 위험합니다. 그래서 환경변수로 관리하고, 코드 내에는 값 자체를 남기지 않는 방식이 안전합니다. 또한 `--safe-mode`를 제공해 민감한 문자열을 마스킹하거나 diff 크기를 제한하는 구조도 필요합니다.

검증 로직도 중요합니다. 제목이 72자를 넘거나 섹션·불릿이 빠지면 리뷰 문서로 쓰기 어렵습니다. 이 도구는 세 단계로 처리합니다. 먼저 `### Summary`, `*` 불릿 같은 표기 차이를 내용 변경 없이 표준 형식으로 정리합니다. 그래도 필수 규칙을 어기면 오류 목록을 프롬프트에 넣어 한 번만 다시 요청합니다. 두 번째 응답도 틀리면 제목을 자르고 빠진 섹션에 "검토 후 직접 작성" 불릿을 넣어 보정합니다. 재생성을 한 번으로 제한한 것은 1회 실행당 요청을 1~2회로 묶어 비용을 예측할 수 있게 하기 위해서입니다.

safe-mode는 diff를 보내기 전에 API Key·토큰·비밀번호·이메일·전화번호를 정규식으로 가리고(A), 기본 10개 파일·200줄까지만 보냅니다(B). 기준은 옵션이나 컨벤션 파일로 바꿀 수 있고, `--dry-run`으로 실제 전송 내용을 먼저 확인할 수 있습니다.

## 6. 실무 적용 관점

이 도구는 단순한 학습 프로젝트를 넘어, 코드 리뷰 보조, 발표 자료 작성, 회고 문서 자동 생성 등 다양한 업무에 확장할 수 있습니다. 핵심은 AI에게 '무엇을 얼마나 구체적으로' 전달하느냐입니다.

사용자가 고친 코드와 의도를 충분히 설명해주면 AI는 리뷰어가 이해하기 쉬운 문장을 반환하므로, 반복적이고 지루한 설명 작업을 줄일 수 있습니다.

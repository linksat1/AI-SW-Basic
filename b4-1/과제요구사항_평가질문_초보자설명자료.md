# B4-1 포트폴리오 과제 설명 및 평가 질문 대비 자료

이 자료는 `b4-1/portfolio` 폴더에 구현된 포트폴리오 웹사이트가 과제 요구사항을 어떻게 만족하는지 초보자도 설명할 수 있도록 정리한 문서입니다.

---

## 1. 과제 결과물 한 줄 설명

이번 과제는 **순수 HTML, CSS, JavaScript만 사용해서 만든 반응형 포트폴리오 웹사이트**입니다.

웹사이트에는 다음 섹션이 들어 있습니다.

- Hero: 첫 인사와 CTA 버튼
- About: 자기소개와 프로필 사진
- Skills: HTML, CSS, JavaScript 등 기술 스택
- Projects: GitHub API로 불러온 저장소 카드
- Contact: 문의 폼
- Footer: 저작권과 소셜 링크

React, Vue, jQuery, Bootstrap, Tailwind 같은 외부 프레임워크 없이 직접 DOM을 선택하고 이벤트를 연결하여 기능을 구현했습니다.

---

## 2. 폴더 구조 요구사항 만족 설명

과제에서는 HTML, CSS, JavaScript, 이미지 파일을 역할별로 분리하라고 요구했습니다.

현재 구조는 다음과 같습니다.

```text
portfolio/
├── index.html
├── css/
│   └── style.css
├── js/
│   └── main.js
├── images/
│   ├── profile.jpg
│   └── profile.png
├── convert_png_to_jpg.py
└── README.md
```

각 파일의 역할은 다음과 같습니다.

- `index.html`: 웹페이지의 뼈대와 내용을 담당합니다.
- `css/style.css`: 색상, 배치, 반응형, 다크 모드 등 디자인을 담당합니다.
- `js/main.js`: 클릭, 스크롤, API 호출, 폼 검사 같은 동작을 담당합니다.
- `images/`: 프로필 이미지 같은 이미지 파일을 저장합니다.
- `convert_png_to_jpg.py`: PNG 이미지를 JPG로 변환할 때 사용한 보조 스크립트입니다.
- `README.md`: 프로젝트 설명, 사용 기술, 실행 방법, 기준값을 정리합니다.

즉, 파일이 역할별로 분리되어 있어서 초보자도 “HTML은 구조, CSS는 디자인, JavaScript는 동작”이라고 설명할 수 있습니다.

---

## 3. HTML 요구사항 만족 설명

`index.html`은 단순히 `div`만 사용하지 않고 의미가 있는 시맨틱 태그를 사용했습니다.

사용한 주요 시맨틱 태그는 다음과 같습니다.

- `<header>`: 페이지 상단 영역입니다.
- `<nav>`: 메뉴 이동 영역입니다.
- `<main>`: 페이지의 핵심 콘텐츠 영역입니다.
- `<section>`: Hero, About, Skills, Projects, Contact처럼 주제별 구역입니다.
- `<article>`: Skills 카드, Projects 카드처럼 독립적인 콘텐츠에 사용했습니다.
- `<footer>`: 저작권과 소셜 링크가 있는 하단 영역입니다.

네비게이션 메뉴에는 `#home`, `#about`, `#skills`, `#projects`, `#contact` 같은 앵커 링크가 있어서 메뉴를 클릭하면 해당 섹션으로 이동합니다.

이미지에는 `alt` 속성이 들어가 있습니다. 예를 들어 프로필 사진에는 “박주선의 프로필 사진”처럼 이미지가 무엇인지 설명하는 대체 텍스트가 있습니다.

Contact 폼에는 `<label for="name">`과 `<input id="name">`처럼 `for`와 `id`가 서로 연결되어 있습니다. 그래서 라벨을 클릭해도 입력칸에 포커스가 가고, 스크린리더도 어떤 입력칸인지 알 수 있습니다.

## 4. CSS 요구사항 만족 설명

`css/style.css`에서는 CSS 변수를 사용했습니다.

예를 들어 `:root`에 색상, 폰트, 간격을 변수로 정의했습니다.

```css
:root {
  --color-primary: #4f46e5;
  --color-bg: #ffffff;
  --color-text: #1e293b;
  --font-family: 'Noto Sans KR', sans-serif;
}
```

이렇게 하면 같은 색상을 여러 곳에 직접 쓰지 않고 `var(--color-primary)`처럼 불러서 사용할 수 있습니다.

다크 모드는 `[data-theme="dark"]`에서 색상 변수를 다시 정의하는 방식으로 구현했습니다.

```css
[data-theme="dark"] {
  --color-bg: #0f172a;
  --color-text: #f1f5f9;
}
```

JavaScript가 `html` 태그에 `data-theme="dark"`를 붙이면 CSS 변수가 바뀌고, 전체 화면이 다크 모드로 전환됩니다.

레이아웃도 요구사항에 맞게 구현했습니다.

- 네비게이션은 Flexbox를 사용했습니다.
- Projects 카드 목록은 Grid를 사용했습니다.
- `repeat(auto-fit, minmax(300px, 1fr))`를 사용해서 화면 크기에 따라 카드가 자동으로 1열, 2열, 3열로 바뀝니다.
- 모바일에서는 햄버거 버튼이 나타나고 메뉴가 접힙니다.
- 768px, 1024px 기준의 반응형 미디어 쿼리를 사용했습니다.

버튼과 카드에는 `hover`, `transition`, `box-shadow`가 적용되어 마우스를 올렸을 때 자연스럽게 반응합니다.

## 5. JavaScript 요구사항 만족 설명

`js/main.js`는 `var`를 사용하지 않고 `const`, `let`을 사용했습니다.

HTML에 `onclick`을 직접 쓰지 않고 `addEventListener`로 이벤트를 연결했습니다.

예를 들어 햄버거 메뉴는 다음 흐름으로 동작합니다.

1. 사용자가 햄버거 버튼을 클릭합니다.
2. JavaScript의 `click` 이벤트가 실행됩니다.
3. `classList.toggle('active')`로 메뉴 상태가 바뀝니다.
4. CSS에서 `.active` 클래스에 맞는 스타일이 적용되어 메뉴가 열리거나 닫힙니다.

DOM 조작도 과제 요구사항에 맞게 사용했습니다.

- `getElementById`, `querySelectorAll`로 요소를 선택했습니다.
- `textContent`로 타이핑 텍스트와 에러 메시지를 변경했습니다.
- `innerHTML`로 GitHub 프로젝트 카드 HTML을 동적으로 렌더링했습니다.
- `classList.add`, `remove`, `toggle`로 메뉴, 다크 모드, 에러 상태를 변경했습니다.

다룬 이벤트는 다음과 같습니다.

- `click`: 햄버거 메뉴, 다크 모드, 스크롤 탑 버튼, 필터 버튼
- `submit`: 문의 폼 전송
- `scroll`: 헤더 스타일 변경, 스크롤 탑 버튼 표시
- `input`: 폼 입력 중 에러 메시지 갱신

폼 제출 시에는 `event.preventDefault()`를 사용해서 실제 페이지 이동이나 새로고침을 막고, JavaScript로 직접 검사와 성공 메시지를 처리합니다.

## 6. 인터랙션 요구사항 만족 설명

### 햄버거 메뉴

모바일 화면에서 햄버거 버튼을 클릭하면 메뉴가 열리고, 다시 클릭하면 닫힙니다.

핵심 코드는 `hamburger.classList.toggle('active')`, `navMenu.classList.toggle('active')`입니다.

### 부드러운 스크롤

CSS의 `scroll-behavior: smooth` 덕분에 메뉴를 클릭하면 해당 섹션으로 부드럽게 이동합니다.

### 스크롤 탑 버튼

스크롤이 300px 이상 내려가면 오른쪽 아래 버튼이 나타납니다. 클릭하면 `window.scrollTo({ top: 0, behavior: 'smooth' })`로 맨 위로 이동합니다.

### 네비게이션 스타일 변경

스크롤이 60px 이상 내려가면 header에 `scrolled` 클래스가 붙습니다. 그러면 헤더 배경색과 그림자가 생겨서 스크롤 상태를 시각적으로 알 수 있습니다.

### 다크 모드

다크 모드 버튼을 클릭하면 `data-theme` 값이 바뀌고 CSS 변수도 함께 바뀝니다.

또한 `localStorage`에 `theme` 값을 저장하기 때문에 새로고침 후에도 사용자가 선택한 테마가 유지됩니다.

### 스크롤 애니메이션

`IntersectionObserver`를 사용했습니다. 섹션이 화면에 20% 이상 보이면 `visible` 클래스가 추가되고, CSS 애니메이션으로 서서히 나타납니다.

### 폼 UX

Contact 폼은 이름, 이메일, 메시지를 검사합니다.

- 빈 값이면 “필수 항목입니다.”
- 이메일 형식이 틀리면 “유효한 이메일 주소를 입력하세요.”
- 메시지가 10자 미만이면 “메시지를 10자 이상 입력하세요.”

에러는 입력 필드 근처에 표시되며, 올바르게 입력하면 에러가 사라집니다.

## 7. GitHub API 요구사항 만족 설명

Projects 섹션은 GitHub API를 사용해 저장소 목록을 가져옵니다.

사용한 주소 형식은 다음과 같습니다.

```text
https://api.github.com/users/linksat1/repos?sort=updated&per_page=12
```

동작 흐름은 다음과 같습니다.

1. `loadProjects()` 함수가 실행됩니다.
2. 먼저 로딩 UI를 보여줍니다.
3. `fetch()`로 GitHub API에 요청합니다.
4. 성공하면 `res.json()`으로 데이터를 JavaScript 배열로 바꿉니다.
5. `map()`으로 저장소 배열을 HTML 카드 문자열로 변환합니다.
6. `projectsGrid.innerHTML`에 넣어서 화면에 표시합니다.
7. 실패하면 `catch`에서 에러 UI와 재시도 버튼을 보여줍니다.
8. 저장소가 없거나 필터 결과가 없으면 빈 상태 메시지를 보여줍니다.

구현된 상태 UI는 다음과 같습니다.

- 로딩 상태: 스피너와 “프로젝트를 불러오는 중...” 표시
- 성공 상태: 프로젝트 카드 목록 표시
- 에러 상태: “프로젝트를 불러올 수 없습니다.” 또는 요청 제한 안내 표시
- 빈 상태: “표시할 프로젝트가 없습니다.” 표시

또한 `sessionStorage`를 사용해 GitHub API 결과를 10분간 캐시합니다. 이렇게 하면 같은 브라우저 탭에서 새로고침을 자주 해도 API 요청 횟수를 줄일 수 있습니다.

캐싱 흐름은 다음과 같습니다.

1. `getCachedRepos()`가 `sessionStorage`에 저장된 데이터가 있는지 확인합니다.
2. 저장된 데이터가 있고 10분이 지나지 않았다면 API를 다시 호출하지 않고 캐시 데이터를 사용합니다.
3. 캐시가 없거나 만료되면 `fetch()`로 GitHub API를 호출합니다.
4. 새로 받아온 저장소 목록은 `cacheRepos()`에서 다시 `sessionStorage`에 저장합니다.

## 8. 상태 관리 흐름 설명

이 과제의 핵심은 “사용자 이벤트 → 상태 변경 → 화면 업데이트” 흐름입니다.

### 예시 1. 다크 모드

1. 사용자 이벤트: 다크 모드 버튼 클릭
2. 상태 변경: `data-theme` 값이 `dark` 또는 `light`로 바뀜
3. 화면 업데이트: CSS 변수가 바뀌면서 전체 색상이 변경됨
4. 상태 유지: `localStorage`에 저장되어 새로고침 후에도 유지됨

### 예시 2. GitHub API

1. 사용자 또는 초기 실행 이벤트: 페이지 로드 시 `loadProjects()` 실행
2. 상태 변경: 로딩, 성공, 에러, 빈 상태 중 하나가 됨
3. 화면 업데이트: 상태에 맞게 스피너, 카드, 에러 메시지, 빈 메시지를 렌더링함

### 예시 3. 폼 유효성 검사

1. 사용자 이벤트: 입력 또는 제출
2. 상태 변경: 각 입력값이 정상인지 에러인지 판단
3. 화면 업데이트: 에러 메시지 표시 또는 제거

### 예시 4. 프로젝트 필터링

1. 사용자 이벤트: 언어 필터 버튼 클릭
2. 상태 변경: `currentFilter` 값이 `all`, `JavaScript`, `HTML`, `CSS` 중 하나로 변경
3. 데이터 선택: `getFilteredRepos()`에서 `filter()`로 조건에 맞는 저장소만 고름
4. 화면 업데이트: `renderFilteredProjects()`가 필터링된 저장소 목록을 다시 렌더링

## 9. 보너스 구현 설명

선택 과제 중 일부도 구현되어 있습니다.

### 프로젝트 언어별 필터링: `filter()` 사용

Projects 섹션에는 `전체`, `JavaScript`, `HTML`, `CSS` 필터 버튼이 있습니다.

사용자가 버튼을 클릭하면 `currentFilter` 값이 바뀌고, `getFilteredRepos()` 함수가 실행됩니다.

```js
function getFilteredRepos() {
  if (currentFilter === 'all') return allRepos;
  return allRepos.filter((repo) => repo.language === currentFilter);
}
```

여기서 `filter()`는 전체 저장소 배열 중에서 `repo.language`가 현재 선택한 언어와 같은 저장소만 골라 새 배열을 만듭니다.

예를 들어 JavaScript 버튼을 누르면 `language` 값이 `JavaScript`인 저장소만 화면에 다시 표시됩니다.

### Hero 타이핑 효과: 이름이 한 글자씩 나타남

Hero 섹션의 이름 부분은 처음에는 비어 있고, JavaScript가 한 글자씩 채웁니다.

```js
const name = '박주선';
let pos = 0;

const timer = setInterval(() => {
  pos++;
  el.textContent = name.slice(0, pos);
  if (pos >= name.length) {
    clearInterval(timer);
  }
}, 200);
```

`setInterval()`은 0.2초마다 코드를 반복 실행합니다. `slice(0, pos)`는 이름의 앞부분부터 지정한 글자 수만큼 잘라서 보여줍니다.

그래서 화면에는 `박` → `박주` → `박주선` 순서로 이름이 나타납니다.

### GitHub API 캐싱: `sessionStorage`로 API 요청 부담 감소

GitHub API는 너무 자주 요청하면 제한에 걸릴 수 있습니다. 그래서 API 응답으로 받은 저장소 목록을 `sessionStorage`에 저장합니다.

```js
sessionStorage.setItem(REPOS_CACHE_KEY, JSON.stringify({
  savedAt: Date.now(),
  repos,
}));
```

저장할 때는 `savedAt`에 저장 시간을 함께 넣습니다. 다시 불러올 때 현재 시간과 저장 시간을 비교해서 10분이 지나지 않았으면 저장된 데이터를 그대로 사용합니다.

이 방식 덕분에 같은 탭에서 새로고침을 반복해도 매번 GitHub API를 호출하지 않아 요청 부담을 줄일 수 있습니다.

## 10. 제출 전 확인할 부분

코드 구현 기준으로 주요 기능은 과제 요구사항을 만족합니다.

다만 실제 제출 전에는 다음 항목을 실제 값으로 채우면 더 완성도가 높습니다.

- `README.md`의 GitHub Pages 배포 URL
- 데스크톱, 모바일, 다크 모드 스크린샷
- 본인 이름, 이메일, GitHub 아이디가 모두 정확한지 최종 확인
- GitHub Pages를 이미 배포했다면, 수정한 파일을 커밋하고 GitHub에 푸시해서 배포 사이트에도 최신 내용이 반영되었는지 확인

## 항목 1. 기능 동작 확인 질문

### Q1. 브라우저 창 크기를 줄였을 때 레이아웃이 모바일에 맞게 변경되는가?

네. CSS 미디어 쿼리를 사용해서 화면 크기에 따라 레이아웃이 바뀌도록 만들었습니다.

모바일 크기에서는 네비게이션 메뉴가 숨겨지고 햄버거 버튼이 나타납니다. Hero, About, Skills, Contact 영역도 가로 배치에서 세로 배치로 바뀌기 때문에 작은 화면에서도 보기 좋게 표시됩니다.

Projects 섹션은 Grid의 `auto-fit`과 `minmax(300px, 1fr)`을 사용해서 화면이 넓으면 여러 열, 좁으면 1열로 자동 조정됩니다.

### Q2. 테마 토글 버튼 클릭 시 다크/라이트 모드가 전환되고, 새로고침 후에도 유지되는가?

네. 버튼을 클릭하면 JavaScript가 `html` 요소의 `data-theme` 값을 바꿉니다.

`data-theme="dark"`가 되면 CSS의 다크 모드 변수가 적용되어 배경색과 글자색이 바뀝니다.

또한 선택한 테마를 `localStorage`에 저장합니다. 그래서 새로고침을 해도 `localStorage.getItem('theme')`로 저장된 값을 다시 읽어서 이전 테마를 유지합니다.

### Q3. 햄버거 메뉴, 스크롤 애니메이션, 맨 위로 가기 버튼 등이 정상 동작하는가?

네.

햄버거 메뉴는 클릭 이벤트에서 `active` 클래스를 토글해서 열고 닫습니다.

스크롤 애니메이션은 `IntersectionObserver`로 섹션이 화면에 들어왔는지 감지하고, 들어오면 `visible` 클래스를 추가해서 서서히 나타나게 합니다.

맨 위로 가기 버튼은 스크롤이 300px 이상 내려갔을 때 표시되고, 클릭하면 `window.scrollTo()`로 페이지 맨 위로 부드럽게 이동합니다.

### Q4. GitHub API에서 데이터를 불러와 화면에 표시되고, 로딩/에러/빈 상태가 구분되는가?

네. `fetch()`와 `async/await`를 사용해 GitHub API에서 저장소 데이터를 가져옵니다.

데이터를 요청하는 동안에는 로딩 스피너가 보입니다. 요청이 성공하면 저장소 카드가 표시됩니다. 요청이 실패하면 에러 메시지와 재시도 버튼이 표시됩니다. 표시할 프로젝트가 없으면 빈 상태 메시지가 표시됩니다.

### Q5. 필수 입력값 누락, 이메일 형식 오류 시 즉각적인 피드백이 표시되는가?

네. Contact 폼에서 이름, 이메일, 메시지를 검사합니다.

필수 입력값이 비어 있으면 “필수 항목입니다.”라는 에러가 표시됩니다. 이메일 형식이 맞지 않으면 이메일 오류 메시지가 표시됩니다. 메시지가 너무 짧으면 10자 이상 입력하라는 메시지가 표시됩니다.

입력 중에도 `input` 이벤트로 다시 검사해서, 올바르게 수정하면 에러 메시지가 사라집니다.

## 항목 2. HTML, CSS, JavaScript 구조 질문

### Q1. HTML, CSS, JavaScript가 각각의 파일로 분리되어 있고, 분리한 이유와 각 파일의 역할을 설명할 수 있는가?

네. 파일을 역할별로 분리했습니다.

`index.html`은 웹페이지의 구조와 내용을 담당합니다. 예를 들어 제목, 메뉴, 섹션, 버튼, 폼 같은 요소를 작성합니다.

`css/style.css`는 디자인을 담당합니다. 색상, 글자 크기, 레이아웃, 반응형, hover 효과, 다크 모드를 작성합니다.

`js/main.js`는 동작을 담당합니다. 버튼 클릭, 스크롤 이벤트, GitHub API 호출, 폼 유효성 검사, 다크 모드 저장 등을 처리합니다.

이렇게 분리하면 코드를 찾기 쉽고, 수정할 때도 구조, 디자인, 동작을 따로 관리할 수 있습니다.

### Q2. header, nav, main, section, footer 등 시맨틱 태그를 사용했고, 어떤 기준으로 태그를 선택했는지 설명할 수 있는가?

네. 태그의 의미에 맞게 선택했습니다.

`header`는 페이지 상단 영역이기 때문에 사용했습니다. `nav`는 메뉴 이동 링크가 있는 영역이라 사용했습니다. `main`은 페이지의 핵심 내용 전체를 감싸기 위해 사용했습니다. `section`은 Hero, About, Skills, Projects, Contact처럼 주제별 구역을 나누기 위해 사용했습니다. `footer`는 저작권과 소셜 링크가 있는 페이지 하단 영역이라 사용했습니다.

시맨틱 태그를 쓰면 사람도 구조를 이해하기 쉽고, 검색엔진과 스크린리더도 페이지 구조를 더 잘 이해할 수 있습니다.

### Q3. CSS 변수(:root)로 색상, 폰트 등을 정의했고, 변수로 관리하면 어떤 이점이 있는지 구체적으로 답변할 수 있는가?

네. `:root`에 색상, 폰트, 간격 같은 값을 변수로 정의했습니다.

예를 들어 주요 색상을 `--color-primary`로 정해두면 여러 곳에서 같은 색상을 반복해서 직접 쓰지 않아도 됩니다. 나중에 색상을 바꾸고 싶을 때 변수 값 하나만 수정하면 버튼, 링크, 강조 색상이 함께 바뀝니다.

다크 모드도 CSS 변수 덕분에 쉽게 구현할 수 있습니다. 라이트 모드 변수와 다크 모드 변수를 따로 정의해두고, JavaScript가 `data-theme`만 바꿔주면 전체 색상이 한 번에 바뀝니다.

### Q4. onclick 인라인 속성 대신 addEventListener를 사용한 이유를 두 방식의 차이와 비교하여 제시할 수 있는가?

네.

`onclick`은 HTML 태그 안에 직접 JavaScript를 쓰는 방식입니다. 예를 들어 `<button onclick="openMenu()">`처럼 작성합니다.

반면 `addEventListener`는 JavaScript 파일에서 요소를 선택한 뒤 이벤트를 연결하는 방식입니다.

이 과제에서는 `addEventListener`를 사용했습니다. 이유는 HTML은 구조만 담당하고, JavaScript는 동작만 담당하도록 분리할 수 있기 때문입니다. 또한 하나의 요소에 여러 이벤트 처리를 추가하기도 쉽고, 코드 관리가 더 깔끔합니다.

## 항목 3. 코드 흐름 및 핵심 개념 질문

### Q1. 다크 모드, API 호출, 폼 유효성 검사 중 하나를 예로 들어 “이벤트 → 상태 변경 → 화면 업데이트” 흐름을 코드에서 어떻게 이어지는지 설명할 수 있는가?

다크 모드로 설명할 수 있습니다.

먼저 사용자가 다크 모드 버튼을 클릭합니다. 이것이 이벤트입니다.

```js
themeToggle.addEventListener('click', () => {
  const isDark = root.getAttribute('data-theme') === 'dark';
  applyTheme(!isDark);
  saveTheme(!isDark ? 'dark' : 'light');
});
```

클릭 이벤트가 발생하면 현재 테마가 다크인지 확인하고, 반대 상태로 바꿉니다. 이것이 상태 변경입니다.

그다음 `applyTheme()` 함수가 실행되면서 `data-theme` 속성과 아이콘이 바뀝니다. 이것이 화면 업데이트입니다.

```js
function applyTheme(isDark) {
  if (isDark) {
    root.setAttribute('data-theme', 'dark');
    themeIcon.className = 'fa-solid fa-sun';
  } else {
    root.setAttribute('data-theme', 'light');
    themeIcon.className = 'fa-solid fa-moon';
  }
}
```

즉, 사용자의 클릭이 테마 상태를 바꾸고, 바뀐 상태가 CSS에 반영되어 화면 색상이 바뀌는 구조입니다.

### Q2. async/await와 try/catch를 사용하여 API 호출 성공과 실패를 어떻게 분기 처리했는지 코드 흐름을 따라 답변할 수 있는가?

네. `loadProjects()` 함수에서 처리합니다.

먼저 `showLoading()`으로 로딩 UI를 보여줍니다. 그다음 `fetch()` 앞에 `await`를 붙여 GitHub API 응답이 올 때까지 기다립니다.

```js
const res = await fetch(
  `https://api.github.com/users/${GITHUB_USERNAME}/repos?sort=updated&per_page=12`
);
```

응답이 성공이면 `await res.json()`으로 데이터를 배열로 바꾼 뒤 `renderProjects()`로 화면에 카드들을 출력합니다.

응답이 실패이면 `throw error`로 에러를 발생시키고, `catch` 블록에서 `showError()`를 실행합니다.

그래서 성공과 실패를 다음처럼 나눌 수 있습니다.

- 성공: API 데이터 받기 → JSON 변환 → 프로젝트 카드 렌더링
- 실패: 에러 잡기 → 에러 메시지와 재시도 버튼 표시

### Q3. map, filter 등 배열 메서드를 활용하여 GitHub 데이터를 카드 UI로 변환하는 과정을 단계별로 정리할 수 있는가?

네.

GitHub API에서 받은 데이터는 저장소 객체들이 들어 있는 배열입니다.

`map()`은 배열의 각 저장소를 HTML 카드 문자열로 바꾸는 데 사용했습니다.

```js
repos.map(({ name, description, html_url, language }) => `
  <article class="project-card">
    <h3>${name}</h3>
    <p>${description || '설명이 없습니다.'}</p>
  </article>
`)
```

이렇게 하면 저장소 배열이 카드 HTML 배열로 바뀝니다. 마지막에 `.join('')`으로 하나의 문자열로 합치고, `innerHTML`에 넣어 화면에 표시합니다.

`filter()`는 언어별 필터링에 사용했습니다.

```js
function getFilteredRepos() {
  if (currentFilter === 'all') return allRepos;
  return allRepos.filter((repo) => repo.language === currentFilter);
}
```

예를 들어 JavaScript 버튼을 누르면 `language`가 `JavaScript`인 저장소만 골라서 다시 렌더링합니다.

### Q4. Flexbox와 Grid를 각각 어디에 적용했고 해당 상황에서 그 방식을 선택한 이유를 비교하여 설명할 수 있는가?

네.

Flexbox는 네비게이션, 버튼 그룹, 카드 내부처럼 한 방향으로 정렬하는 곳에 사용했습니다. 예를 들어 로고는 왼쪽, 메뉴는 오른쪽에 배치해야 하므로 네비게이션에는 Flexbox가 적합합니다.

Grid는 Projects 카드 목록, About 정보 목록, Contact 레이아웃처럼 행과 열을 함께 다루는 곳에 사용했습니다. 특히 프로젝트 카드는 화면 크기에 따라 여러 열로 배치되어야 하므로 Grid가 적합합니다.

쉽게 말하면 Flexbox는 한 줄 정렬에 강하고, Grid는 카드 목록처럼 2차원 배치에 강합니다.

## 항목 4. 설계 의도 질문

### Q1. 상태(STATE) 객체를 따로 만들어서 관리한 이유는 무엇이며, 그냥 변수로 처리하면 안 되는지 설명할 수 있는가?

이 프로젝트에서는 모든 상태를 하나의 큰 객체로 묶지는 않았지만, 상태 역할을 하는 값들을 따로 관리했습니다.

예를 들어 다음 값들이 상태입니다.

- `allRepos`: GitHub API에서 받아온 전체 저장소 목록
- `currentFilter`: 현재 선택된 프로젝트 필터
- `data-theme`: 현재 다크 모드인지 라이트 모드인지
- 각 입력 필드의 에러 여부

상태를 따로 관리하는 이유는 화면이 그 상태에 따라 달라지기 때문입니다.

예를 들어 `currentFilter`가 `all`이면 전체 프로젝트를 보여주고, `JavaScript`이면 JavaScript 프로젝트만 보여줍니다. 즉, 화면은 상태를 기준으로 다시 그려집니다.

그냥 아무 변수나 여기저기 흩어놓고 처리하면 나중에 “현재 화면이 왜 이렇게 보이는지” 추적하기 어렵습니다. 상태를 의식해서 관리하면 이벤트가 발생했을 때 어떤 값이 바뀌고, 그 결과 화면이 어떻게 바뀌는지 설명하기 쉬워집니다.

React에서 말하는 상태 관리도 결국 이 개념을 더 체계적으로 만든 것입니다.

### Q2. 반응형 디자인에서 “모바일 퍼스트”로 작성한 이유를 이야기할 수 있는가?

모바일 퍼스트는 작은 화면을 먼저 기준으로 만들고, 화면이 커질 때 태블릿과 데스크톱 스타일을 추가하는 방식입니다.

이 방식을 선택한 이유는 요즘 사용자가 모바일로 웹사이트를 보는 경우가 많기 때문입니다. 작은 화면에서 먼저 잘 보이게 만들면 핵심 콘텐츠를 간결하게 구성할 수 있고, 이후 큰 화면에서는 공간을 활용해 가로 배치나 여러 열 레이아웃을 추가하면 됩니다.

또한 모바일 화면은 공간이 좁기 때문에 가장 까다로운 조건입니다. 모바일에서 먼저 잘 동작하게 만들면 태블릿과 데스크톱으로 확장하기가 더 쉽습니다.

## 11. 발표 또는 평가 때 사용할 짧은 요약

제 포트폴리오 웹사이트는 순수 HTML, CSS, JavaScript로 구현했습니다.

HTML은 `header`, `nav`, `main`, `section`, `article`, `footer` 같은 시맨틱 태그를 사용해서 구조를 명확하게 만들었습니다.

CSS는 변수, Flexbox, Grid, 미디어 쿼리를 사용해서 라이트 모드와 다크 모드, 모바일/태블릿/데스크톱 반응형 레이아웃을 구현했습니다.

JavaScript는 `addEventListener`로 이벤트를 연결하고, 다크 모드, 햄버거 메뉴, 스크롤 탑 버튼, 스크롤 애니메이션, GitHub API 호출, 폼 유효성 검사를 구현했습니다.

특히 GitHub API 부분에서는 `async/await`, `try/catch`, `map`, `filter`를 사용해 데이터를 가져오고 카드 UI로 렌더링했습니다.

전체적으로 “사용자 이벤트 → 상태 변경 → 화면 업데이트” 흐름을 직접 구현해서 React를 배우기 전 필요한 DOM 조작, 이벤트 처리, 비동기 처리의 기본 개념을 익힐 수 있는 과제입니다.

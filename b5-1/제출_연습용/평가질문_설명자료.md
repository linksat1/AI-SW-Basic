## 2. 데이터베이스가 "엑셀과 뭐가 다른지" 설명

**아주 쉬운 설명**: 엑셀은 표 하나에 모든 정보를 다 적으려고 해서 같은 내용이 여러 번 반복되지만,
데이터베이스는 정보를 역할별로 나눈 여러 표(테이블)로 쪼개고, 표끼리 "번호(ID)"로 서로 연결합니다.

예를 들어 엑셀 한 장에 "주문번호, 고객이름, 고객번호, 메뉴이름, 가격, 수량"을 전부 적으면,
같은 고객이 여러 번 주문할 때마다 그 고객의 이름과 번호를 매번 다시 적어야 합니다.
이러다가 한 곳에서 이름 철자를 잘못 적으면 데이터가 서로 안 맞게 됩니다.

이 과제에서는 그래서 표를 4개로 나눴습니다.

| 표 | 담는 정보 | 왜 따로 뒀는가 |
|---|---|---|
| `customer` | 고객 정보 (이름, 전화번호) | 고객 정보는 한 번만 저장하고, 여러 주문에서 재사용 |
| `menu` | 메뉴 정보 (이름, 가격, 카테고리) | 메뉴 가격이 바뀌어도 메뉴 표 한 줄만 수정하면 됨 |
| `orders` | 주문 1건의 정보 (누가, 언제, 상태) | "어떤 주문이 있었는지"만 담당 |
| `order_item` | 주문 안에 담긴 메뉴들 (몇 개 시켰는지) | 주문 1건에 메뉴가 여러 개 담길 수 있어서 따로 분리 |

→ **핵심 한 줄**: "같은 정보를 여러 번 적지 않고, 표를 나눈 뒤 번호로 연결해서 관리하는 것"이 엑셀과 DB의 근본적인 차이입니다.

## 3. PK/FK가 무엇이고, 1:N 관계가 데이터를 어떻게 연결하는지 설명

**PK(Primary Key, 기본키)**: 그 표에서 각 줄을 구별하는 "고유 번호표"입니다. 중복되면 안 됩니다.
**FK(Foreign Key, 외래키)**: 다른 표의 PK를 그대로 가져와서 "이 줄은 저 표의 몇 번과 연결된다"고 표시하는 값입니다.

`schema.sql`에서 실제로 쓴 부분:

```sql
CREATE TABLE customer (
    id    INTEGER PRIMARY KEY AUTOINCREMENT,  -- customer의 PK
    ...
);

CREATE TABLE orders (
    id          INTEGER PRIMARY KEY AUTOINCREMENT, -- orders의 PK
    customer_id INTEGER NOT NULL,                  -- customer를 가리키는 FK
    ...
    FOREIGN KEY (customer_id) REFERENCES customer(id)
);
```

**1:N 관계란?**: "한쪽은 1개, 다른 쪽은 여러 개"로 연결되는 관계입니다.
이 과제에는 1:N 관계가 3개 있습니다.

| 1 (부모) | N (자식) | 의미 |
|---|---|---|
| `customer` 1명 | `orders` 여러 건 | 고객 한 명이 주문을 여러 번 할 수 있다 |
| `orders` 1건 | `order_item` 여러 줄 | 주문 1건에 메뉴가 여러 개 담길 수 있다 |
| `menu` 1개 | `order_item` 여러 줄 | 메뉴 하나가 여러 주문에 반복해서 팔릴 수 있다 |

**말로 설명하는 예시**: "김도윤 고객(customer.id=1)이 주문을 2번 했는데(orders 테이블에 customer_id=1인 줄이 2개),
그 중 1번 주문 안에는 아메리카노 2잔과 초코케이크 1개가 담겨 있습니다(order_item 테이블에 order_id=1인 줄이 2개).
이렇게 번호(FK)로 표를 이어 붙이면, 표를 나눠도 정보가 끊기지 않고 다시 합칠 수 있습니다."

## 4. SELECT / INSERT / UPDATE / DELETE를 언제 쓰는지 설명

| 명령어 | 언제 쓰는가 | 이 과제에서 실제로 쓴 예 |
|---|---|---|
| `SELECT` | 이미 있는 데이터를 "조회"만 할 때 | `queries.sql`의 15개 쿼리 대부분 |
| `INSERT` | 새 데이터를 표에 "추가"할 때 | `data.sql`에서 고객/메뉴/주문 데이터 입력 |
| `UPDATE` | 이미 있는 데이터의 값을 "수정"할 때 | `queries.sql`에서 `주문접수` 상태를 `제조중`으로 변경 |
| `DELETE` | 이미 있는 데이터를 "삭제"할 때 | `queries.sql`에서 취소된 주문을 삭제 |

**아주 쉬운 비유**: SELECT는 "찾아보기", INSERT는 "새로 쓰기", UPDATE는 "고쳐쓰기", DELETE는 "지우기"입니다.

주의해서 설명할 점: UPDATE와 DELETE는 `WHERE` 조건을 빼먹으면 표 전체가 수정/삭제되므로,
항상 "어떤 줄만 바꿀지" 조건을 먼저 확인하고 실행해야 합니다.

```sql
-- WHERE로 "주문접수 상태인 것만" 골라서 수정
UPDATE orders
SET status = '제조중'
WHERE status = '주문접수';
```

## 5. JOIN과 GROUP BY로 "연결된 데이터를 한 번에 뽑는 방법" 설명

**JOIN이란?**: 표 여러 개를 번호(FK)로 이어 붙여서, 한 번의 조회로 여러 표의 정보를 같이 보는 것입니다.

`queries.sql`의 실제 예시 (주문마다 고객 이름을 같이 보여주는 쿼리):

```sql
SELECT o.id AS 주문번호, c.name AS 고객, o.order_date, o.status
FROM orders o
INNER JOIN customer c ON o.customer_id = c.id
ORDER BY o.order_date;
```

**말로 설명하면**: "orders 표는 고객 이름을 모르고 customer_id 번호만 갖고 있습니다.
그래서 customer 표와 '번호가 같은 줄끼리' 이어 붙여서, 주문 목록에 고객 이름까지 같이 보이게 만든 것입니다."

**INNER JOIN과 LEFT JOIN의 차이** (평가자가 자주 묻는 부분):
- `INNER JOIN`: 양쪽 표에 모두 값이 있는 경우만 보여줍니다.
- `LEFT JOIN`: 왼쪽 표는 전부 보여주고, 오른쪽에 연결된 값이 없으면 빈 값(NULL)으로 보여줍니다.

실제로 쓴 LEFT JOIN 예시 (주문을 한 번도 안 한 고객도 0건으로 포함해서 보여주기):

```sql
SELECT c.name, COUNT(o.id) AS 주문횟수
FROM customer c
LEFT JOIN orders o ON c.id = o.customer_id
GROUP BY c.id, c.name
ORDER BY 주문횟수 DESC;
```

**GROUP BY란?**: 데이터를 "같은 값끼리 묶어서" 개수/합계/평균 같은 요약값을 구하는 것입니다.
위 쿼리에서는 "고객 이름별로" 묶어서 각 고객이 몇 번 주문했는지(`COUNT`) 셌습니다.
만약 `LEFT JOIN`을 안 쓰고 `INNER JOIN`을 썼다면, 주문을 한 번도 안 한 고객(한도현)은 결과에서 아예 빠졌을 것입니다.
실제로 `results/08_조인LEFT1.txt`를 보면 한도현의 주문횟수가 `0`으로 정상적으로 표시됩니다.

## 6. 실무 요구(검색/정렬/집계/랭킹)를 SQL로 푸는 감각 설명

| 실무 요구 | SQL 표현 | 이 과제의 예시 |
|---|---|---|
| 검색(조건에 맞는 것만 찾기) | `WHERE` | 커피 카테고리 메뉴만 조회 (`기본조회 2`) |
| 정렬(순서대로 나열) | `ORDER BY` | 가장 비싼 메뉴 순으로 정렬 (`기본조회 4`) |
| 랭킹(상위 N개만 보기) | `ORDER BY` + `LIMIT` | 가장 비싼 메뉴 TOP 3 (`기본조회 4`) |
| 집계(개수/합계/평균 구하기) | `GROUP BY` + `COUNT`/`SUM`/`AVG` | 메뉴별 판매 수량 합계 (`집계 1`) |

**말로 설명하는 예시**: "가장 비싼 메뉴 3개를 뽑아라"는 요구가 오면,
"가격 기준으로 내림차순 정렬(`ORDER BY price DESC`)하고, 위에서 3개만 자른다(`LIMIT 3`)"로 바꿔서 풀면 됩니다.

```sql
SELECT name, price
FROM menu
ORDER BY price DESC
LIMIT 3;
```

## 7. 인덱스가 왜 필요한지, 어떤 컬럼에 적용하면 좋은지 설명

**인덱스란?**: 책의 "찾아보기(색인)"처럼, 특정 컬럼으로 자주 검색한다면 미리 정렬된 목록을 만들어둬서
데이터를 더 빨리 찾게 해주는 것입니다.

이 과제에서 적용한 인덱스:

```sql
CREATE INDEX idx_order_item_order_id ON order_item(order_id);
```

**왜 이 컬럼에 걸었나?**: `order_item` 표에서 "이 주문(order_id)에 어떤 메뉴가 담겼는지"를
자주 조회하기 때문입니다. 인덱스가 없으면 매번 표 전체를 처음부터 끝까지 훑어야 하지만(Full Scan),
인덱스가 있으면 바로 해당 order_id 위치로 찾아갈 수 있습니다.

실제로 `EXPLAIN QUERY PLAN`으로 확인한 결과(`results/15_인덱스.txt`):

```
QUERY PLAN
`--SEARCH order_item USING INDEX idx_order_item_order_id (order_id=?)
```

`SEARCH ... USING INDEX`라고 나온 것이 "표 전체를 훑지 않고 인덱스를 이용해 바로 찾아갔다"는 증거입니다.

**주의할 점**: 인덱스는 조회는 빠르게 해주지만, 데이터를 추가/수정할 때마다 인덱스도 같이 갱신해야 하므로
모든 컬럼에 무조건 걸면 오히려 느려질 수 있습니다. 그래서 "자주 검색 조건으로 쓰이는 컬럼"에만 선택적으로 적용합니다.

## 8. 제약조건(NOT NULL, UNIQUE, FK) 설명

| 제약조건 | 의미 | 이 과제에서 적용한 곳 |
|---|---|---|
| `NOT NULL` | 이 값은 반드시 있어야 한다(빈 값 금지) | `customer.name`, `customer.phone`, `orders.customer_id` 등 |
| `UNIQUE` | 이 값은 표 안에서 중복되면 안 된다 | `customer.phone`, `menu.name` |
| `FOREIGN KEY` | 이 값은 반드시 부모 표에 실제로 존재하는 값이어야 한다 | `orders.customer_id → customer.id` 등 |

**FK가 실제로 막아주는 상황 설명**: 만약 `orders`에 존재하지 않는 `customer_id`(예: 999번)를 넣으려고 하면
아래처럼 에러가 나면서 저장이 거부됩니다.

```
FOREIGN KEY constraint failed
```

→ 이게 왜 중요하냐면, "있지도 않은 고객이 주문한 것처럼" 데이터가 잘못 저장되는 것을 DB가 스스로 막아주기 때문입니다.
SQLite는 기본적으로 이 검사를 꺼둔 상태라서, `schema.sql` 맨 위에 `PRAGMA foreign_keys = ON;`을 반드시 넣어야
FK 제약이 실제로 동작합니다.

## 9. 서브쿼리 설명

**서브쿼리란?**: 쿼리 안에 또 다른 쿼리를 넣어서, "먼저 조회한 결과를 조건으로 다시 쓰는" 방법입니다.

실제 예시 (주문을 한 번도 안 한 고객 찾기):

```sql
SELECT name, phone
FROM customer
WHERE id NOT IN (SELECT DISTINCT customer_id FROM orders);
```

**말로 설명하면**: "안쪽 쿼리(`SELECT DISTINCT customer_id FROM orders`)가 먼저 '주문을 한 적 있는 고객 번호 목록'을 만들고,
바깥쪽 쿼리가 '그 목록에 없는(NOT IN) 고객'만 골라낸다"는 2단계 흐름입니다.

**JOIN과 차이**: 같은 결과를 LEFT JOIN + `WHERE o.id IS NULL`로도 만들 수 있는데,
서브쿼리는 "이 조건에 맞는 목록"을 먼저 따로 구한 뒤 비교한다는 점이 다릅니다.

## 10. 왜 이 주제(카페 주문)를 선택했는지 설명

- 실생활에서 이해하기 쉬운 도메인이라 테이블 간 관계(고객→주문→주문상세←메뉴)를 직관적으로 설명할 수 있습니다.
- 1:N 관계가 자연스럽게 3개(customer→orders, orders→order_item, menu→order_item) 나와서
  과제 요구사항(1:N 관계 2개 이상)을 충분히 만족합니다.
- "주문 상태(대기/제조중/완료/취소)"가 있어서 UPDATE, DELETE, 집계 쿼리를 현실적인 시나리오로 만들 수 있었습니다.

## 11. 발표 또는 평가 때 사용할 짧은 요약

> "엑셀 한 장 대신, 고객·메뉴·주문·주문상세로 표를 나누고 번호(PK/FK)로 서로 연결했습니다.
> 그래서 고객 정보나 메뉴 가격은 한 곳에만 저장하고, 여러 주문에서 재사용할 수 있습니다.
> SELECT/JOIN/GROUP BY로 필요한 정보를 조합해서 뽑고, 서브쿼리로 '주문 이력이 없는 고객'처럼
> 조건을 좁혀가는 조회도 만들었습니다. UPDATE/DELETE로 주문 상태를 관리했고,
> 자주 조회하는 컬럼(order_id)에는 인덱스를 걸어서 조회 속도를 확인했습니다."

### 항목 1 — 산출물 체크리스트 (증거 기반으로 즉시 확인 가능)

> 최소 4개 테이블이 존재하고, 각 테이블에 PK가 정의되어 있는가? / FK를 사용한 1:N 관계가
> 최소 2개 이상 존재하고, 실제 값 참조가 실제로 맞는가? / 각 테이블에 최소 10행 이상의 샘플
> 데이터가 입력되어 있는가? / 기본 조회(4개), 조인(4개), 집계(3개), 서브쿼리(1개), 수정/삭제(2개),

| FK 참조 값이 실제로 유효 | ✅ orders.customer_id는 전부 1~10 범위(customer 존재 범위), order_item.order_id/menu_id도 전부 유효 범위 | `제출_연습용/data.sql` 전체, `PRAGMA foreign_keys = ON;`(L6, L12)으로 강제 |
| 테이블당 10행 이상 | ✅ customer 10 / menu 10 / orders 12 / order_item 17 | `제출_연습용/data.sql` |
| 쿼리 15개, 카테고리 구성(4/4/3/1/2/1) | ✅ 기본조회4·조인4(INNER3+LEFT1)·집계3·서브쿼리1·수정삭제2·인덱스1 | `제출_연습용/queries.sql` (파일 상단 주석에 카테고리 명시) |
| 쿼리별 실행 결과 첨부 | ✅ 15개 쿼리 각각 `results/NN_이름.txt`로 실행 SQL + 결과 세트로 존재 | `제출_연습용/results/01~15*.txt` |

**말로 확인시켜 줄 때**: "제출 폴더의 `schema.sql`을 열면 CREATE TABLE 4개와 FOREIGN KEY 3곳이

분류가 적혀 있습니다. `results/` 폴더에 쿼리 파일명과 1:1로 매칭되는 실행 결과 15개가 들어
있습니다"라고 파일을 직접 열어 보여주면서 설명하면 이 항목은 즉시 확인됩니다.

### 항목 2 — 테이블 설계 이해 질문

> 테이블을 어떻게 나눴는지, 각 테이블의 역할을 말할 수 있는가? / FK로 연결한 1:N 관계가
> 실제 도메인에서 어떤 의미인지 예시를 들어 보여줄 수 있는가? / 컬럼 타입(TEXT, INTEGER,
> DATE 등)을 왜 그렇게 선택했는지 설명할 수 있는가? / 인덱스를 어떤 컬럼에 걸었고, 왜 그
> 컬럼이어야 하는지 이유를 답변할 수 있는가?

**Q1. 테이블을 어떻게 나눴는지, 각 테이블의 역할은?**

카페 주문이라는 하나의 흐름을 "누가/무엇을/얼마나/언제"로 쪼갰습니다.

| 테이블 | 역할 | 한 줄 답변 |
|---|---|---|
| `customer` | 누가(고객) | 이름·전화번호·가입일처럼 "그 사람에 대한 정보"만 담습니다 |
| `menu` | 무엇을(메뉴) | 이름·카테고리·가격처럼 "그 메뉴에 대한 정보"만 담습니다 |
| `orders` | 언제/누가(주문 1건) | "이 주문이 언제, 누가, 무슨 상태인지"만 담고, 안에 뭐가 담겼는지는 모릅니다 |
| `order_item` | 얼마나(주문 상세) | "이 주문에 이 메뉴가 몇 개 들어갔는지"만 담습니다 — 주문과 메뉴를 이어주는 연결 역할 |

**Q2. FK로 연결한 1:N 관계가 실제 도메인에서 어떤 의미인지 예시로 보여달라고 하면?**

`results/05_조인INNER1.txt`를 펴서 이렇게 설명합니다: "customer.id=1(김도윤)이
orders 테이블에 두 번 나옵니다(주문번호 1, 4) — 이게 `customer(1) → orders(N)`입니다.
그리고 `results/06_조인INNER2.txt`를 보면 주문번호 1 안에 아메리카노 2잔과 초코케이크
1개, 총 2줄이 order_item에 있습니다 — 이게 `orders(1) → order_item(N)`입니다. 즉 '한
고객이 여러 번 주문하고, 한 주문 안에 여러 메뉴가 담긴다'는 카페의 실제 운영 방식을
그대로 테이블 관계로 옮긴 것입니다."

**Q3. 컬럼 타입을 왜 그렇게 선택했는가?**

| 컬럼 예시 | 선택한 타입 | 이유 |
|---|---|---|
| `customer.name`, `menu.category` | `TEXT` | 길이가 정해지지 않은 문자열이고, 산술 연산 대상이 아님 |
| `customer.id`, `menu.price`, `order_item.quantity` | `INTEGER` | 정수 연산(합계·평균·비교)이 필요하거나 자동 증가 PK로 써야 함 |
| `customer.joined_at`, `orders.order_date` | `DATE` | "이후/이전" 같은 날짜 비교(`WHERE joined_at >= '2025-03-01'`)와 정렬을 SQL이 날짜로 이해하게 하려고 문자열이 아니라 DATE로 선언 |

가격(`menu.price`)을 `INTEGER`로 한 이유도 짚어두면 좋습니다: "원 단위라 소수점이 필요
없어서 `REAL`(실수) 대신 `INTEGER`를 썼고, 부동소수점 오차 없이 정확한 합계(`SUM`)를
구할 수 있습니다."

**Q4. 인덱스를 어떤 컬럼에 걸었고, 왜 그 컬럼이어야 하는가?**

`order_item.order_id`에 걸었습니다(`schema.sql` L56: `CREATE INDEX idx_order_item_order_id
ON order_item(order_id);`). 이유는 "이 주문에 어떤 메뉴가 몇 개 담겼는지"를 조회하는
`WHERE order_id = ?` 형태의 쿼리가 실무에서 가장 자주 일어날 조회 패턴이기 때문입니다.
인덱스가 없으면 `order_item` 전체를 처음부터 훑어야 하지만(Full Scan), 인덱스가 있으면
바로 그 order_id로 찾아갑니다. `results/15_인덱스.txt`의 `EXPLAIN QUERY PLAN` 결과에
`SEARCH order_item USING INDEX idx_order_item_order_id (order_id=?)`라고 찍힌 것이
"인덱스를 실제로 탔다"는 직접적인 증거입니다.

### 항목 3 — 개념 이해(DB 기초) 질문

> 데이터베이스가 엑셀과 무엇이 다른지, 왜 테이블을 나눠서 저장하는지 비교하며 설명할 수
> 있는가? / PK와 FK의 역할을 구분하고, 1:N 관계가 데이터를 어떻게 연결하는지 본인 스키마
> 기준으로 보여줄 수 있는가? / INNER JOIN과 LEFT JOIN의 차이를 실행 결과를 보며 설명할 수
> 있는가? / GROUP BY와 집계 함수(COUNT, SUM, AVG)가 어떻게 동작하는지 쿼리 결과를 보며
> 이야기할 수 있는가?

**Q1. 데이터베이스가 엑셀과 무엇이 다른가?**

"엑셀 한 장에 주문·고객·메뉴 정보를 전부 욱여넣으면, 같은 고객이 주문할 때마다 그
고객의 이름·전화번호를 매번 다시 적게 됩니다. 이름 철자를 한 번이라도 잘못 치면 그
순간부터 '같은 사람'인지 프로그램이 구분을 못 합니다. 저는 그래서 표를 4개(customer/
menu/orders/order_item)로 나누고, 고객 정보는 customer에 딱 한 번만 저장한 뒤 orders에서
customer_id 번호만 참조하게 만들었습니다. 고객 전화번호가 바뀌어도 customer 표 한 줄만
고치면 그 고객의 모든 과거 주문에 자동으로 반영됩니다 — 이게 '데이터가 얼마나 많냐'가
아니라 '관계를 표현할 수 있냐'의 차이입니다."

**Q2. PK와 FK의 역할을 본인 스키마 기준으로 구분해서 보여달라고 하면?**

"`orders` 테이블을 예로 들면, `id`는 PK로 '이 주문 자체를 구별하는 고유 번호'이고,
`customer_id`는 FK로 '이 주문을 누가 했는지, customer 테이블의 몇 번을 가리키는지'
나타냅니다. PK는 '나는 누구인가'를 나타내고 FK는 '나는 누구와 연결되어 있는가'를
나타낸다고 구분해서 설명합니다." (`schema.sql` L37-43을 보여주며 설명)

**Q3. INNER JOIN과 LEFT JOIN의 차이를 실행 결과를 보며 설명할 수 있는가?**

`results/07_조인INNER3.txt`와 `results/08_조인LEFT1.txt`를 나란히 펴놓고 비교합니다.
"INNER JOIN(조인-INNER 3)은 취소된 주문이 있는 고객만 보여줍니다 — 양쪽에 값이 다
있을 때만 나옵니다. 반면 LEFT JOIN(조인-LEFT 1)으로 고객별 주문 횟수를 세면, 주문을
한 번도 안 한 한도현 고객도 목록에서 빠지지 않고 '주문횟수 0'으로 나옵니다. 만약 이걸
INNER JOIN으로 했다면 한도현은 통째로 결과에서 사라졌을 겁니다 — 그게 두 JOIN의
핵심 차이입니다."

**Q4. GROUP BY와 집계 함수(COUNT/SUM/AVG)가 어떻게 동작하는지 쿼리 결과를 보며 설명하면?**

`results/09_집계1.txt`(SUM), `results/10_집계2.txt`(COUNT), `results/11_집계3.txt`(AVG)
세 개를 순서대로 보여주며 설명합니다.

- **SUM** (`집계 1`): "메뉴 이름으로 GROUP BY 한 다음, 같은 메뉴가 여러 주문에 나눠 팔린
  수량(`quantity`)을 `SUM`으로 다 더칩니다. 예를 들어 카페라떼가 주문 2번(수량 1)과
  9번(수량 3)에 나눠 팔렸다면, 결과에는 카페라떼 한 줄에 총 4로 합쳐져 나옵니다."
- **COUNT** (`집계 2`): "주문 상태(`status`)로 GROUP BY 해서 '완료가 몇 건, 취소가 몇
  건'처럼 상태별 개수를 셉니다."
- **AVG** (`집계 3`): "메뉴 카테고리로 GROUP BY 해서 커피/음료/디저트 각각의 평균 가격을
  구합니다. `ROUND(AVG(price), 0)`로 소수점을 반올림해 보기 좋게 만들었습니다."

한 줄 요약: "GROUP BY는 '같은 값끼리 한 무더기로 묶는' 역할만 하고, 그 무더기 안에서
실제로 개수를 셀지(COUNT)/합칠지(SUM)/평균 낼지(AVG)는 집계 함수가 결정합니다."

### 항목 4 — 심화/회고 질문

> 작성한 쿼리 중 가장 복잡한 쿼리를 선택하고, 어떻게 작동되는지 단계별로 설명할 수
> 있는가? / 미션 수행 중 가장 어려웠던 부분과 해결 방법을 구체적으로 말할 수 있는가?

**Q1. 가장 복잡한 쿼리를 골라 단계별로 설명하면?**

`조인-LEFT 1`(`results/08_조인LEFT1.txt`)을 가장 복잡한 쿼리로 꼽습니다.

```sql
SELECT c.name, COUNT(o.id) AS 주문횟수
FROM customer c
LEFT JOIN orders o ON c.id = o.customer_id
GROUP BY c.id, c.name
ORDER BY 주문횟수 DESC;
```

단계별 설명:
1. **FROM customer c** — 먼저 고객 10명을 전부 기준(왼쪽 표)으로 놓습니다.
2. **LEFT JOIN orders o ON c.id = o.customer_id** — 각 고객에게 연결된 주문을 붙이되,
   주문이 하나도 없는 고객(한도현)도 버리지 않고 orders 쪽 값을 NULL로 채워 남깁니다.
   (여기서 INNER JOIN을 썼다면 한도현이 이 시점에 이미 사라졌을 것입니다.)
3. **GROUP BY c.id, c.name** — 고객 단위로 방금 붙인 주문들을 다시 묶습니다. 같은
   고객이 여러 줄(여러 주문)로 붙어 있던 걸 한 줄로 모으는 단계입니다.
4. **COUNT(o.id)** — 묶인 그룹 안에서 orders.id가 NULL이 아닌 것만 셉니다. 한도현처럼
   주문이 없어 NULL만 있는 그룹은 정확히 0으로 계산됩니다(`COUNT(*)`가 아니라
   `COUNT(o.id)`를 쓴 이유가 이것입니다 — `COUNT(*)`였다면 NULL 행도 1로 잘못 셀 뻔했습니다).
5. **ORDER BY 주문횟수 DESC** — 마지막으로 주문을 많이 한 고객이 위로 오도록 정렬합니다.

**Q2. 미션 수행 중 가장 어려웠던 부분과 해결 방법은?**

"가장 어려웠던 부분은 DELETE 쿼리에서 FK 제약 순서를 처음에 반대로 짰던 것입니다.
취소된 주문(orders)을 먼저 지우려고 했더니 `FOREIGN KEY constraint failed` 에러가
났습니다. 원인을 보니, order_item이 그 주문을 여전히 참조하고 있는데 부모(orders)를
먼저 지우려 했기 때문이었습니다. 자식 데이터가 남아있는 상태에서 부모를 지우면 '고아
데이터(참조가 끊긴 데이터)'가 생기기 때문에 SQLite가 이를 막은 것입니다. 해결 방법은
DELETE 순서를 뒤집어서, 자식 테이블(order_item)의 관련 행을 먼저 지운 뒤에 부모
테이블(orders)을 지우는 것이었습니다(`queries.sql`의 `[삭제 DELETE]` 두 문장 순서 참고).
이 경험으로 'FK 제약은 단순히 잘못된 값 저장을 막는 것뿐 아니라, 삭제 순서도 강제해서
데이터의 일관성을 지켜준다'는 것을 몸으로 이해하게 됐습니다. 비슷하게, SQLite는 FK
제약을 기본으로 꺼둔다는 것도 처음엔 몰라서 `PRAGMA foreign_keys = ON;`을 빼먹고
테스트했다가 제약이 전혀 안 걸리는 걸 보고 나서야 알게 됐습니다."

### 항목 5 — 보너스 과제

> 보너스 문제 해결에 따른 크레딧 부여

현재 제출물에는 보너스 과제(① 같은 요구를 JOIN과 서브쿼리 두 방식으로 풀어 비교 /
② FK 에러를 일부러 유발해 원인·해결을 기록 / ③ 핵심 지표 3개를 정의한 미니 리포트)를
**포함하지 않았습니다.** 필수 요구사항(테이블 4개·1:N 2개 이상·10행 이상·쿼리 15개)을
확실히 맞추는 데 먼저 집중했기 때문입니다.

다만 이미 만든 자료로 **①과 ②는 추가 코드 없이도 바로 말로 보여줄 수 있는 부분**이 있습니다.

- **① JOIN vs 서브쿼리 비교**: `제출_연습용/queries.sql`의 `[서브쿼리]`(주문 이력 없는 고객 찾기,
  `NOT IN`)와, 항목 3-Q3에서 언급한 동일 결과의 LEFT JOIN 버전
  (`LEFT JOIN orders o ON c.id=o.customer_id WHERE o.id IS NULL`)을 나란히 제시하면
  "같은 요구를 두 방식으로 푼" 사례를 즉석에서 보여줄 수 있습니다.
- **② FK 위반 재현**: `INSERT INTO orders (customer_id, order_date, status) VALUES
  (999, '2026-07-01', '주문접수');`처럼 존재하지 않는 customer_id로 INSERT를 시도하면
  `FOREIGN KEY constraint failed` 에러가 즉시 재현됩니다. 항목 4-Q2의 DELETE 순서 경험과
  묶어서 "FK가 어떻게 정합성을 지키는지 직접 깨뜨려 확인했다"고 설명할 수 있습니다.
- **③ 미니 리포트**는 아직 준비되어 있지 않습니다. 필요하다면 "메뉴별 판매 순위 TOP 3"
  (`집계 1` 쿼리를 `LIMIT 3`만 추가하면 재사용 가능), "고객별 누적 결제 금액", "일별 주문
  건수 추이" 세 가지를 지표로 제안할 수 있습니다.

재평가 전 시간이 된다면 ②(FK 위반 재현 쿼리 1줄 + 결과 캡처 1개)가 가장 적은 노력으로
가장 확실한 보너스 크레딧을 받을 수 있는 항목입니다.

실제 코드와 실행 결과를 보여주면서 설명하는 것이 가장 확실합니다.

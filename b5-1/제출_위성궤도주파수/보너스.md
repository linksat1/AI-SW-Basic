모든 쿼리는 `연습/schema.sql` + `연습/data.sql`로 새로 만든 DB에서 실행했습니다.

## 1. 조인 vs 서브쿼리 비교

**요구사항**: "정지궤도(GSO)로 등록된 위성망 신고만 조회한다." (geo 테이블에 위치 정보가 있는 notice)

### INNER JOIN 버전

```sql
SELECT DISTINCT n.ntc_id, n.adm, n.d_rcv
FROM notice n
INNER JOIN geo g ON n.ntc_id = g.ntc_id
ORDER BY n.ntc_id;
```

실행 결과: 15행 (notice 중 ntc_type='G'인 모든 행)

실행 계획:
```
QUERY PLAN
|--SCAN g
|--SEARCH n USING INTEGER PRIMARY KEY (rowid=?)
|--USE TEMP B-TREE FOR DISTINCT
`--USE TEMP B-TREE FOR ORDER BY
```

### 서브쿼리(IN) 버전

```sql
SELECT n.ntc_id, n.adm, n.d_rcv
FROM notice n
WHERE n.ntc_id IN (SELECT ntc_id FROM geo)
ORDER BY n.ntc_id;
```

실행 결과: 동일한 15행

실행 계획:
```
QUERY PLAN
|--SEARCH n USING INTEGER PRIMARY KEY (rowid=?)
`--LIST SUBQUERY 1
   `--SCAN geo
```

### 비교

- **결과는 동일**하지만(15건, 같은 신고 목록) 실행 계획은 다르다.
- JOIN 버전은 geo와 notice를 결합한 뒤 **DISTINCT로 중복을 제거**하고 다시 **정렬을 위한 임시
  B-TREE**를 만든다. 지금은 notice:geo가 1:1에 가까워 중복이 안 생기지만, 만약 geo에 한 신고당
  여러 행(예: 궤도 위치가 여러 번 갱신된 이력)이 들어있다면 JOIN은 부모(notice) 행을 그만큼
  중복 출력하므로 DISTINCT/GROUP BY가 **꼭 필요**해진다.
- 서브쿼리(IN) 버전은 자식 테이블 값을 "존재 여부"로만 사용하기 때문에 애초에 중복이 생기지 않고,
  notice의 rowid(=ntc_id, INTEGER PRIMARY KEY) 순서를 그대로 타므로 별도의 ORDER BY용 임시
  B-TREE도 필요 없었다.
- 즉, **JOIN은 자식 테이블의 컬럼(long_nom 등)까지 같이 가져와야 할 때**, **서브쿼리는 "자식이
  있는지/없는지"만 필터 조건으로 쓸 때** 더 적합하다는 걸 실행 계획으로 확인했다.

## 2. 정합성 깨뜨려보기

**시도**: 존재하지 않는 부모 `ntc_id`(999999999)로 `geo`에 INSERT

```sql
PRAGMA foreign_keys = ON;
INSERT INTO geo (ntc_id, sat_name, long_nom) VALUES (999999999, 'GHOST-SAT', 100);
```

**실행 결과**:
```
Error: FOREIGN KEY constraint failed
```

확인: `SELECT COUNT(*) FROM geo WHERE sat_name = 'GHOST-SAT';` → `0` (실제로 삽입되지 않음)

### 왜 막히는가

`geo.ntc_id`가 `FOREIGN KEY (ntc_id) REFERENCES notice(ntc_id)`로 선언돼 있고,
`PRAGMA foreign_keys = ON`이 켜져 있으면 SQLite가 INSERT 시점에 `notice` 테이블에 해당
`ntc_id`가 실제로 존재하는지 검사한다. 999999999는 `notice`에 없는 값이므로 "고아 행(orphan row)"이
생기는 걸 막기 위해 제약이 발동해 INSERT 자체를 거부한다.

### 어떻게 고치는가

부모(`notice`)에 해당 `ntc_id`를 먼저 넣은 뒤 같은 INSERT를 실행하면 성공한다.

```sql
INSERT INTO notice (ntc_id, adm, ntc_type, d_rcv, ntf_rsn, st_cur)
VALUES (999999999, 'KOR', 'G', '2026-07-19', 'N', 50);

INSERT INTO geo (ntc_id, sat_name, long_nom) VALUES (999999999, 'GHOST-SAT', 100);
```

결과: `999999999 | GHOST-SAT | 100.0` — 정상 삽입됨.

**교훈**: FK 제약은 "자식을 부모보다 먼저 넣지 마라"는 것을 강제로 지켜준다. `data.sql`에서
`notice → geo/orbit/freq` 순서로 INSERT한 것도 이 때문이다.

## 3. 미니 리포트 — 핵심 지표 3개

### 지표 1. 신고국(adm)별 신고 건수 및 비중

어떤 나라가 위성망 신고를 가장 많이 했는지 파악하는 지표.

```sql
SELECT adm, COUNT(*) AS 건수,
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM notice), 1) AS 비중_퍼센트
FROM notice
GROUP BY adm
ORDER BY 건수 DESC;
```

| adm | 건수 | 비중(%) |
|---|---|---|
| F (프랑스) | 5 | 29.4 |
| CHN (중국) | 3 | 17.6 |
| RUS (러시아) | 2 | 11.8 |
| KOR (한국) | 2 | 11.8 |
| VTN/LUX/IND/E/CYP | 각 1 | 각 5.9 |

→ 이 표본에서는 프랑스(F)가 가장 많은 위성망을 신고했고, 한국은 KOREASAT 2건으로 공동 3위권.

### 지표 2. 정지궤도(GSO) vs 비정지궤도(NGSO) 비율

전체 신고 중 어떤 궤도 방식이 더 흔한지 보는 지표.

```sql
SELECT ntc_type, COUNT(*) AS 건수,
       ROUND(100.0 * COUNT(*) / (SELECT COUNT(*) FROM notice), 1) AS 비중_퍼센트
FROM notice
GROUP BY ntc_type;
```

| ntc_type | 건수 | 비중(%) |
|---|---|---|
| G (정지궤도) | 15 | 88.2 |
| N (비정지궤도) | 2 | 11.8 |

→ 표본 데이터는 정지궤도(방송/통신 중계용) 신고가 압도적으로 많다. 실제 위성망 등록 DB 전체 통계에서도
방송위성 서비스 관련 GSO 신고 비중이 높은 편이라는 것과 방향이 일치한다.

### 지표 3. 주파수 대역 구분별 신고 건수 및 평균 대역폭

C/Ku/Ka 대역 중 어디에 신고가 몰려 있고 대역폭은 얼마나 넓은지 보는 지표.
(주파수 하한 `freq_min` 기준으로 대략적인 대역을 분류: 1GHz 미만=L/S, 1~8GHz=C, 8~18GHz=Ku, 18GHz 이상=Ka)

```sql
SELECT
  CASE
    WHEN freq_min < 1000  THEN '1.L/S 이하'
    WHEN freq_min < 8000  THEN '2.C 대역'
    WHEN freq_min < 18000 THEN '3.Ku 대역'
    ELSE '4.Ka 대역 이상'
  END AS 대역구분,
  COUNT(*) AS 건수,
  ROUND(AVG(bdwdth), 0) AS 평균대역폭_kHz
FROM freq
GROUP BY 대역구분
ORDER BY 대역구분;
```

| 대역구분 | 건수 | 평균 대역폭(kHz) |
|---|---|---|
| L/S 이하 | 9 | 19,667 |
| C 대역 | 20 | 38,346 |
| Ku 대역 | 11 | 64,545 |
| Ka 대역 이상 | 10 | 565,000 |

→ 대역이 높아질수록(고주파로 갈수록) 평균 대역폭도 함께 크게 넓어진다. Ka 대역 이상은 건수는
적지만 평균 대역폭이 다른 대역보다 압도적으로 넓은데, 이는 실제로 Ka 대역이 고용량 피더링크
(위성-지상국 간 대용량 백홀 회선)에 주로 쓰이기 때문이다.

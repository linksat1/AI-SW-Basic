## 2. 데이터베이스가 "엑셀과 뭐가 다른지" 설명

**아주 쉬운 설명**: 엑셀은 표 하나에 모든 정보를 다 적으려고 해서 같은 내용이 여러 번 반복되지만,
데이터베이스는 정보를 역할별로 나눈 여러 표(테이블)로 쪼개고, 표끼리 "번호(ID)"로 서로 연결합니다.

예를 들어 엑셀 한 장에 "신고번호, 신고국, 위성이름, 궤도경도, 주파수대역"을 전부 적으면,
같은 신고에 주파수 대역이 여러 개 딸려 있을 때마다 신고번호·신고국을 매번 다시 적어야 합니다.
이러다가 신고국 코드를 한 곳에서 잘못 적으면 데이터가 서로 안 맞게 됩니다.

이 과제에서는 그래서 표를 4개로 나눴습니다.

| 표 | 담는 정보 | 왜 따로 뒀는가 |
|---|---|---|
| `notice` | 신고 원장 (신고국, 신고일, GSO/NGSO 구분) | 신고 정보는 한 번만 저장하고, 여러 궤도/주파수 정보에서 재사용 |
| `geo` | 정지궤도(GSO) 위성의 궤도 경도 | GSO 위성만 갖는 정보라 따로 분리 |
| `orbit` | 비정지궤도(NGSO) 위성의 궤도면 정보 | NGSO 위성만 갖는 정보이고, 한 신고에 궤도면이 여러 개(최대 15개) 있을 수 있어 분리 |
| `freq` | 신고에 포함된 주파수 대역 | 신고 1건에 주파수 대역이 여러 개(신고당 2~3개 이상) 딸리므로 분리 |

→ **핵심 한 줄**: "같은 정보를 여러 번 적지 않고, 표를 나눈 뒤 번호로 연결해서 관리하는 것"이 엑셀과 DB의 근본적인 차이입니다.

## 3. PK/FK가 무엇이고, 1:N 관계가 데이터를 어떻게 연결하는지 설명

**PK(Primary Key, 기본키)**: 그 표에서 각 줄을 구별하는 "고유 번호표"입니다. 중복되면 안 됩니다.
**FK(Foreign Key, 외래키)**: 다른 표의 PK를 그대로 가져와서 "이 줄은 저 표의 몇 번과 연결된다"고 표시하는 값입니다.

`schema.sql`에서 실제로 쓴 부분:

```sql
CREATE TABLE notice (
    ntc_id   INTEGER PRIMARY KEY,   -- notice의 PK (ITU 실제 신고번호를 그대로 사용)
    ...
);

CREATE TABLE geo (
    id       INTEGER PRIMARY KEY AUTOINCREMENT, -- geo 자체의 PK
    ntc_id   INTEGER NOT NULL,                   -- notice를 가리키는 FK
    ...
    FOREIGN KEY (ntc_id) REFERENCES notice(ntc_id)
);
```

**참고**: `notice.ntc_id`는 `AUTOINCREMENT`를 쓰지 않고 실제 ITU 신고번호(예: `125520116`)를
그대로 PK로 사용했습니다. 실제 원본 데이터의 식별자를 그대로 살려서 "이 데이터가 가짜가 아니라
실제 신고 기록"이라는 걸 유지하기 위한 선택입니다.

**1:N 관계란?**: "한쪽은 1개, 다른 쪽은 여러 개"로 연결되는 관계입니다.
이 과제에는 1:N 관계가 3개 있습니다.

| 1 (부모) | N (자식) | 의미 |
|---|---|---|
| `notice` 1건 | `geo` 여러 줄 (실제로는 1줄) | 정지궤도 신고 1건에는 궤도 위치 정보가 있다 |
| `notice` 1건 | `orbit` 여러 줄 | 비정지궤도 신고 1건에는 궤도면이 여러 개(11개, 15개 등) 있을 수 있다 |
| `notice` 1건 | `freq` 여러 줄 | 신고 1건에는 주파수 대역이 여러 개 딸려 있다 |

**말로 설명하는 예시**: "한국이 신고한 KOREASAT-116K-2(notice.ntc_id=125520116)는 geo 테이블에
궤도 경도 116°E로 1줄 연결돼 있고, freq 테이블에는 이 신고에 딸린 주파수 대역 3개
(10950~10955MHz, 10950~11000MHz, 11000~11050MHz)가 붙어 있습니다(`results/07_조인INNER3.txt`).
이렇게 번호(FK)로 표를 이어 붙이면, 표를 나눠도 정보가 끊기지 않고 다시 합칠 수 있습니다."

## 4. SELECT / INSERT / UPDATE / DELETE를 언제 쓰는지 설명

| 명령어 | 언제 쓰는가 | 이 과제에서 실제로 쓴 예 |
|---|---|---|
| `SELECT` | 이미 있는 데이터를 "조회"만 할 때 | `queries.sql`의 15개 쿼리 대부분 |
| `INSERT` | 새 데이터를 표에 "추가"할 때 | `data.sql`에서 신고/궤도/주파수 데이터 입력 |
| `UPDATE` | 이미 있는 데이터의 값을 "수정"할 때 | `queries.sql`에서 심사 중인 베트남(VTN) 신고를 처리 완료 상태로 승인 |
| `DELETE` | 이미 있는 데이터를 "삭제"할 때 | `queries.sql`에서 초광대역(1GHz 이상) 주파수 대역을 정리 |

**아주 쉬운 비유**: SELECT는 "찾아보기", INSERT는 "새로 쓰기", UPDATE는 "고쳐쓰기", DELETE는 "지우기"입니다.

주의해서 설명할 점: UPDATE와 DELETE는 `WHERE` 조건을 빼먹으면 표 전체가 수정/삭제되므로,
항상 "어떤 줄만 바꿀지" 조건을 먼저 확인하고 실행해야 합니다.

```sql
-- WHERE로 "베트남이 신고했고 아직 심사 중(20)인 것만" 골라서 수정
UPDATE notice
SET st_cur = 50
WHERE adm = 'VTN' AND st_cur = 20;
```

## 5. JOIN과 GROUP BY로 "연결된 데이터를 한 번에 뽑는 방법" 설명

**JOIN이란?**: 표 여러 개를 번호(FK)로 이어 붙여서, 한 번의 조회로 여러 표의 정보를 같이 보는 것입니다.

`queries.sql`의 실제 예시 (위성망 이름과 신고국, 궤도 경도를 같이 보여주는 쿼리):

```sql
SELECT n.ntc_id, n.adm, g.sat_name, g.long_nom
FROM notice n
INNER JOIN geo g ON n.ntc_id = g.ntc_id
ORDER BY g.long_nom;
```

**말로 설명하면**: "notice 표는 위성 이름이나 궤도 경도를 모르고 ntc_id 번호만 갖고 있습니다.
그래서 geo 표와 '번호가 같은 줄끼리' 이어 붙여서, 신고 목록에 위성 이름과 궤도 위치까지 같이 보이게 만든 것입니다."

**INNER JOIN과 LEFT JOIN의 차이** (평가자가 자주 묻는 부분):
- `INNER JOIN`: 양쪽 표에 모두 값이 있는 경우만 보여줍니다.
- `LEFT JOIN`: 왼쪽 표는 전부 보여주고, 오른쪽에 연결된 값이 없으면 빈 값(NULL)으로 보여줍니다.

실제로 쓴 LEFT JOIN 예시 (모든 신고에 대해 정지궤도 위치 정보 유무를 확인):

```sql
SELECT n.ntc_id, n.adm, n.ntc_type, g.sat_name, g.long_nom
FROM notice n
LEFT JOIN geo g ON n.ntc_id = g.ntc_id
ORDER BY n.ntc_id;
```

**GROUP BY란?**: 데이터를 "같은 값끼리 묶어서" 개수/합계/평균 같은 요약값을 구하는 것입니다.
위 LEFT JOIN 쿼리 결과(`results/08_조인LEFT1.txt`)를 보면, 비정지궤도(NGSO) 신고인
`125520122`, `125520134`는 geo 정보가 없어서 `sat_name`, `long_nom`이 빈 값(NULL)으로
나옵니다. 만약 `INNER JOIN`을 썼다면 이 2건은 아예 결과에서 빠졌을 것입니다 — 이게 "비정지궤도
신고에는 애초에 geo 정보가 없다"는 사실을 있는 그대로 보여주는 LEFT JOIN의 역할입니다.

## 6. 실무 요구(검색/정렬/집계/랭킹)를 SQL로 푸는 감각 설명

| 실무 요구 | SQL 표현 | 이 과제의 예시 |
|---|---|---|
| 검색(조건에 맞는 것만 찾기) | `WHERE` | 한국(KOR)이 신고한 위성망만 조회 (`기본조회 2`) |
| 정렬(순서대로 나열) | `ORDER BY` | 최근 접수된 신고부터 정렬 (`기본조회 1`) |
| 랭킹(상위 N개만 보기) | `ORDER BY` + `LIMIT` | 최근 접수된 GSO 신고 TOP 5 (`기본조회 1`) |
| 집계(개수/합계/평균 구하기) | `GROUP BY` + `COUNT`/`SUM`/`AVG` | 신고국별 신고 건수 (`집계 1`) |

**말로 설명하는 예시**: "가장 최근에 접수된 정지궤도 신고 5건을 뽑아라"는 요구가 오면,
"접수일 기준으로 내림차순 정렬(`ORDER BY d_rcv DESC`)하고, 위에서 5개만 자른다(`LIMIT 5`)"로 바꿔서 풀면 됩니다.

```sql
SELECT ntc_id, adm, d_rcv
FROM notice
WHERE ntc_type = 'G'
ORDER BY d_rcv DESC
LIMIT 5;
```

## 7. 인덱스가 왜 필요한지, 어떤 컬럼에 적용하면 좋은지 설명

**인덱스란?**: 책의 "찾아보기(색인)"처럼, 특정 컬럼으로 자주 검색한다면 미리 정렬된 목록을 만들어둬서
데이터를 더 빨리 찾게 해주는 것입니다.

이 과제에서 적용한 인덱스:

```sql
CREATE INDEX idx_freq_ntc_id ON freq(ntc_id);
CREATE INDEX idx_orbit_ntc_id ON orbit(ntc_id);
```

**왜 이 컬럼에 걸었나?**: `freq`는 4개 테이블 중 행이 가장 많고(신고당 여러 대역), "이 신고
(ntc_id)에 어떤 주파수 대역이 딸렸는지"를 자주 조회하기 때문입니다. 인덱스가 없으면 매번 표
전체를 처음부터 끝까지 훑어야 하지만(Full Scan), 인덱스가 있으면 바로 해당 ntc_id 위치로
찾아갈 수 있습니다.

실제로 `EXPLAIN QUERY PLAN`으로 확인한 결과(`results/15_인덱스.txt`):

```
QUERY PLAN
|--SEARCH n USING INTEGER PRIMARY KEY (rowid=?)
`--SEARCH f USING INDEX idx_freq_ntc_id (ntc_id=?)
```

`SEARCH ... USING INDEX`라고 나온 것이 "표 전체를 훑지 않고 인덱스를 이용해 바로 찾아갔다"는 증거입니다.

**주의할 점**: 인덱스는 조회는 빠르게 해주지만, 데이터를 추가/수정할 때마다 인덱스도 같이 갱신해야 하므로
모든 컬럼에 무조건 걸면 오히려 느려질 수 있습니다. 그래서 "자주 검색 조건으로 쓰이는 컬럼"에만 선택적으로 적용합니다.

## 8. 제약조건(NOT NULL, UNIQUE, FK) 설명

| 제약조건 | 의미 | 이 과제에서 적용한 곳 |
|---|---|---|
| `NOT NULL` | 이 값은 반드시 있어야 한다(빈 값 금지) | `notice.adm`, `notice.ntc_type`, `notice.d_rcv`, `geo.sat_name`, `freq.emi_rcp` 등 |
| `UNIQUE` | 이 값은 표 안에서 중복되면 안 된다 | `geo.sat_name` |
| `FOREIGN KEY` | 이 값은 반드시 부모 표에 실제로 존재하는 값이어야 한다 | `geo.ntc_id`, `orbit.ntc_id`, `freq.ntc_id → notice.ntc_id` |

**FK가 실제로 막아주는 상황 설명**: 만약 `geo`에 존재하지 않는 `ntc_id`(예: 999999999)를 넣으려고 하면
아래처럼 에러가 나면서 저장이 거부됩니다. (`보너스.md` 2번 항목에서 실제로 재현하고 캡처함)

```
Error: FOREIGN KEY constraint failed
```

→ 이게 왜 중요하냐면, "존재하지도 않는 신고에 궤도/주파수 정보가 달린 것처럼" 데이터가
잘못 저장되는 것을 DB가 스스로 막아주기 때문입니다. SQLite는 기본적으로 이 검사를 꺼둔
상태라서, `schema.sql` 맨 위에 `PRAGMA foreign_keys = ON;`을 반드시 넣어야 FK 제약이
실제로 동작합니다.

## 9. 서브쿼리 설명

**서브쿼리란?**: 쿼리 안에 또 다른 쿼리를 넣어서, "먼저 조회한 결과를 조건으로 다시 쓰는" 방법입니다.

실제 예시 (전체 평균보다 넓은 주파수 대역 찾기):

```sql
SELECT ntc_id, emi_rcp, freq_min, freq_max, bdwdth
FROM freq
WHERE bdwdth > (SELECT AVG(bdwdth) FROM freq)
ORDER BY bdwdth DESC;
```

**말로 설명하면**: "안쪽 쿼리(`SELECT AVG(bdwdth) FROM freq`)가 먼저 '전체 주파수 대역의
평균 대역폭'이라는 숫자 하나를 계산하고, 바깥쪽 쿼리가 '그 평균보다 넓은(bdwdth > 평균) 대역'만
골라낸다"는 2단계 흐름입니다.

**보너스에서 더 다룬 서브쿼리 활용**: `보너스.md` 1번 항목에서는 "GSO 신고만 조회"를
`WHERE ntc_id IN (SELECT ntc_id FROM geo)` 서브쿼리 방식과 INNER JOIN 방식으로 각각 풀어
실행계획까지 비교했습니다. 서브쿼리는 "존재 여부"만 확인할 때 중복 걱정 없이 더 단순하게
동작한다는 걸 `EXPLAIN QUERY PLAN`으로 직접 확인했습니다.

## 10. 왜 이 주제(위성 궤도/주파수)를 선택했는지 설명

- 실제 위성망 등록 DB_3075 공개 데이터를 발췌해서 만들었기 때문에, 가상의 예시 데이터보다 "실제로 쓰이는
  DB가 어떻게 생겼는지"를 훨씬 현실감 있게 보여줄 수 있습니다.
- 1:N 관계가 자연스럽게 3개(notice→geo, notice→orbit, notice→freq) 나와서 과제 요구사항
  (1:N 관계 2개 이상)을 충분히 만족합니다.
- 정지궤도(GSO)/비정지궤도(NGSO)라는 "서로 배타적인 두 종류"가 있어서, `geo`와 `orbit`이
  같은 부모(notice)를 가리키면서도 항상 둘 중 하나만 채워지는 구조를 만들 수 있었고, 이
  덕분에 LEFT JOIN의 필요성(NULL이 실제로 의미 있게 발생하는 상황)을 억지 없이 자연스럽게
  보여줄 수 있었습니다.
- "신고 상태(처리중/확정)"가 있어서 UPDATE, DELETE, 집계 쿼리를 현실적인 시나리오로 만들 수 있었습니다.

## 11. 발표 또는 평가 때 사용할 짧은 요약

> "엑셀 한 장 대신, 신고·궤도위치·궤도면·주파수로 표를 나누고 번호(PK/FK)로 서로 연결했습니다.
> 실제 ITU 위성망 신고 데이터를 발췌해서 썼기 때문에 KOREASAT처럼 실존하는 위성 이름과 실제
> 주파수 대역이 그대로 들어 있습니다. SELECT/JOIN/GROUP BY로 필요한 정보를 조합해서 뽑고,
> 서브쿼리로 '평균보다 넓은 대역'처럼 조건을 좁혀가는 조회도 만들었습니다. UPDATE/DELETE로
> 신고 상태와 데이터를 정리했고, 자주 조회하는 컬럼(ntc_id)에는 인덱스를 걸어서 조회 속도를
> 실행계획으로 확인했습니다. 보너스 과제 3개(JOIN vs 서브쿼리 비교, FK 위반 재현, 미니
> 리포트)도 전부 실제로 수행했습니다."

### 항목 2 — 테이블 설계 이해 질문

**Q1. 테이블을 어떻게 나눴는지, 각 테이블의 역할은?**

위성망 신고라는 하나의 절차를 "누가 신고했나 / 어디에(궤도) / 뭘 쓰나(주파수)"로 쪼갰습니다.

| 테이블 | 역할 | 한 줄 답변 |
|---|---|---|
| `notice` | 누가(신고국·신고일) | 이 신고가 언제, 어느 나라가, 정지/비정지궤도 중 무엇으로 했는지만 담습니다 |
| `geo` | 어디에(정지궤도 위치) | 정지궤도 신고만 갖는 "궤도 경도(°)" 정보를 담습니다 |
| `orbit` | 어디에(비정지궤도 궤도면) | 비정지궤도 신고 하나에 여러 개 있을 수 있는 "궤도면별 위성 수·경사각" 정보를 담습니다 |
| `freq` | 뭘 쓰나(주파수) | "이 신고가 몇~몇 MHz 대역을 쓰겠다고 신고했는지"를 담습니다 |

**Q2. FK로 연결한 1:N 관계가 실제 도메인에서 어떤 의미인지 예시로 보여달라고 하면?**

`results/05_조인INNER1.txt`를 펴서 이렇게 설명합니다: "notice.ntc_id=125520116(한국,
KOR)이 geo 테이블에 KOREASAT-116K-2라는 이름과 116°E라는 궤도 경도로 1줄 연결돼 있습니다
— 이게 `notice(1) → geo(N)`입니다. 그리고 `results/06_조인INNER2.txt`를 보면 비정지궤도
신고 125520122(LUX)는 orbit 테이블에 궤도면 11개가 딸려 있습니다 — 이게 `notice(1) →
orbit(N)`입니다. 즉 '신고 하나에 궤도 정보나 주파수 대역이 여러 개 붙을 수 있다'는 실제
위성망 신고 절차를 그대로 테이블 관계로 옮긴 것입니다."

**Q3. 컬럼 타입을 왜 그렇게 선택했는가?**

| 컬럼 예시 | 선택한 타입 | 이유 |
|---|---|---|
| `notice.adm`, `geo.sat_name`, `freq.emi_rcp` | `TEXT` | 길이가 정해지지 않은 문자/코드값이고, 산술 연산 대상이 아님 |
| `orbit.nbr_sat_pl`, `notice.st_cur` | `INTEGER` | 위성 개수·상태 코드처럼 정수 연산/비교가 필요함 |
| `geo.long_nom`, `freq.freq_min/freq_max`, `orbit.inclin_ang` | `REAL` | 궤도 경도(-180~180)나 주파수(MHz)는 소수점이 있는 실수값이라 정확한 비교·정렬을 위해 REAL로 선언 |
| `notice.d_rcv` | `DATE` | "이후/이전" 같은 날짜 비교와 정렬을 SQL이 날짜로 이해하게 하려고 문자열이 아니라 DATE로 선언 |

**Q4. 인덱스를 어떤 컬럼에 걸었고, 왜 그 컬럼이어야 하는가?**

`freq.ntc_id`와 `orbit.ntc_id`에 걸었습니다(`schema.sql`의
`CREATE INDEX idx_freq_ntc_id ON freq(ntc_id);`). 이유는 "이 신고에 어떤 주파수 대역이
딸렸는지"를 조회하는 `WHERE ntc_id = ?` 형태의 쿼리가 가장 자주 일어날 조회 패턴이기
때문입니다. `freq`는 4개 테이블 중 행이 가장 많아서(50행) 인덱스 효과가 가장 뚜렷합니다.
`results/15_인덱스.txt`의 `EXPLAIN QUERY PLAN` 결과에
`SEARCH f USING INDEX idx_freq_ntc_id (ntc_id=?)`라고 찍힌 것이 "인덱스를 실제로 탔다"는
직접적인 증거입니다.

### 항목 3 — 개념 이해(DB 기초) 질문

**Q1. 데이터베이스가 엑셀과 무엇이 다른가?**

신고에 딸린 모든 궤도·주파수 정보에 자동으로 반영됩니다 — 이게 '데이터가 얼마나 많냐'가

"`geo` 테이블을 예로 들면, `id`는 PK로 '이 궤도 위치 정보 자체를 구별하는 고유 번호'이고,
`ntc_id`는 FK로 '이 궤도 정보가 어떤 신고에 딸린 것인지, notice 테이블의 몇 번을
가리키는지' 나타냅니다. PK는 '나는 누구인가'를 나타내고 FK는 '나는 누구와 연결되어
있는가'를 나타낸다고 구분해서 설명합니다." (`schema.sql`의 `geo` 테이블 정의를 보여주며 설명)

**Q3. INNER JOIN과 LEFT JOIN의 차이를 실행 결과를 보며 설명할 수 있는가?**

`results/05_조인INNER1.txt`와 `results/08_조인LEFT1.txt`를 나란히 펴놓고 비교합니다.

했다면 이 2건은 통째로 결과에서 사라졌을 겁니다 — 그게 두 JOIN의 핵심 차이입니다."

**Q4. GROUP BY와 집계 함수(COUNT/SUM/AVG)가 어떻게 동작하는지 쿼리 결과를 보며 설명하면?**

`results/09_집계1.txt`(COUNT), `results/10_집계2.txt`(COUNT+AVG),
`results/11_집계3.txt`(SUM) 세 개를 순서대로 보여주며 설명합니다.

- **COUNT** (`집계 1`): "신고국(adm)으로 GROUP BY 한 다음, 각 나라가 신고를 몇 건 했는지
  `COUNT`로 셉니다. 프랑스(F)가 5건으로 가장 많습니다."
- **COUNT + AVG** (`집계 2`): "신고번호(ntc_id)로 GROUP BY 해서, 신고 하나당 주파수 대역이
  몇 개 딸렸는지(`COUNT`)와 그 대역들의 평균 대역폭(`AVG`)을 같이 구합니다."
- **SUM** (`집계 3`): "비정지궤도 신고번호로 GROUP BY 해서, 그 신고에 딸린 모든 궤도면의

한 줄 요약: "GROUP BY는 '같은 값끼리 한 무더기로 묶는' 역할만 하고, 그 무더기 안에서

### 항목 4 — 심화/회고 질문

**Q1. 가장 복잡한 쿼리를 골라 단계별로 설명하면?**

`조인-INNER 3`(`results/07_조인INNER3.txt`)을 가장 복잡한 쿼리로 꼽습니다.

```sql
SELECT n.adm, g.sat_name, f.emi_rcp, f.freq_min, f.freq_max
FROM notice n
INNER JOIN geo g ON n.ntc_id = g.ntc_id
INNER JOIN freq f ON n.ntc_id = f.ntc_id
WHERE n.adm = 'KOR';
```

단계별 설명:
1. **FROM notice n** — 먼저 전체 신고 17건을 기준(첫 번째 표)으로 놓습니다.
2. **INNER JOIN geo g ON n.ntc_id = g.ntc_id** — notice와 geo를 ntc_id로 이어 붙여서,
   geo 정보가 있는(=정지궤도인) 신고만 남깁니다. 이 시점에 비정지궤도 신고 2건은 이미
   빠집니다.
3. **INNER JOIN freq f ON n.ntc_id = f.ntc_id** — 같은 ntc_id로 freq까지 한 번 더 이어
   붙입니다. 한 신고에 주파수 대역이 3개 딸려 있으면, 이 단계에서 그 신고가 3줄로
   늘어납니다(1:N 관계이기 때문).
4. **WHERE n.adm = 'KOR'** — 마지막으로 신고국이 한국인 것만 골라냅니다.
5. 결과: KOREASAT-116K-2와 KOREASAT-78W-K, 두 위성망 각각의 주파수 대역 3개씩,
   총 6줄이 나옵니다(`results/07_조인INNER3.txt`).

**Q2. 미션 수행 중 가장 어려웠던 부분과 해결 방법은?**

"가장 어려웠던 부분은 실제 원본 데이터(위성망 등록 DB_3075, ~80개 테이블 규모)에서 과제에 맞는
규모로 데이터를 추려내는 것이었습니다. `freq` 테이블 하나가 원본에는 5만 건 넘게
있어서, 그대로 쓰면 과제 범위를 훨씬 넘어섰습니다. 신고(notice) 17건을 먼저 고정하고,
그 신고들에 딸린 geo/orbit/freq만 골라서(각 신고당 주파수 대역 2~3개로 제한) 10~50행
규모로 맞췄습니다. 두 번째로 어려웠던 부분은 Windows PowerShell에서 `Get-Content`로

실제 생성된 컬럼을 확인해서 원인을 찾았고, `Get-Content -Encoding UTF8`을 명시해서

### 항목 5 — 보너스 과제

과거 카페 주문 제출 때는 시간 부족으로 보너스 과제를 포함하지 못했지만, 이번 위성
궤도/주파수 제출에서는 **3개 모두 실제로 실행하고 `보너스.md`에 결과를 기록**했습니다.

**① JOIN vs 서브쿼리 비교**

"GSO 신고만 조회"라는 같은 요구를 두 방식으로 풀었습니다.

```sql
-- JOIN 버전
SELECT DISTINCT n.ntc_id, n.adm, n.d_rcv
FROM notice n
INNER JOIN geo g ON n.ntc_id = g.ntc_id
ORDER BY n.ntc_id;

-- 서브쿼리 버전
SELECT n.ntc_id, n.adm, n.d_rcv
FROM notice n
WHERE n.ntc_id IN (SELECT ntc_id FROM geo)
ORDER BY n.ntc_id;
```

결과는 동일(15건)했지만 `EXPLAIN QUERY PLAN`을 비교해보니, JOIN 버전은 중복 제거용
`DISTINCT`와 정렬용 임시 B-TREE가 추가로 필요했던 반면, 서브쿼리 버전은 그런 부가 작업
없이 바로 notice의 PK 순서를 탔습니다. "자식 컬럼까지 같이 가져와야 하면 JOIN, 존재
여부만 필터링하면 서브쿼리가 유리하다"는 걸 직접 확인했습니다.

**② 정합성 깨뜨려보기**

존재하지 않는 `ntc_id`(999999999)로 `geo`에 INSERT를 시도했습니다.

```sql
PRAGMA foreign_keys = ON;
INSERT INTO geo (ntc_id, sat_name, long_nom) VALUES (999999999, 'GHOST-SAT', 100);
```

→ `Error: FOREIGN KEY constraint failed`가 즉시 발생했고, 실제로 데이터가 들어가지
않은 것도 `COUNT(*)`로 확인했습니다. 그 다음 `notice`에 먼저 부모 행을 넣고 나서 같은
INSERT를 재시도하니 정상적으로 들어갔습니다 — "자식을 부모보다 먼저 넣지 마라"는 원칙을
FK 제약이 강제로 지켜준다는 걸 직접 체험했습니다.

   평균 대역폭(565,000kHz)이 압도적으로 넓음 (고용량 피더링크 용도이기 때문)

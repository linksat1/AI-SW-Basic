## 2. 데이터베이스가 "엑셀과 뭐가 다른지" 설명

**아주 쉬운 설명**: 엑셀은 표 하나에 모든 정보를 다 적으려고 해서 같은 내용이 여러 번 반복되지만,
데이터베이스는 정보를 역할별로 나눈 여러 표(테이블)로 쪼개고, 표끼리 "번호(ID)"로 서로 연결합니다.

예를 들어 엑셀 한 장에 "주문번호, 고객이름, 고객번호, 메뉴이름, 가격, 수량"을 전부 적으면,
같은 고객이 여러 번 주문할 때마다 그 고객의 이름과 번호를 매번 다시 적어야 합니다.
이러다가 한 곳에서 이름 철자를 잘못 적으면 데이터가 서로 안 맞게 됩니다.

이 과제에서는 그래서 표를 4개로 나눴습니다.

| 표 | 담는 정보 | 왜 따로 뒀는가 |
|---|---|---|
| `customer` | 고객 정보 (이름, 전화번호) | 고객 정보는 한 번만 저장하고, 여러 주문에서 재사용 |
| `menu` | 메뉴 정보 (이름, 가격, 카테고리) | 메뉴 가격이 바뀌어도 메뉴 표 한 줄만 수정하면 됨 |
| `orders` | 주문 1건의 정보 (누가, 언제, 상태) | "어떤 주문이 있었는지"만 담당 |
| `order_item` | 주문 안에 담긴 메뉴들 (몇 개 시켰는지) | 주문 1건에 메뉴가 여러 개 담길 수 있어서 따로 분리 |

→ **핵심 한 줄**: "같은 정보를 여러 번 적지 않고, 표를 나눈 뒤 번호로 연결해서 관리하는 것"이 엑셀과 DB의 근본적인 차이입니다.

## 3. PK/FK가 무엇이고, 1:N 관계가 데이터를 어떻게 연결하는지 설명

**PK(Primary Key, 기본키)**: 그 표에서 각 줄을 구별하는 "고유 번호표"입니다. 중복되면 안 됩니다.
**FK(Foreign Key, 외래키)**: 다른 표의 PK를 그대로 가져와서 "이 줄은 저 표의 몇 번과 연결된다"고 표시하는 값입니다.

`schema.sql`에서 실제로 쓴 부분:

```sql
CREATE TABLE customer (
    id    INTEGER PRIMARY KEY AUTOINCREMENT,  -- customer의 PK
    ...
);

CREATE TABLE orders (
    id          INTEGER PRIMARY KEY AUTOINCREMENT, -- orders의 PK
    customer_id INTEGER NOT NULL,                  -- customer를 가리키는 FK
    ...
    FOREIGN KEY (customer_id) REFERENCES customer(id)
);
```

**1:N 관계란?**: "한쪽은 1개, 다른 쪽은 여러 개"로 연결되는 관계입니다.
이 과제에는 1:N 관계가 3개 있습니다.

| 1 (부모) | N (자식) | 의미 |
|---|---|---|
| `customer` 1명 | `orders` 여러 건 | 고객 한 명이 주문을 여러 번 할 수 있다 |
| `orders` 1건 | `order_item` 여러 줄 | 주문 1건에 메뉴가 여러 개 담길 수 있다 |
| `menu` 1개 | `order_item` 여러 줄 | 메뉴 하나가 여러 주문에 반복해서 팔릴 수 있다 |

**말로 설명하는 예시**: "김도윤 고객(customer.id=1)이 주문을 2번 했는데(orders 테이블에 customer_id=1인 줄이 2개),
그 중 1번 주문 안에는 아메리카노 2잔과 초코케이크 1개가 담겨 있습니다(order_item 테이블에 order_id=1인 줄이 2개).
이렇게 번호(FK)로 표를 이어 붙이면, 표를 나눠도 정보가 끊기지 않고 다시 합칠 수 있습니다."

## 4. SELECT / INSERT / UPDATE / DELETE를 언제 쓰는지 설명

| 명령어 | 언제 쓰는가 | 이 과제에서 실제로 쓴 예 |
|---|---|---|
| `SELECT` | 이미 있는 데이터를 "조회"만 할 때 | `queries.sql`의 15개 쿼리 대부분 |
| `INSERT` | 새 데이터를 표에 "추가"할 때 | `data.sql`에서 고객/메뉴/주문 데이터 입력 |
| `UPDATE` | 이미 있는 데이터의 값을 "수정"할 때 | `queries.sql`에서 `주문접수` 상태를 `제조중`으로 변경 |
| `DELETE` | 이미 있는 데이터를 "삭제"할 때 | `queries.sql`에서 취소된 주문을 삭제 |

**아주 쉬운 비유**: SELECT는 "찾아보기", INSERT는 "새로 쓰기", UPDATE는 "고쳐쓰기", DELETE는 "지우기"입니다.

주의해서 설명할 점: UPDATE와 DELETE는 `WHERE` 조건을 빼먹으면 표 전체가 수정/삭제되므로,
항상 "어떤 줄만 바꿀지" 조건을 먼저 확인하고 실행해야 합니다.

```sql
-- WHERE로 "주문접수 상태인 것만" 골라서 수정
UPDATE orders
SET status = '제조중'
WHERE status = '주문접수';
```

## 5. JOIN과 GROUP BY로 "연결된 데이터를 한 번에 뽑는 방법" 설명

**JOIN이란?**: 표 여러 개를 번호(FK)로 이어 붙여서, 한 번의 조회로 여러 표의 정보를 같이 보는 것입니다.

`queries.sql`의 실제 예시 (주문마다 고객 이름을 같이 보여주는 쿼리):

```sql
SELECT o.id AS 주문번호, c.name AS 고객, o.order_date, o.status
FROM orders o
INNER JOIN customer c ON o.customer_id = c.id
ORDER BY o.order_date;
```

**말로 설명하면**: "orders 표는 고객 이름을 모르고 customer_id 번호만 갖고 있습니다.
그래서 customer 표와 '번호가 같은 줄끼리' 이어 붙여서, 주문 목록에 고객 이름까지 같이 보이게 만든 것입니다."

**INNER JOIN과 LEFT JOIN의 차이** (평가자가 자주 묻는 부분):
- `INNER JOIN`: 양쪽 표에 모두 값이 있는 경우만 보여줍니다.
- `LEFT JOIN`: 왼쪽 표는 전부 보여주고, 오른쪽에 연결된 값이 없으면 빈 값(NULL)으로 보여줍니다.

실제로 쓴 LEFT JOIN 예시 (주문을 한 번도 안 한 고객도 0건으로 포함해서 보여주기):

```sql
SELECT c.name, COUNT(o.id) AS 주문횟수
FROM customer c
LEFT JOIN orders o ON c.id = o.customer_id
GROUP BY c.id, c.name
ORDER BY 주문횟수 DESC;
```

**GROUP BY란?**: 데이터를 "같은 값끼리 묶어서" 개수/합계/평균 같은 요약값을 구하는 것입니다.
위 쿼리에서는 "고객 이름별로" 묶어서 각 고객이 몇 번 주문했는지(`COUNT`) 셌습니다.
만약 `LEFT JOIN`을 안 쓰고 `INNER JOIN`을 썼다면, 주문을 한 번도 안 한 고객(한도현)은 결과에서 아예 빠졌을 것입니다.
실제로 `results/08_조인LEFT1.txt`를 보면 한도현의 주문횟수가 `0`으로 정상적으로 표시됩니다.

## 6. 실무 요구(검색/정렬/집계/랭킹)를 SQL로 푸는 감각 설명

| 실무 요구 | SQL 표현 | 이 과제의 예시 |
|---|---|---|
| 검색(조건에 맞는 것만 찾기) | `WHERE` | 커피 카테고리 메뉴만 조회 (`기본조회 2`) |
| 정렬(순서대로 나열) | `ORDER BY` | 가장 비싼 메뉴 순으로 정렬 (`기본조회 4`) |
| 랭킹(상위 N개만 보기) | `ORDER BY` + `LIMIT` | 가장 비싼 메뉴 TOP 3 (`기본조회 4`) |
| 집계(개수/합계/평균 구하기) | `GROUP BY` + `COUNT`/`SUM`/`AVG` | 메뉴별 판매 수량 합계 (`집계 1`) |

**말로 설명하는 예시**: "가장 비싼 메뉴 3개를 뽑아라"는 요구가 오면,
"가격 기준으로 내림차순 정렬(`ORDER BY price DESC`)하고, 위에서 3개만 자른다(`LIMIT 3`)"로 바꿔서 풀면 됩니다.

```sql
SELECT name, price
FROM menu
ORDER BY price DESC
LIMIT 3;
```

## 7. 인덱스가 왜 필요한지, 어떤 컬럼에 적용하면 좋은지 설명

**인덱스란?**: 책의 "찾아보기(색인)"처럼, 특정 컬럼으로 자주 검색한다면 미리 정렬된 목록을 만들어둬서
데이터를 더 빨리 찾게 해주는 것입니다.

이 과제에서 적용한 인덱스:

```sql
CREATE INDEX idx_order_item_order_id ON order_item(order_id);
```

**왜 이 컬럼에 걸었나?**: `order_item` 표에서 "이 주문(order_id)에 어떤 메뉴가 담겼는지"를
자주 조회하기 때문입니다. 인덱스가 없으면 매번 표 전체를 처음부터 끝까지 훑어야 하지만(Full Scan),
인덱스가 있으면 바로 해당 order_id 위치로 찾아갈 수 있습니다.

실제로 `EXPLAIN QUERY PLAN`으로 확인한 결과(`results/15_인덱스.txt`):

```
QUERY PLAN
`--SEARCH order_item USING INDEX idx_order_item_order_id (order_id=?)
```

`SEARCH ... USING INDEX`라고 나온 것이 "표 전체를 훑지 않고 인덱스를 이용해 바로 찾아갔다"는 증거입니다.

**주의할 점**: 인덱스는 조회는 빠르게 해주지만, 데이터를 추가/수정할 때마다 인덱스도 같이 갱신해야 하므로
모든 컬럼에 무조건 걸면 오히려 느려질 수 있습니다. 그래서 "자주 검색 조건으로 쓰이는 컬럼"에만 선택적으로 적용합니다.

## 8. 제약조건(NOT NULL, UNIQUE, FK) 설명

| 제약조건 | 의미 | 이 과제에서 적용한 곳 |
|---|---|---|
| `NOT NULL` | 이 값은 반드시 있어야 한다(빈 값 금지) | `customer.name`, `customer.phone`, `orders.customer_id` 등 |
| `UNIQUE` | 이 값은 표 안에서 중복되면 안 된다 | `customer.phone`, `menu.name` |
| `FOREIGN KEY` | 이 값은 반드시 부모 표에 실제로 존재하는 값이어야 한다 | `orders.customer_id → customer.id` 등 |

**FK가 실제로 막아주는 상황 설명**: 만약 `orders`에 존재하지 않는 `customer_id`(예: 999번)를 넣으려고 하면
아래처럼 에러가 나면서 저장이 거부됩니다.

```
FOREIGN KEY constraint failed
```

→ 이게 왜 중요하냐면, "있지도 않은 고객이 주문한 것처럼" 데이터가 잘못 저장되는 것을 DB가 스스로 막아주기 때문입니다.
SQLite는 기본적으로 이 검사를 꺼둔 상태라서, `schema.sql` 맨 위에 `PRAGMA foreign_keys = ON;`을 반드시 넣어야
FK 제약이 실제로 동작합니다.

## 9. 서브쿼리 설명

**서브쿼리란?**: 쿼리 안에 또 다른 쿼리를 넣어서, "먼저 조회한 결과를 조건으로 다시 쓰는" 방법입니다.

실제 예시 (주문을 한 번도 안 한 고객 찾기):

```sql
SELECT name, phone
FROM customer
WHERE id NOT IN (SELECT DISTINCT customer_id FROM orders);
```

**말로 설명하면**: "안쪽 쿼리(`SELECT DISTINCT customer_id FROM orders`)가 먼저 '주문을 한 적 있는 고객 번호 목록'을 만들고,
바깥쪽 쿼리가 '그 목록에 없는(NOT IN) 고객'만 골라낸다"는 2단계 흐름입니다.

**JOIN과 차이**: 같은 결과를 LEFT JOIN + `WHERE o.id IS NULL`로도 만들 수 있는데,
서브쿼리는 "이 조건에 맞는 목록"을 먼저 따로 구한 뒤 비교한다는 점이 다릅니다.

## 10. 왜 이 주제(카페 주문)를 선택했는지 설명

- 실생활에서 이해하기 쉬운 도메인이라 테이블 간 관계(고객→주문→주문상세←메뉴)를 직관적으로 설명할 수 있습니다.
- 1:N 관계가 자연스럽게 3개(customer→orders, orders→order_item, menu→order_item) 나와서
  과제 요구사항(1:N 관계 2개 이상)을 충분히 만족합니다.
- "주문 상태(대기/제조중/완료/취소)"가 있어서 UPDATE, DELETE, 집계 쿼리를 현실적인 시나리오로 만들 수 있었습니다.

## 11. 발표 또는 평가 때 사용할 짧은 요약

> "엑셀 한 장 대신, 고객·메뉴·주문·주문상세로 표를 나누고 번호(PK/FK)로 서로 연결했습니다.
> 그래서 고객 정보나 메뉴 가격은 한 곳에만 저장하고, 여러 주문에서 재사용할 수 있습니다.
> SELECT/JOIN/GROUP BY로 필요한 정보를 조합해서 뽑고, 서브쿼리로 '주문 이력이 없는 고객'처럼
> 조건을 좁혀가는 조회도 만들었습니다. UPDATE/DELETE로 주문 상태를 관리했고,
> 자주 조회하는 컬럼(order_id)에는 인덱스를 걸어서 조회 속도를 확인했습니다."

## 12. 평가 질문 대비 답변 자료

아래 답변은 외워서 말하기보다, 본인 말투로 자연스럽게 설명하는 연습용입니다.

### 항목 1. 설계 확인 질문

**Q1. 왜 테이블을 4개로 나눴는가? 하나의 표로 합치면 안 되는가?**

합칠 수는 있지만, 그러면 고객 이름/전화번호가 그 고객의 주문 수만큼 반복해서 저장됩니다.
전화번호가 바뀌면 모든 주문 줄을 다 찾아서 고쳐야 하니 실수하기 쉽습니다.
표를 나누고 번호(FK)로 연결하면, 고객 정보는 `customer` 표 한 줄만 고치면 모든 주문에 자동으로 반영됩니다.

**Q2. 1:N 관계가 어디에 있는지 구체적으로 짚을 수 있는가?**

`customer`(1) → `orders`(N): 고객 한 명이 주문을 여러 건 가질 수 있습니다.
`orders`(1) → `order_item`(N): 주문 한 건에 메뉴가 여러 줄 담길 수 있습니다.
`menu`(1) → `order_item`(N): 메뉴 하나가 여러 주문에 반복해서 등장할 수 있습니다.
`제출/schema.sql`의 `FOREIGN KEY` 구문 3곳이 이 관계를 코드로 표현한 부분입니다.

**Q3. PK와 FK를 어떻게 구별해서 설계했는가?**

각 표마다 자기 자신을 구분하는 `id` 컬럼을 PK로 뒀고, "N" 쪽 표(자식 표)에는 부모 표의 PK를 그대로
가져온 컬럼(`customer_id`, `order_id`, `menu_id`)을 FK로 추가했습니다.

---

### 항목 2. 데이터 무결성 질문

**Q1. NOT NULL과 UNIQUE는 각각 어디에, 왜 적용했는가?**

`customer.phone`과 `menu.name`에는 UNIQUE를 걸어서 같은 전화번호나 같은 메뉴 이름이 중복 저장되지
않게 했습니다. `customer.name`, `orders.customer_id` 등 핵심 값에는 NOT NULL을 걸어서 빈 값으로
저장되는 것을 막았습니다.

**Q2. FK 제약이 실제로 동작하는지 어떻게 확인했는가?**

`data.sql`에서 항상 부모 표(`customer`, `menu`)에 먼저 데이터를 넣고, 그다음 자식 표(`orders`, `order_item`)에
데이터를 넣도록 순서를 맞췄습니다. 만약 존재하지 않는 고객 번호로 주문을 넣으려 하면
`FOREIGN KEY constraint failed` 에러가 나서 저장이 거부되는 것을 직접 확인했습니다.

**Q3. 데이터를 넣는 순서가 왜 중요한가?**

자식 표(`orders`, `order_item`)의 FK 값은 반드시 부모 표에 이미 있는 값이어야 하기 때문입니다.
부모 데이터가 없는 상태에서 자식 데이터부터 넣으면 참조할 대상이 없어서 에러가 납니다.

---

### 항목 3. 쿼리 작성 질문

**Q1. INNER JOIN과 LEFT JOIN을 각각 언제, 왜 사용했는가?**

주문-고객처럼 "무조건 서로 짝이 있는 관계"를 조회할 때는 INNER JOIN을 썼습니다.
반면 "주문이 하나도 없는 고객도 포함해서 보고 싶을 때"는 LEFT JOIN을 썼습니다(`조인-LEFT 1`).
INNER JOIN만 쓰면 주문 이력이 없는 고객(한도현)이 결과에서 통째로 빠지기 때문입니다.

**Q2. GROUP BY를 쓴 쿼리를 하나 골라 어떤 기준으로 묶었는지 설명할 수 있는가?**

`집계 1` 쿼리는 `order_item`과 `menu`를 조인한 뒤, 메뉴 이름(`m.id, m.name`) 기준으로 묶어서
각 메뉴가 총 몇 개 팔렸는지(`SUM(oi.quantity)`) 구했습니다.

**Q3. 서브쿼리를 쓴 이유와, JOIN으로 바꾼다면 어떻게 바꿀 수 있는가?**

"주문 이력이 없는 고객"을 찾을 때, 먼저 주문을 한 적 있는 고객 번호 목록을 안쪽 쿼리로 구하고,
바깥쪽에서 그 목록에 없는 고객만 걸렀습니다. 같은 결과를 `LEFT JOIN customer c ... WHERE o.id IS NULL`
방식으로도 만들 수 있습니다.

**Q4. UPDATE/DELETE를 실행하기 전에 어떤 점을 조심했는가?**

WHERE 조건 없이 실행하면 표 전체가 바뀌므로, 항상 WHERE로 대상 범위를 먼저 좁혔습니다.
DELETE는 `order_item`(자식)을 먼저 지우고 나서 `orders`(부모)를 지웠습니다.
자식 데이터가 남아있는 상태에서 부모를 먼저 지우면 FK 제약에 걸려 삭제가 거부되기 때문입니다.

### 항목 4. 성능/설계 의도 질문

**Q1. 인덱스를 만든 컬럼과 이유는?**

`order_item.order_id`에 인덱스를 만들었습니다. "이 주문에 어떤 메뉴가 담겼는지" 조회하는 일이
많을 것으로 예상했기 때문입니다. `EXPLAIN QUERY PLAN` 결과에서 실제로 인덱스를 타는 것을 확인했습니다.

**Q2. 인덱스를 아무 컬럼에나 걸면 안 되는 이유는?**

인덱스는 조회는 빠르게 해주지만, 데이터가 추가/수정될 때마다 인덱스도 같이 갱신해야 해서
쓰기 작업은 오히려 느려질 수 있습니다. 그래서 자주 검색 조건(WHERE, JOIN 조건)으로 쓰이는
컬럼에만 선택적으로 적용해야 합니다.

**Q3. 왜 SQLite를 선택했는가?**

서버 설치 없이 파일 하나로 바로 실행할 수 있어서, SQL 문법과 관계 설계 자체에 집중하기에
적합했기 때문입니다. `PRAGMA foreign_keys = ON;`처럼 SQLite 전용 문법은 주석으로 표시했습니다.

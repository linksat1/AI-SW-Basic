# b6-1 클라우드 환경에서 웹 서비스 인프라 구축 — 실행 가이드

이 과제는 b3-1/b3-2(로컬 코드)와 근본적으로 다릅니다. **AWS 콘솔/CLI에서 실제로 손을 움직여야
하는 핸즈온 과제**이고, 실제 비용이 발생할 수 있는 클라우드 자원을 다룹니다. 그래서 이 가이드는
"이미 완성된 결과물"이 아니라 **당신이 처음부터 끝까지 직접 따라 하는 실습 순서**입니다.

## 1. 과제 개요와 이 문서의 성격

**만들어야 하는 것**: VPC로 격리된 네트워크 위에 EC2 웹 서버를 올려 외부에서 접속 가능하게
만들고, 보안 그룹과 IAM 최소 권한을 적용한 뒤, 트러블슈팅 기록과 함께 안전하게 정리까지
마치는 것.

**폴더 구조** (이번에 미리 만들어 둔 것):

## 3. Step 1 — IAM 사용자(최소 권한) 만들기

과제 제약: "관리자 권한(AdministratorAccess)은 부여하지 않는다", "EC2/VPC/Security Group
구성에 필요한 범위로 제한한다."

1. 루트 계정으로 **딱 한 번만** 로그인해 IAM 콘솔로 이동합니다.
2. **사용자(User) 생성** → 사용자 이름 예: `b6-1-lab-user`
3. **콘솔 액세스** 활성화 (본인만 로그인할 것이므로 비밀번호 직접 설정)
4. **권한 정책 연결**: `AdministratorAccess`를 선택하지 말고, 아래처럼 **커스텀 정책**을 새로
   만들어 연결합니다 (IAM → 정책 → 정책 생성 → JSON 탭에 붙여넣기).

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EC2VpcMinimalAccess",
      "Effect": "Allow",
      "Action": [
        "ec2:Describe*",
        "ec2:CreateVpc",
        "ec2:CreateSubnet",
        "ec2:CreateInternetGateway",
        "ec2:AttachInternetGateway",
        "ec2:CreateRouteTable",
        "ec2:CreateRoute",
        "ec2:AssociateRouteTable",
        "ec2:CreateSecurityGroup",
        "ec2:AuthorizeSecurityGroupIngress",
        "ec2:AuthorizeSecurityGroupEgress",
        "ec2:RevokeSecurityGroupIngress",
        "ec2:RunInstances",
        "ec2:TerminateInstances",
        "ec2:StopInstances",
        "ec2:StartInstances",
        "ec2:CreateTags",
        "ec2:DeleteTags",
        "ec2:CreateKeyPair",
        "ec2:DeleteKeyPair",
        "ec2:AllocateAddress",
        "ec2:AssociateAddress",
        "ec2:DisassociateAddress",
        "ec2:ReleaseAddress",
        "ec2:DeleteVpc",
        "ec2:DeleteSubnet",
        "ec2:DeleteInternetGateway",
        "ec2:DetachInternetGateway",
        "ec2:DeleteRouteTable",
        "ec2:DeleteRoute",
        "ec2:DisassociateRouteTable",
        "ec2:DeleteSecurityGroup",
        "ec2:DeleteVolume",
        "ec2:ModifyVpcAttribute",
        "ec2:ModifySubnetAttribute"
      ],
      "Resource": "*"
    }
  ]
}
```

**왜 이렇게 만들었는가** (평가 질문 대비): `AdministratorAccess`는 계정 전체(과금 설정,
IAM 사용자 삭제, S3의 모든 데이터 등)를 건드릴 수 있는 과도한 권한입니다. 이 실습은 EC2와
VPC(그 하위의 Subnet/IGW/RouteTable/SecurityGroup)만 다루므로, `ec2:*` 중에서도 실습에
필요한 생성·조회·연결·삭제 동작만 화이트리스트로 열어뒀습니다. S3, RDS, IAM 자체를 다루는
권한은 포함하지 않았습니다 — 이것이 "최소 권한 원칙(Principle of Least Privilege)"입니다.

5. 사용자 생성 완료 후 **루트 계정에서 로그아웃**하고, 이후 모든 작업은 방금 만든
   IAM 사용자로 로그인해서 진행합니다.

**증빙으로 남길 것**: IAM 사용자 목록 화면, 연결된 정책 화면 스크린샷 (README에 첨부 권장)

## 4. Step 2 — VPC/Subnet/Internet Gateway/Route Table 구성

VPC 콘솔 → 왼쪽 메뉴에서 하나씩 만듭니다. (VPC 마법사로 한 번에 만들어도 되지만, 각 구성요소의
역할을 이해하기 위해 **하나씩 따로 만드는 것을 권장**합니다.)

### 4-1. VPC 생성
- CIDR: `10.0.0.0/16`
- 이름 태그: `b6-1-vpc`

### 4-2. Public Subnet 생성
- 소속 VPC: `b6-1-vpc`
- 가용 영역: `ap-northeast-2a` (아무 AZ나 선택 가능)
- CIDR: `10.0.1.0/24`
- 이름 태그: `b6-1-public-subnet`
- **"퍼블릭 IPv4 자동 할당" 활성화** (서브넷 설정 → 편집에서 체크) — 이걸 켜야 이 서브넷에
  올라간 EC2가 별도 조작 없이 퍼블릭 IP를 자동으로 받습니다.

### 4-3. Internet Gateway 생성 및 연결
- 이름 태그: `b6-1-igw`
- 생성 후 **VPC에 연결(Attach to VPC)** → `b6-1-vpc` 선택

### 4-4. Route Table 설정
- Public Subnet용 라우트 테이블을 새로 만들거나(권장) 기본 라우트 테이블을 사용
- 이름 태그: `b6-1-public-rt`
- **라우트 편집**: `0.0.0.0/0` → 대상(Target) `b6-1-igw` 추가
- **서브넷 연결(Subnet Association)**: `b6-1-public-subnet`을 이 라우트 테이블에 연결

**왜 이 4단계가 순서대로 필요한가** (평가 질문 대비 — 트래픽 흐름):
```
인터넷 → Internet Gateway → (Route Table의 0.0.0.0/0 규칙으로 안내) → Public Subnet → EC2
```
- **VPC**: 다른 사용자/서비스와 완전히 격리된 나만의 가상 네트워크 "울타리"
- **Subnet**: VPC 안을 더 작게 나눈 구역. "Public"이라는 이름 자체는 AWS가 정해주는 게
  아니라, **Route Table에 인터넷 게이트웨이로 나가는 길이 있는 서브넷**을 관례상 Public
  Subnet이라고 부릅니다.
- **Internet Gateway**: VPC와 실제 인터넷을 연결하는 유일한 통로. VPC에 연결(attach)만
  해두면 자동으로 트래픽이 통하는 게 아니라, 라우트 테이블이 "이 트래픽은 IGW로 보내라"고
  명시적으로 지정해야 합니다.
- **Route Table**: 서브넷 안의 트래픽이 "어디로 가야 하는지"를 정하는 이정표. `0.0.0.0/0`
  (모든 대상)을 IGW로 보내라는 규칙이 없으면, VPC가 인터넷에 연결되어 있어도 실제로는
  트래픽이 안 나갑니다 — 이게 이 과제에서 가장 자주 나오는 "외부에서 접속이 안 돼요"의
  원인 중 하나입니다.

## 5. Step 3 — Security Group 생성

EC2 콘솔 → 보안 그룹 → 보안 그룹 생성

- 이름: `b6-1-web-sg`
- 소속 VPC: `b6-1-vpc`
- **인바운드 규칙**:
  | 유형 | 프로토콜 | 포트 | 소스 |
  |---|---|---|---|
  | HTTP | TCP | 80 | `0.0.0.0/0` |
  | SSH | TCP | 22 | `<본인의 IP>/32` (Step 2-2에서 확인한 IP) |
- **절대 추가하면 안 되는 규칙**: 포트 범위 `0-65535`를 소스 `0.0.0.0/0`으로 여는 규칙
  (실습 편의를 위해 "일단 다 열어두자"는 유혹이 강하지만, 과제 제약사항이 명시적으로 금지)
- 아웃바운드 규칙: 기본값(전체 허용) 그대로 둬도 무방 — 외부로 나가는 트래픽까지 막을
  이유는 이 실습에서는 없습니다.

**SG와 IAM의 차이** (평가 질문 대비): Security Group은 **네트워크 트래픽**(어떤 IP가 어떤
포트로 들어오고 나갈 수 있는지)을 통제하는 가상 방화벽입니다. IAM은 **AWS API 호출 권한**
(누가 EC2를 생성/삭제할 수 있는지 등 콘솔·CLI 조작 권한)을 통제합니다. 비유하면 SG는 "건물의
어느 문으로 누가 들어올 수 있는가"이고, IAM은 "건물 안에서 누가 어느 방의 열쇠를 가졌는가"에
가깝습니다.

## 6. Step 4 — EC2 인스턴스 생성 및 웹 서버 설치

EC2 콘솔 → 인스턴스 시작

- AMI: `Ubuntu Server 22.04 LTS` (또는 Amazon Linux 2023) — 프리 티어 표시 확인
- 인스턴스 유형: `t2.micro` 또는 `t3.micro` (프리 티어 대상)
- 키 페어: 새로 생성 → `.pem` 파일을 안전한 곳에 저장하고 **권한을 반드시 제한**
  ```bash
  chmod 400 <키페어이름>.pem
  ```
- 네트워크 설정: VPC=`b6-1-vpc`, Subnet=`b6-1-public-subnet`, **퍼블릭 IP 자동 할당: 활성화**
- 방화벽(보안 그룹): 기존 보안 그룹 선택 → `b6-1-web-sg`
- 스토리지: 8~10GiB (gp3), 기본값 유지
- **고급 세부 정보 → 사용자 데이터(User data)**에 아래를 넣으면 부팅과 동시에 nginx가
  자동 설치됩니다(수동 설치를 원하면 생략하고 아래 6-2를 SSH 접속 후 직접 실행):

  ```bash
  #!/bin/bash
  apt-get update -y
  apt-get install -y nginx
  systemctl enable nginx
  systemctl start nginx
  echo "OK" > /var/www/html/health
  ```

  (Amazon Linux 계열이면 `apt-get` 대신 `dnf install -y nginx`)

### 6-1. SSH 접속

```bash
ssh -i <키페어이름>.pem ubuntu@<퍼블릭IP>
# Amazon Linux면 사용자명이 ec2-user
```

### 6-2. 웹 서버 설치 확인/수동 설치

User data를 안 썼다면 접속 후 직접:
```bash
sudo apt-get update -y
sudo apt-get install -y nginx
sudo systemctl enable --now nginx
echo "OK" | sudo tee /var/www/html/health
```

### 6-3. 인스턴스 내부 검증 (과제 필수 요구사항)

```bash
# 로컬에서 웹 서버 응답 확인 (200이어야 함)
curl -i http://localhost

# 인터넷으로 아웃바운드 통신 확인 (Route Table/IGW가 제대로 됐는지 증명)
curl -i https://example.com
```
두 명령의 결과를 캡처해 `docs/` 밑에 저장하거나 README에 붙여넣으면 좋은 증빙이 됩니다.

## 7. Step 5 — 외부 접속 검증

**본인 PC(EC2가 아닌 로컬 브라우저/터미널)** 에서 아래 중 하나를 선택해 확인합니다.
(과제 요구사항: 방식 A/B 중 택1, `README.md`에 선택한 방식과 접속 정보 기재 + 스크린샷 1장 이상)

- **(A) 브라우저 접속**: 주소창에 `http://<퍼블릭IP>` 입력 → "Welcome to nginx!" 페이지가
  뜨는 화면을 스크린샷
- **(B) 헬스체크 호출**: 로컬 터미널에서
  ```bash
  curl -i http://<퍼블릭IP>/health
  ```
  `HTTP/1.1 200 OK`와 `OK` 응답이 나오는 터미널 화면을 스크린샷

스크린샷은 `docs/screenshots/` 폴더를 만들어 저장하고, `README.md`에 경로를 적어두세요.

**만약 접속이 안 된다면** → Step 8(트러블슈팅)로 이동해 실제로 겪은 문제를 기록하면서
원인을 찾아가는 것 자체가 이 과제의 핵심 학습 목표입니다. 아래 표를 먼저 훑어보세요.

| 증상 | 가장 흔한 원인 |
|---|---|
| 브라우저에서 응답 없음(타임아웃) | SG 인바운드에 80/TCP·0.0.0.0/0 규칙 누락, 또는 Route Table에 0.0.0.0/0→IGW 누락 |
| Connection refused | nginx가 설치는 됐지만 실행 중이 아님(`systemctl status nginx`로 확인) |
| SSH 접속 안 됨(timeout) | SG 인바운드 22번 포트의 소스 IP가 본인 IP와 다름(IP가 바뀌었을 수 있음, 재확인) |
| SSH 접속 안 됨(Permission denied) | `.pem` 키 권한 문제(`chmod 400`) 또는 사용자명 오타(ubuntu vs ec2-user) |
| /health가 404 | User data 스크립트 미실행 또는 `echo "OK" > .../health` 명령을 안 함 |

## 8. Step 6 — 트러블슈팅 기록

실습 중 **최소 1건**은 실제로 막혔던 경험이 있을 것입니다(없다면 SSH를 일부러 잘못된 IP로
제한해보고 재현해도 됩니다 — 실제로 문제를 겪고 해결하는 경험 자체가 목적입니다).

`docs/troubleshooting.md` 템플릿을 열어 아래 구조로 실제 경험을 채워 넣으세요.

```
증상(문제 상황) → 원인 가설 → 검증 방법 → 조치 내용 → 결과 → 재발 방지
```

말로 설명할 때 핵심은 **"어떻게 원인을 좁혀갔는가"** 입니다. 예를 들어 "안 됐는데 SG를
고쳤더니 됐다"보다, "브라우저 타임아웃 → SG 인바운드 규칙 확인 → 80 포트가 없는 것을 발견
→ 80/TCP/0.0.0.0/0 추가 → 재접속 성공 → 이후 배포 체크리스트에 SG 규칙 확인 항목 추가"처럼
**가설을 세우고 검증한 과정**이 드러나야 평가 질문("트러블슈팅 과정을 설명할 수 있는가")에
바로 답할 수 있습니다.

## 9. Step 7 — 리소스 정리(과금 방지, 필수)

**실습이 끝나면 반드시** `docs/cleanup-checklist.md`의 순서대로 삭제합니다. 삭제 순서가
중요한 이유는 서로 의존 관계가 있기 때문입니다(예: EIP가 인스턴스에 연결된 상태로는 일부
작업이 막힐 수 있고, IGW는 VPC에서 분리해야 VPC를 지울 수 있습니다).

권장 순서: **EC2 종료 → EIP 릴리스 → (있다면) NAT/ELB/RDS 삭제 → IGW 분리·삭제 → Subnet
삭제 → Route Table 삭제 → VPC 삭제**

마지막으로 **Billing Dashboard**(계정 우측 상단 → 결제 대시보드)에서 "요금 및 사용량"이
0에 수렴하는지 하루 이틀 뒤 다시 확인하는 것을 권장합니다(과금 반영에는 시차가 있습니다).

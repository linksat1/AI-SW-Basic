# B6-1 클라우드 웹 서비스 인프라 구축 — 설명 및 평가 질문 대비 자료

이 자료는 이 과제(`과제`)의 "3. 과제 목표" 5가지를 평가자 앞에서 아주 쉬운 말로 설명할 수
있도록 정리한 문서입니다. 외워서 말하기보다, 본인이 `가이드.md`를 따라 실제로 AWS 콘솔에서
만든 리소스(본인 VPC 이름, 본인 퍼블릭 IP, 본인이 겪은 오류)를 예시로 바꿔가며 연습하세요.
개념 자체는 AWS 콘솔의 실제 이름·용어를 그대로 사용했습니다.

## 1. VPC / Subnet / Route Table / Internet Gateway의 역할과 트래픽 흐름

**한 줄 비유**: VPC는 "내 소유의 사무실 건물", Subnet은 "건물 안의 층/구역", Internet
Gateway는 "건물과 도로를 잇는 정문", Route Table은 "이 구역에서 나가려면 어느 문으로
가야 하는지 적힌 안내판"입니다.

| 구성요소 | 역할 | 이 과제에서 만든 것 |
|---|---|---|
| VPC | 다른 계정/사용자와 완전히 격리된 나만의 가상 네트워크 | `b6-1-vpc` (10.0.0.0/16) |
| Subnet | VPC를 더 작은 구역으로 나눈 것. IP 대역과 가용영역(AZ)이 정해짐 | `b6-1-public-subnet` (10.0.1.0/24) |
| Internet Gateway | VPC와 실제 인터넷을 연결하는 유일한 관문. VPC에 "붙이기(Attach)"만 하면 존재하게 됨 | `b6-1-igw` |
| Route Table | 서브넷에서 나가는 트래픽을 "어디로 보낼지" 정하는 규칙표 | `0.0.0.0/0 → b6-1-igw` |

**"Public Subnet"이라는 이름은 AWS가 정해주는 게 아니다**: 서브넷 자체에는 "public"이라는
속성이 따로 없습니다. **그 서브넷과 연결된 Route Table에 `0.0.0.0/0 → Internet Gateway`
경로가 있으면** 그 서브넷을 관례적으로 Public Subnet이라 부릅니다. 이 경로가 없으면 서브넷
안의 EC2가 퍼블릭 IP를 가지고 있어도 인터넷과 통신할 수 없습니다.

**트래픽 흐름 (외부 → 서비스)**:
```
사용자 브라우저
  → 인터넷
  → Internet Gateway (b6-1-igw, VPC에 Attach됨)
  → Route Table의 라우팅 규칙(0.0.0.0/0 → igw)에 따라 안내됨
  → Public Subnet (10.0.1.0/24)
  → Security Group의 인바운드 규칙 통과 (80/TCP 허용됨)
  → EC2 인스턴스의 Nginx (포트 80에서 대기 중)
```

**말로 설명하는 예시**: "IGW를 VPC에 연결하는 것만으로는 트래픽이 자동으로 통하지
않습니다. Route Table에 명시적으로 '0.0.0.0/0(모든 대상)은 IGW로 보내라'는 규칙이 있어야
하고, 그 라우트 테이블이 실제로 제 Public Subnet에 연결(Association)되어 있어야 합니다.
이 셋(IGW 연결 + 라우트 규칙 + 서브넷 연결) 중 하나라도 빠지면 EC2에 퍼블릭 IP가 있어도
외부에서 접속이 안 됩니다 — 실제로 저는 `가이드.md` 4단계를 하나씩 순서대로 만들면서
이 세 가지가 각각 별개의 설정이라는 걸 확인했습니다."

## 2. Security Group과 IAM의 역할 차이, 최소 권한 원칙

**한 줄 비유**: Security Group은 "건물의 어느 문으로 누가(어떤 IP가) 들어올 수 있는가"를
통제하는 **네트워크 방화벽**이고, IAM은 "건물 안에서 누가 어느 방의 열쇠(AWS 리소스를
만들고 지울 권한)를 가졌는가"를 통제하는 **API 조작 권한**입니다. 완전히 다른 층위의
보안입니다 — 하나는 "패킷이 오갈 수 있는가", 하나는 "콘솔/CLI로 무엇을 할 수 있는가".

| | Security Group | IAM |
|---|---|---|
| 통제 대상 | 네트워크 트래픽(IP, 포트, 프로토콜) | AWS API 호출(EC2 생성, VPC 삭제 등 "행위") |
| 적용 위치 | EC2 인스턴스(정확히는 ENI) 단위 | 사용자/Role 단위, 계정 전체에 적용 |
| 이 과제에서 설정한 것 | 80/TCP는 전체 허용, 22/TCP는 내 IP만 허용 | `b6-1-lab-user`에게 EC2/VPC/SG 관련 동작만 허용하는 커스텀 정책 |
| 잘못 설정 시 위험 | 포트가 뚫려 있으면 외부에서 서버 자체를 공격 가능 | 권한이 넓으면 실수/탈취 시 계정 전체(과금, 데이터)가 위험 |

**최소 권한 원칙(Principle of Least Privilege)을 실제로 어떻게 적용했는가**:
`AdministratorAccess`(계정 전체를 다 만지는 권한)를 부여하지 않고, `가이드.md` 3장의
JSON 정책처럼 **이 실습에서 실제로 쓰는 EC2/VPC 관련 동작만** 화이트리스트로 나열했습니다.
S3, RDS, IAM 자체를 다루는 권한(예: 다른 IAM 사용자를 삭제하거나 비밀번호를 바꾸는 권한)은
전혀 포함하지 않았습니다.

**왜 필요한가**: 만약 이 실습용 IAM 사용자의 자격 증명(액세스 키 등)이 실수로 코드에 커밋되어
공개 저장소에 노출되는 사고가 나더라도, 이 사용자는 EC2/VPC 관련 동작만 할 수 있으므로
공격자가 S3 버킷을 통째로 지우거나 다른 서비스에 손댈 수 없습니다. 권한 범위 자체가
"사고가 나도 피해가 제한되는" 방어선 역할을 합니다.

## 3. 외부 요청이 EC2 웹 서버까지 도달하기 위해 필요한 설정

세 가지가 **동시에** 맞아야 합니다. 하나라도 빠지면 접속이 안 됩니다.

1. **라우팅(Routing)**: Public Subnet의 Route Table에 `0.0.0.0/0 → Internet Gateway`
   경로가 있어야 합니다. (없으면: 트래픽이 애초에 VPC 밖으로/안으로 오갈 길이 없음)
2. **퍼블릭 IP(Public IP)**: EC2 인스턴스가 인터넷에서 도달 가능한 주소를 가지고 있어야
   합니다. Public Subnet의 "퍼블릭 IPv4 자동 할당"을 켜두면 인스턴스 시작 시 자동으로
   할당됩니다. (없으면: 사설 IP뿐이라 인터넷에서 그 주소로 찾아올 방법이 없음)
3. **보안 그룹(Security Group)**: 인바운드 규칙에 80/TCP를 0.0.0.0/0으로 허용해야 합니다.
   (없으면: 트래픽이 인스턴스 코앞까지 왔어도 방화벽에서 막힘)

**세 가지를 다 갖췄는데도 안 된다면 확인할 4번째**: 실제로 웹 서버(Nginx)가 인스턴스
안에서 **실행 중**이어야 합니다(`systemctl status nginx`). 네트워크 설정이 전부 맞아도
서버 프로세스 자체가 꺼져 있으면 `Connection refused`가 납니다.

**말로 설명하는 예시**: "저는 이 셋을 계층으로 나눠서 이해했습니다 — 1번(라우팅)은
'이 동네까지 배달이 오는가', 2번(퍼블릭 IP)은 '우리 집 주소가 실제로 등록되어 있는가',
3번(보안그룹)은 '현관문이 잠겨있지 않은가'입니다. 셋 다 확인해야 택배(HTTP 요청)가
실제로 저희 집(EC2의 Nginx)까지 옵니다."

## 4. 오류 발생 시 로그/증상 기반 트러블슈팅 과정

과제에서 요구하는 6단계 구조를 실제로 어떻게 진행했는지 설명할 수 있어야 합니다
(구체적인 사례는 `docs/troubleshooting.md`에 실제로 겪은 문제로 기록되어 있습니다).

```
증상 파악 → 원인 가설 세우기 → 가설 검증 → 조치 → 결과 재확인 → 재발 방지책 마련
```

**단계별로 어떻게 접근하는가**:
1. **증상**: 무엇을 시도했고, 기대와 다르게 무엇이 일어났는지를 구체적으로 적습니다
   ("안 돼요"가 아니라 "브라우저가 타임아웃됐다" / "Connection refused가 떴다" / "SSH가
   Permission denied로 거부됐다"처럼 에러의 "종류"를 구분하는 것이 원인 후보를 좁히는
   첫걸음입니다).
2. **원인 가설**: 증상의 종류에 따라 의심되는 지점이 다릅니다. 타임아웃(응답이 아예 없음)은
   보통 네트워크/방화벽 단계(SG, Route Table)에서 막혔다는 신호이고, Connection
   refused(응답은 오지만 거부됨)는 서버가 그 포트에서 아예 듣고 있지 않다는 신호입니다.
3. **검증**: 콘솔에서 SG 인바운드 규칙, 라우트 테이블을 직접 눈으로 확인하거나, 인스턴스
   안에 SSH로 들어가 `systemctl status nginx`, `curl -i http://localhost`, `sudo ss -tlnp`
   (어떤 포트가 실제로 열려 있는지) 등으로 서버 쪽 상태를 직접 확인합니다.
4. **조치**: 검증으로 확인된 원인만 정확히 고칩니다(원인을 모른 채 여러 개를 한꺼번에
   바꾸면 나중에 "무엇 때문에 해결됐는지" 알 수 없게 됩니다).
5. **결과**: 조치 후 반드시 **처음 증상이 나타났던 방식 그대로 재현해서** 해결을 확인합니다
   (예: 브라우저로 다시 접속, 또는 `curl -i` 재실행).
6. **재발 방지**: "다음에 새 인스턴스를 배포할 때 무엇을 미리 체크하면 이 문제를 피할 수
   있는가"를 체크리스트 항목으로 남깁니다.

**왜 로그/증거 기반이 중요한가**: "느낌"으로 조치하면(예: "그냥 SG를 전체 허용으로
바꿔보자") 문제가 우연히 해결될 수는 있어도 왜 해결됐는지 모른 채 넘어가게 되고, 오히려
과제 제약사항이 금지하는 "전체 포트 개방" 같은 위험한 설정을 임시방편으로 남기기 쉽습니다.
가설 → 검증 순서를 지키면 정확히 필요한 만큼만 고치게 됩니다.

## 5. 클라우드 과금 요인과 안전한 리소스 정리 순서·이유

**대표적인 과금 요인** (이 과제 범위에서):

| 리소스 | 과금 기준 | 흔한 실수 |
|---|---|---|
| EC2 인스턴스 | 켜져 있는 시간(정지해도 아니고 "실행 중"일 때) | 실습 후 종료를 안 하고 콘솔 탭만 닫음 |
| EBS 볼륨 | 인스턴스와 무관하게 볼륨이 존재하는 것 자체로 과금 | 인스턴스 종료 시 "종료 시 삭제" 옵션을 안 켜서 볼륨만 남음 |
| Elastic IP | **인스턴스에 연결되지 않은 채 할당만 되어 있으면** 오히려 과금(가동 중인 인스턴스에 붙어 있으면 무료) | 테스트 중 인스턴스를 지웠는데 EIP는 그대로 할당 상태로 남김 |
| 데이터 전송(아웃바운드) | 인터넷으로 나가는 트래픽 양 | 이 과제 규모에서는 미미하지만 실무에서는 큰 비중 |

**왜 "삭제 순서"가 중요한가**: 리소스끼리 의존 관계가 있어서, 의존하는 대상이 먼저
정리되어야 다음 단계가 가능합니다.
- EIP가 인스턴스에 연결(Associate)된 상태에서는 먼저 연결 해제(Disassociate)해야
  릴리스(Release)할 수 있습니다.
- Internet Gateway는 VPC에서 분리(Detach)해야 삭제할 수 있고, VPC는 그 안의
  Subnet/Route Table/Security Group이 모두 없어져야 삭제할 수 있습니다.
- 이 순서를 무시하고 아무거나 먼저 지우려고 하면 콘솔이 "다른 리소스가 참조 중이라 삭제할
  수 없다"는 에러를 냅니다 — 이 자체가 "의존 관계"를 보여주는 신호입니다.

**"삭제했다"와 "삭제를 확인했다"는 다르다**: EC2를 종료 버튼만 누르고 화면을 벗어나면
실제로 완전히 종료됐는지, 연결된 EBS/EIP가 같이 정리됐는지 놓치기 쉽습니다. 그래서
`docs/cleanup-checklist.md`는 각 리소스 목록 화면에서 "실제로 없어진 것을 두 눈으로
확인"하고 체크하도록 만들었고, 마지막에 Billing Dashboard에서 과금이 실제로 0에
수렴하는지까지 확인하는 것을 권장합니다(콘솔 상태와 실제 과금 반영 사이에는 약간의
시차가 있을 수 있기 때문입니다).

## 6. 발표 또는 평가 때 사용할 짧은 요약

> "VPC 안에 Public Subnet을 만들고, Internet Gateway를 연결한 뒤 Route Table에
> 0.0.0.0/0→IGW 경로를 추가해 외부와 통신 가능한 네트워크를 구성했습니다. EC2에 Nginx를
> 올리고, Security Group으로 HTTP(80)는 전체 허용, SSH(22)는 제 IP만 허용해 필요한
> 포트만 열었습니다. IAM은 관리자 권한 대신 EC2/VPC 조작만 가능한 커스텀 정책으로
> 최소 권한을 적용했습니다. 배포 중 겪은 문제는 증상→가설→검증→조치→결과→재발방지
> 순서로 기록했고, 실습 종료 후에는 의존 관계 역순(EC2→EIP→IGW→Subnet→RouteTable→VPC)으로
> 리소스를 정리해 과금이 남지 않도록 했습니다."

## 7. 평가 질문 대비 답변 자료

### 항목 1. 네트워크 설계 질문

**Q1. VPC CIDR을 10.0.0.0/16으로, Subnet을 10.0.1.0/24로 잡은 이유는?**

`/16`은 VPC 안에서 나중에 여러 서브넷(예: Public 2개, Private 2개 등)으로 나눌 여유
공간을 남겨두는 관례적인 크기이고, `/24`(256개 IP)는 EC2 몇 대를 올리는 실습 규모에
충분한 크기입니다. AWS VPC 마법사가 기본으로 제시하는 값이기도 해서 다른 자료와
호환성도 좋습니다.

**Q2. Route Table을 서브넷마다 따로 만드는 이유는?**

만약 나중에 Private Subnet(인터넷 직접 노출 없이 NAT을 통해서만 나가는 서브넷)을
추가한다면, Public Subnet과는 다른 라우팅 규칙(0.0.0.0/0 → NAT Gateway)이 필요합니다.
서브넷마다 라우트 테이블을 분리해두면 "이 구역은 이렇게 나간다"는 규칙을 독립적으로
관리할 수 있습니다. 이번 실습은 Public Subnet 1개뿐이라 차이가 크게 드러나지 않지만,
구조적으로 옳은 습관입니다.

**Q3. 퍼블릭 IP 자동 할당을 켜지 않으면 어떻게 되는가?**

EC2가 사설 IP(10.0.1.x)만 가지게 되어, 사설 IP는 인터넷 어디서도 라우팅되지 않는
주소이므로 외부에서 접속할 방법이 없어집니다. 이 경우 Elastic IP를 별도로 할당해
연결해야 같은 효과를 낼 수 있습니다.

---

### 항목 2. 보안 설계 질문

**Q1. SSH를 0.0.0.0/0으로 열지 않고 내 IP로 제한한 이유는?**

SSH(22번 포트)가 전체 공개되어 있으면 전 세계 어디서든 인스턴스에 비밀번호/키
무차별 대입 공격을 시도할 수 있습니다. 관리 목적(나 혼자 접속)이라면 내 IP 하나만
허용해도 충분하고, 공격 표면을 극적으로 줄일 수 있습니다.

**Q2. 왜 전체 포트(0-65535)를 한 번에 열면 안 되는가?**

포트 하나하나가 "이 서비스만 외부에 노출하겠다"는 명시적 선언입니다. 전체 포트를
열면 지금은 안 쓰지만 나중에 실수로 켜질 수 있는 다른 서비스(예: 관리용 포트,
데이터베이스 기본 포트)까지 그대로 외부에 노출되어, 의도하지 않은 공격 지점이 생깁니다.

**Q3. IAM 최소 권한을 어떻게 검증했는가?**

`가이드.md`에서 만든 IAM 정책 JSON에 `AdministratorAccess`가 포함되지 않았는지,
S3/RDS 등 이 실습과 무관한 서비스의 Action이 없는지 정책 내용을 직접 읽어 확인했습니다.
IAM 콘솔의 "액세스 관리자(Access Advisor)" 탭에서 이 사용자가 실제로 어떤 서비스를
호출했는지도 사후에 확인할 수 있습니다.

### 항목 3. 트러블슈팅/운영 질문

**Q1. 이번 실습에서 실제로 겪은 문제는 무엇이었는가?**

`docs/troubleshooting.md`의 "사건 #1"을 그대로 설명합니다(실제 겪은 증상 → 가설 →
검증 → 조치 → 결과 → 재발 방지 순서로).

**Q2. Elastic IP를 왜 신경 써서 정리해야 하는가?**

EIP는 AWS의 IPv4 주소 부족 문제 때문에, "할당은 됐지만 실제로 실행 중인 인스턴스에
붙어 있지 않은" 상태일 때 오히려 과금됩니다(자원을 붙잡아두고 안 쓰는 것에 대한
페널티 성격). 이 과제는 자동 할당 퍼블릭 IP만 써서 EIP를 따로 만들지 않았다면 해당
사항이 없지만, EIP를 만들었다면 인스턴스 종료 전에 연결 해제·릴리스까지 챙겨야 합니다.

**Q3. 리소스를 다 지웠는데도 안심할 수 없는 경우는?**

콘솔에서 리소스 목록이 비어 보여도, 과금은 실제 사용량 집계 후 하루 정도 지연되어
Billing Dashboard에 반영될 수 있습니다. 그래서 삭제 직후 판단하지 않고, 하루 이틀
뒤 Billing Dashboard의 "요금 및 사용량"을 다시 확인하는 습관이 필요합니다.

---

라우트 테이블, 보안 그룹 인바운드 규칙)을 같이 열어 보여주면서 설명하는 것이 가장
확실합니다.
